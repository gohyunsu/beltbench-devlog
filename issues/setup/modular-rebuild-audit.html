beltbench / 개발 기록
프로젝트이슈
ISSUE-008 · 2026-08-06 · 진행 중

움직이는 물체 조작을 기능 추가가 아닌 계약 중심의 모듈 재구축 문제로 정의했다.

기존 구현은 정지 물체의 관찰, 초기 pose, tracking 입력 변환, grasp 후보, xArm trajectory dry-run까지 개별 경로를 갖고 있다. 그러나 conveyor interception에 필요한 동기화, 속도 추정, 미래 상태 예측, latency budget, 충돌 검사는 아직 공통 계약으로 연결되지 않았다. 기존 script에 조건문을 계속 추가하면 offline 검증과 실제 장비 경로가 갈라지므로, 기록 가능한 데이터 계약을 중심으로 내부 구조를 단계적으로 교체한다.

확인한 연구 맥락

BeltBench의 현재 기준선은 M0 정지 tabletop pick-place이며 M1에서 일정한 belt 속도와 interception timing을 추가한다. FoundationPose는 초기 6D pose를 만들고 GoTrack은 이후 frame의 pose measurement를 제공한다. BODex 계열은 object-frame grasp 후보를 제공하며, 현재 xArm planning은 IK, joint limit, velocity interpolation까지 검증하지만 collision-aware planning은 아니다.

참고 저장소를 최신 원격과 비교한 결과, BeltBench가 사용하는 FoundationPose·DA3 snapshot 이후 AutoDex 쪽 추가 변경은 주로 Franka 실행 경로였다. 반면 ParaDex 최신 변경에는 camera 장애 격리, process dashboard, hand-eye 및 mounting transform 수정이 포함되어 있어 향후 adapter 설계 시 선별 검토할 가치가 있다. fork 전체를 병합하지 않고 필요한 변경을 계약 테스트와 함께 가져오는 방식을 택한다.

발생한 문제와 원인

로컬 테스트 환경 부재

기본 Python에서 test discovery는 되었지만 NumPy와 OpenCV가 없어 대부분 import 단계에서 멈췄다. 코드 실패와 환경 실패를 구분할 수 있도록 CPU core 환경과 GPU tracking 환경을 분리해야 한다.

서버 clone 실패

GPU 서버에는 GitHub credential이 없고 BeltBench는 private repository라 HTTPS clone이 인증 입력 단계에서 실패했다. 원격 HEAD와 동일함을 확인한 로컬 Git 작업 사본을 SSH로 전송해 revision을 보존하는 방식으로 전환했다.

공용 Conda 실행 오류

서버의 /usr/bin/lsb_release가 실행 가능한 파일처럼 보이지만 interpreter인 system Python 실행 권한이 없어 exit 126을 반환했다. 구버전 Conda가 OS 정보를 수집하다 실패했다.

NFS 환경 생성 지연

사용자 home filesystem 사용률이 높고 Conda transaction이 NFS에서 장시간 소요됐다. 큰 CUDA 환경은 기본 환경 검증과 cache 위치 확인 없이 중복 생성하지 않기로 했다.

해결 절차와 현재 결과

GitHub CLI의 active account가 gohyunsu이고 private repository 접근 scope를 갖는지 확인했다. BeltBench와 devlog의 로컬 HEAD가 각각 원격 기본 branch와 정확히 일치하는 것도 확인했다. 서버에서는 공용 Conda 경로를 명시하고, Conda 실행에 한해서만 문제가 있는 system 명령을 PATH에서 제외하자 metadata 해석과 Python 3.10 dependency solve가 통과했다.

검증 경계: 2026-08-06에 서버 공용 Python 3.10, 기존 NumPy·SciPy, 임시 directory에 격리 설치한 OpenCV 4.8.1로 unit test 18개를 실행해 모두 통과했다. 이는 core CPU code와 artifact adapter의 구조 검증이다. GoTrack GPU 정확도, conveyor prediction, collision-aware planning은 아직 검증하지 않았다.

재구축할 모듈 경계

ObservationBatch → ObjectMeasurement → ObjectTrack → InterceptRequest → InterceptPlan → ExecutionEvent → TrialRecord 순서의 typed contract를 기준으로 삼는다. 모든 contract는 source timestamp, clock domain, 좌표계 방향, SI unit, uncertainty, provenance를 명시한다. FoundationPose, GoTrack, BODex, simulator, xArm과 camera transport는 이 core 바깥의 adapter가 된다.

첫 단계는 기존 scene·pose·observation 표현을 하나로 통합하고 recorded replay와 synthetic multi-camera generator를 만드는 것이다. 다음으로 tracker와 독립적인 동적 상태 추정, belt-constrained prediction, time-indexed collision-aware interception planning을 순서대로 구현한다. 실제 로봇이 없어도 occlusion, frame drop, timestamp skew, depth noise, latency, infeasible IK와 missed window를 simulation에서 주입해 안전 상태와 trial record를 검증할 수 있다.

완료 조건과 다음 행동

한 번 실행되는 script는 완료로 보지 않는다. CPU unit test, deterministic offline replay, GPU 또는 simulator smoke, failure injection 결과가 revision 및 environment identity와 함께 남아야 한다. 다음 작업은 core contract migration의 첫 acceptance test를 작성하고, compute node의 짧은 GPU allocation에서 driver·CUDA·checkpoint smoke를 별도로 수행하는 것이다.

초기 pose와 GoTrack 연결, GPU runtime, M0 평가 계약이 이 작업의 선행 기록이다.

프로젝트이슈
ISSUE-008 · 2026-08-06 · 진행 중

움직이는 물체 조작을 기능 추가가 아닌 계약 중심의 모듈 재구축 문제로 정의했다.

기존 구현은 정지 물체의 관찰, 초기 pose, tracking 입력 변환, grasp 후보, xArm trajectory dry-run까지 개별 경로를 갖고 있다. 그러나 conveyor interception에 필요한 동기화, 속도 추정, 미래 상태 예측, latency budget, 충돌 검사는 아직 공통 계약으로 연결되지 않았다. 기존 script에 조건문을 계속 추가하면 offline 검증과 실제 장비 경로가 갈라지므로, 기록 가능한 데이터 계약을 중심으로 내부 구조를 단계적으로 교체한다.

확인한 연구 맥락

BeltBench의 현재 기준선은 M0 정지 tabletop pick-place이며 M1에서 일정한 belt 속도와 interception timing을 추가한다. FoundationPose는 초기 6D pose를 만들고 GoTrack은 이후 frame의 pose measurement를 제공한다. BODex 계열은 object-frame grasp 후보를 제공하며, 현재 xArm planning은 IK, joint limit, velocity interpolation까지 검증하지만 collision-aware planning은 아니다.

참고 저장소를 최신 원격과 비교한 결과, BeltBench가 사용하는 FoundationPose·DA3 snapshot 이후 AutoDex 쪽 추가 변경은 주로 Franka 실행 경로였다. 반면 ParaDex 최신 변경에는 camera 장애 격리, process dashboard, hand-eye 및 mounting transform 수정이 포함되어 있어 향후 adapter 설계 시 선별 검토할 가치가 있다. fork 전체를 병합하지 않고 필요한 변경을 계약 테스트와 함께 가져오는 방식을 택한다.

발생한 문제와 원인

로컬 테스트 환경 부재

기본 Python에서 test discovery는 되었지만 NumPy와 OpenCV가 없어 대부분 import 단계에서 멈췄다. 코드 실패와 환경 실패를 구분할 수 있도록 CPU core 환경과 GPU tracking 환경을 분리해야 한다.

서버 clone 실패

GPU 서버에는 GitHub credential이 없고 BeltBench는 private repository라 HTTPS clone이 인증 입력 단계에서 실패했다. 원격 HEAD와 동일함을 확인한 로컬 Git 작업 사본을 SSH로 전송해 revision을 보존하는 방식으로 전환했다.

공용 Conda 실행 오류

서버의 /usr/bin/lsb_release가 실행 가능한 파일처럼 보이지만 interpreter인 system Python 실행 권한이 없어 exit 126을 반환했다. 구버전 Conda가 OS 정보를 수집하다 실패했다.

NFS 환경 생성 지연

사용자 home filesystem 사용률이 높고 Conda transaction이 NFS에서 장시간 소요됐다. 큰 CUDA 환경은 기본 환경 검증과 cache 위치 확인 없이 중복 생성하지 않기로 했다.

해결 절차와 현재 결과

GitHub CLI의 active account가 gohyunsu이고 private repository 접근 scope를 갖는지 확인했다. BeltBench와 devlog의 로컬 HEAD가 각각 원격 기본 branch와 정확히 일치하는 것도 확인했다. 서버에서는 공용 Conda 경로를 명시하고, Conda 실행에 한해서만 문제가 있는 system 명령을 PATH에서 제외하자 metadata 해석과 Python 3.10 dependency solve가 통과했다.

검증 경계: 2026-08-06에 서버 공용 Python 3.10, 기존 NumPy·SciPy, 임시 directory에 격리 설치한 OpenCV 4.8.1로 unit test 18개를 실행해 모두 통과했다. 이는 core CPU code와 artifact adapter의 구조 검증이다. GoTrack GPU 정확도, conveyor prediction, collision-aware planning은 아직 검증하지 않았다.

2026-08-27 재감사: 실제 연결과 문서 구조를 다시 분리했다

초기 계획 이후 구현 규모가 크게 증가했지만, 최상위 architecture 문서는 여전히 offline reference라고 설명하고 일부 시연 문서는 과거 RGB-D 경로에서 끝나 있었다. 반대로 실제 최신 runner는 RGB-only event acquisition부터 collision admission, future-start handoff, PhysX feedback와 rigid-object lifecycle까지 연결돼 있었다. 문서가 실제 실행보다 뒤처진 상태에서는 새 기능의 역할과 readiness blocker를 판단할 단일 기준이 없었다.

선행 코드도 원격 source identity를 다시 고정했다. AutoDex는 willi19/autodex-code@3dcb5ef, ParaDex는 willi19/paradex@312e5c5를 기준으로 읽었다. ParaDex의 공개 branch 17개를 head 단위로 비교했지만 최신 main보다 크게 뒤처진 실험 branch를 통째로 병합할 근거는 없었다. AutoDex의 object-relative grasp와 offline filtering, ParaDex의 timestamped distributed RGB I/O와 calibration 원리는 유지하되, static episode runner, first-success planning, whole-mesh 제거, hard-coded robot 조합, legacy Isaac Gym simulator는 runtime 구현으로 채택하지 않았다.

최신 실제 증거: RTX 3090의 r627은 revision 0d7171a에서 RGB topology 15단계를 모두 실행했다. RGB observation이 selection을 구동했고 simulator truth는 evaluator에만 남았다. Contact, attachment, release, containment와 407/407 영상 frame은 확인됐다. 그러나 professor_demo_ready=false다. 1,625 control tick 중 38개가 한 주기 이상 늦었고 approach에서 최대 23개가 연속 지연됐으며, controller에 실행 가능한 prevalidated stop route가 설치되지 않았다. 따라서 영상은 공개 성공 자료로 승격하지 않았다.

확정한 모듈과 시간 계층

  1. Offline compiler: grasp 생성·정규화, intrinsic/deployment 검증, complete command family, uncertainty tube와 phase-aware stop을 만든다.
  2. Startup residency: source digest와 calibration을 확인하고 segmentation·pose·collision backend, fixed-capacity catalog와 controller route를 한 번만 load·warmup한다.
  3. Event acquisition: 충분히 upstream에서 synchronized RGB를 받아 segmentation과 stable-pose-conditioned planar pose를 한 번 bounded solve한다.
  4. Event decision: encoder-aligned prediction, resident command-family query, robust-slack ranking, exact remaining-command collision과 future-start lease를 commit 전에 완료한다.
  5. Periodic state/control: 60 Hz에서는 encoder propagation, admitted correction, command sampling, feedback, guarded contact와 lifecycle/stop monitor만 수행한다.
  6. Asynchronous evidence: JSON serialization, video와 Viser는 control tick 밖에서 measured state를 소비한다.

FoundPose는 physical RGB initial pose 후보지만 매 frame tracker로 사용하지 않는다. 현재 source-closed physical candidate는 accuracy holdout을 통과하지 못했다. GoTrack은 두 카메라 topology에서 latency와 error를 새로 측정한 뒤 optional low-rate correction 또는 reacquisition backend로만 판단한다. Nominal 상태 전파는 object yaw가 변하지 않는 task 가정과 independent encoder를 사용하므로 GoTrack이 기본 control-state owner일 필요가 없다.

2026-08-27 phase-aware abort의 runtime 경계를 분리했다

r627의 stop blocker를 닫기 위해 기존 Isaac runner에 즉시 정지 boolean을 추가하는 방안부터 배제했다. 접촉 전, 접촉 commit, attached transport, release commit, contained 이후에는 안전한 취소 동작이 서로 다르다. 따라서 nominal full command의 모든 sample을 하나의 미래 abort latch와 사전 검증된 resident abort command에 연결하고, controller feedback에서 상수 시간으로 선택하는 방식을 구현했다. 변경은 476240a의 route selection과 57d9a16의 activation boundary 두 커밋으로 나누어 push했다.

발생한 문제원인해결과 결과
Abort catalog가 있어도 runtime에서 어느 경로를 실행할지 결정할 수 없었음계약과 unit fixture는 offline metadata까지만 다뤘고 controller progress, generation, freshness가 연결되지 않았음greatest_reached_nominal_sample_index를 immutable catalog index에 직접 매핑했다. stale feedback, lineage/state mismatch, progress regression, missed latch는 모두 protective stop 요구로 전환한다.
Route를 선택해도 device와 controller가 실제 slot을 갖는지 증명할 수 없었음slot ID와 upload event 문자열이 device residency 또는 controller ownership receipt를 의미하지 않음startup capability, metadata-only activation request, deadline-bound receipt를 별도 계약으로 만들었다. 온라인 메시지에는 trajectory tensor를 넣지 않고 slot, CUDA event, digest, generation만 운반한다.
Backend 호출 중 예외나 late acknowledgement 뒤 slot을 재사용할 위험호출 실패가 controller switch 미실행을 보장하지 않음backend 호출 이후 유효한 completion receipt가 없으면 activation_uncertain으로 격리한다. 다른 abort를 재시도하거나 allocation을 release하지 않는다.
서버 private clone 인증 실패RTX workstation에는 GitHub HTTPS credential이 없음기존 dirty checkout을 보존하고 로컬 57d9a16 Git bundle을 SSH stdin으로 전송해 /home/hyunsu/.agile/projects/beltbench-57d9a16 clean checkout을 만들었다.

검증 결과와 해석

RTX 3090, driver 535.309.01, Python 3.10.20, NumPy 1.26.4, Torch 2.5.1+cu121 환경에서 관련 test 39개가 모두 통과했다. clean revision은 57d9a16b41e2296bd9b2bc04c89d5df874debe05다. 실제 control 주기와 분리된 startup 검증을 먼저 수행한 뒤, fake slot backend를 이용해 host-side runtime 경로 2,000회를 측정했다.

해석 제한: 이 수치는 RTX host에서 계약, digest, lookup, fake backend receipt의 비용을 측정한 것이다. 실제 abort tensor upload, cuRobo full-task collision, CUDA event wait, Isaac articulation command switch, controller tracking, protective stop은 실행하지 않았다. 따라서 host-side 모듈 경계가 60 Hz loop에 들어갈 여유가 있다는 예비 결과일 뿐, r627의 prevalidated_controller_stop_route_not_installed blocker를 닫지 않는다.

다음 구현 순서

  1. 테스트 hold fixture가 아닌 독립 계획·충돌·동역학 검증된 abort command를 materialize하고, 실제 CUDA catalog upload와 Isaac slot-controller backend를 연결해 fault injection으로 전환을 검증한다.
  2. r627의 approach 구간을 재현해 command preparation과 CPU PhysX substep 비용을 분리 최적화하고, 동일 pacing policy로 여러 독립 run을 통과시킨다.
  3. Resident cuRobo collision gate를 exact remaining arm/hand/object command에 연결하고, HPP-FCL mesh oracle holdout에서 false accept 0과 target deadline을 동시에 확인한다.
  4. 물리 RGB rig가 준비되면 native frame만으로 synchronization, clock mapping, undistortion, segmentation과 planar pose sealed holdout을 수행한다.
  5. Camera·encoder live/controller disabled shadow mode를 거친 뒤 낮은 belt 속도에서 supervised execution으로 넘어간다.

이 순서는 professor용 영상 품질을 먼저 꾸미는 계획이 아니다. Stop과 pacing을 닫지 않은 영상은 functional diagnostic으로만 남기고, 실제 실행 가능한 module authority가 하나씩 연결될 때 같은 real-time visualization을 다시 생성한다.

2026-08-06 당시 정의한 초기 모듈 경계

ObservationBatch → ObjectMeasurement → ObjectTrack → InterceptRequest → InterceptPlan → ExecutionEvent → TrialRecord 순서의 typed contract를 기준으로 삼는다. 모든 contract는 source timestamp, clock domain, 좌표계 방향, SI unit, uncertainty, provenance를 명시한다. FoundationPose, GoTrack, BODex, simulator, xArm과 camera transport는 이 core 바깥의 adapter가 된다.

첫 단계는 기존 scene·pose·observation 표현을 하나로 통합하고 recorded replay와 synthetic multi-camera generator를 만드는 것이다. 다음으로 tracker와 독립적인 동적 상태 추정, belt-constrained prediction, time-indexed collision-aware interception planning을 순서대로 구현한다. 실제 로봇이 없어도 occlusion, frame drop, timestamp skew, depth noise, latency, infeasible IK와 missed window를 simulation에서 주입해 안전 상태와 trial record를 검증할 수 있다.

2026-08-06 당시 완료 조건

한 번 실행되는 script는 완료로 보지 않는다. CPU unit test, deterministic offline replay, GPU 또는 simulator smoke, failure injection 결과가 revision 및 environment identity와 함께 남아야 한다. 다음 작업은 core contract migration의 첫 acceptance test를 작성하고, compute node의 짧은 GPU allocation에서 driver·CUDA·checkpoint smoke를 별도로 수행하는 것이다.

초기 pose와 GoTrack 연결, GPU runtime, M0 평가 계약이 이 작업의 선행 기록이다.

자동 calibration 코드는 무엇을 입력으로 받고, 무엇을 계산하는가?

BeltBench는 ParaDex의 흐름을 참고했지만, 전체 runtime을 복사하지 않았다. xArm·camera transport와 무관하게 동작하는 작은 calibration core를 만들고, 실제 장비 연결은 두 개의 thin adapter로 제한했다. 이 페이지는 코드의 데이터 흐름과 수학을 함수 단위로 설명한다.

핵심 아이디어: Charuco board를 xArm tool에 단단히 고정한다. robot이 여러 안전 pose로 이동하면, 매 pose에서 robot은 base_to_tool을, camera는 camera_to_board를 제공한다. 둘은 같은 물리 board를 가리키므로 이 반복 관측으로 camera extrinsic과 board mount transform을 함께 찾을 수 있다.

고정 camera의 extrinsic과 tool-mounted board를 함께 푼다

BeltBench core는 한 번의 capture session에서 base_to_camera와 tool_to_board를 함께 추정한다. 전자는 “고정 camera가 xArm base에서 어디에 있는가”라는 extrinsic이고, 후자는 “tool에 붙인 board가 tool에서 어디에 있는가”라는 mount transform이다. 여러 robot pose에서 같은 board를 관측해 두 미지수를 동시에 제약한다.

기존 ParaDex의 extrinsic 흐름은 사람이 board를 capture volume 안에서 움직이며 multi-camera reconstruction을 만드는 별도 session이고, hand-eye 흐름은 robot이 미리 준비한 trajectory를 따라 움직이는 별도 session이다. 이는 기존 distributed camera/COLMAP pipeline에 잘 맞는 설계다. 반면 BeltBench의 목표는 selected fixed camera를 현재 xArm workcell에 빠르게 연결하는 것이므로, tool-mounted board를 여러 pose에서 관측해 camera별 extrinsic과 mount transform을 함께 푼다. camera끼리 직접 동시에 보지 못해도, 각 camera가 board를 네 pose 이상 보면 같은 robot base를 기준으로 독립적으로 풀 수 있다.

0. 좌표계를 먼저 읽는 법

A_to_B는 B 좌표계에서 표현된 점을 A 좌표계로 옮기는 4×4 homogeneous transform이다. 위쪽 3×3은 방향(rotation), 오른쪽 3×1은 위치(translation)다. 따라서 매 pose에서 동일한 board 위치는 다음 두 경로로 표현된다.

base_to_tool · tool_to_board
    =
base_to_camera · camera_to_board

왼쪽은 xArm base에서 tool을 거쳐 board로 가는 경로, 오른쪽은 xArm base에서 fixed camera를 거쳐 board로 가는 경로다. 미지수는 고정된 tool_to_board와 base_to_camera다. robot pose와 board 영상 pose가 다양하게 쌓일수록 두 값을 안정적으로 찾을 수 있다.

1. charuco.py: image를 board pose로 바꾼다

Board dataclass는 Charuco board의 square 수·실제 길이·marker dictionary를 정의한다. Charuco는 chessboard의 정밀한 corner와 ArUco marker의 식별성을 결합한 calibration pattern이다. image마다 detect()는 다음을 수행한다.

  1. private intrinsic에서 3×3 camera matrix와 lens distortion을 읽는다.
  2. cv2.aruco.CharucoDetector로 corner와 ID를 찾는다.
  3. corner 수가 최소 기준보다 작으면 None을 돌려 그 image를 버린다.
  4. board의 알려진 3D corner와 image의 2D corner를 짝지어 cv2.solvePnP를 실행한다.
  5. rotation vector와 translation을 4×4 camera_to_board transform으로 만든다.
corners, ids = CharucoDetector(board).detectBoard(image)
if ids is None or len(ids) < minimum_corners:
    return None
ok, rvec, tvec = cv2.solvePnP(object_points, image_points,
                              camera_matrix, distortion)

이 단계는 “카메라가 board를 본다”를 숫자로 만드는 단계다. blur·가림·너무 작은 board 때문에 corner가 부족하면 억지로 pose를 만들지 않는다.

2. capture.py: 장비 의존성을 두 interface로 제한한다

capture_session()은 xArm SDK나 특정 camera SDK를 import하지 않는다. 대신 다음 두 protocol만 요구한다.

Robot:  move_joints(joints), base_to_tool()
Frames: read(camera_ids)

실제 xArm adapter는 승인된 joint waypoint로 이동하고, 실제 camera adapter는 선택 camera의 동기화된 frame을 반환하면 된다. core는 각 waypoint 뒤 image를 읽고, 유효한 Charuco observation만 JSON session에 넣는다.

for joints in waypoints:
    robot.move_joints(joints)
    for camera, image in frames.read(camera_ids).items():
        observation = detect(image, intrinsics[camera])
        if observation is not None:
            board_poses[camera] = observation.camera_to_board.tolist()
    samples.append({"base_to_tool": robot.base_to_tool().tolist(),
                    "camera_to_board": board_poses})

통합 runner에는 선택적으로 원본 frame을 local evidence directory에 기록하는 기능도 추가했다. 이 JPEG는 board가 실제로 보였는지, 어느 자세에서 corner가 부족했는지 다시 검토하기 위한 로컬 증거다. raw frame과 intrinsic 수치는 public repository에 넣지 않고, 외부에 공유할 사진은 metadata 제거·민감 영역 점검을 거친 별도 사본만 사용한다.

중요: robot 정지 확인, collision-free waypoint, E-stop, camera timestamp 동기화는 core가 임의로 추측하지 않는다. live adapter와 실험 operator가 명시적으로 보장해야 한다. 이 분리는 solver가 조용히 robot을 움직이거나 특정 연구실 network에 묶이는 것을 막는다.

승인된 Paradex2 pose를 supervised capture trajectory로 연결한다

ParaDex hand-eye의 joint-position sequence는 capture 순서의 출발점으로만 사용했다. BeltBench에는 현재 xArm·board·cable 배치에서 한 개씩 저속 검증한 Paradex2 pose 0–18만 남겼다. hand, board mount, table, cable이 바뀌면 같은 joint angle도 다른 충돌 여유와 visibility를 가지므로, trajectory는 planner가 아니라 현재 workcell에서만 유효한 승인 목록으로 다룬다.

poses = load_joint_poses(Path("calibration/trajectories/paradex2-xarm"))
robot = XArmCalibrationRobot(driver, speed, acceleration, settle, max_delta, approved)
session = capture_session(robot, frames, [pose.joints_rad for pose in poses], intrinsics, board)

위 구현에서 trajectory loader는 여섯 관절값·radian 단위·범위를 먼저 검증한다. adapter는 큰 시작 전이, controller 경고, blocking move, settle interval을 확인하고, core는 유효한 Charuco observation만 session에 넣는다.

따라서 BeltBench에서는 기존 trajectory를 그대로 실행하지 않는다. 먼저 현재 hand+board의 collision envelope와 table·basket·cable을 검토하고, 낮은 속도의 supervised dry run으로 후보 pose를 검증한다. 그 다음 board corner 수, image 내 크기, rotation 다양성, robot 도착 후 안정화 시간까지 통과한 pose만 waypoints로 고정한다. capture_session()의 Robot.move_joints()는 이 “도착과 정지까지 보장하는 blocking adapter”로 구현할 계획이다.

한 pose씩 검증하는 BeltBench 도구

전체 calibration capture를 시작하기 전에, BeltBench에는 Paradex2 calibration pose를 한 번에 하나씩 검토하는 verifier를 추가했다. 기본 mode는 robot에 연결하지 않고 pose 파일의 여섯 관절값·단위·범위를 읽어 목록으로 보여 주는 dry-run이다. 실제 motion mode는 pose index를 두 번 명시하고, workspace-clear를 사람이 확인하고, 큰 관절 전이는 별도로 승인해야만 한 번의 slow blocking move를 보낸다.

이 도구는 “pose가 안전함을 선언하는 자동 판정기”가 아니다. 대신 각 pose를 독립적으로 geometry → low-speed motion → camera visibility → settle → evidence 순서로 검토하게 만들어, 문제가 생기면 전체 trajectory를 실행하지 않고 해당 pose에서 멈출 수 있게 한다. 검토를 통과한 pose만 자동 capture waypoint로 사용한다.

현재 workcell에서의 pose 검증

현재 checkerboard mount와 cable 배치에서 paradex2-xarm의 pose 0–18을 low-speed blocking move로 순차 검증했다. 모든 pose가 안전하게 도달했으며, 아래는 현장에서 남긴 19장의 전체 자세 증거를 metadata와 주변 인물을 제거해 정리한 것이다. 번호는 현장 검증 사진의 순서를 나타내며, solver input의 pose index와 일대일로 대응하는 기록은 local capture session에만 남긴다.

이 검증은 현재 mount에서의 motion safety를 확인한 것이다. integrated calibration capture에서는 각 pose마다 Charuco corner 수·timestamp·solver residual도 함께 기록해, motion-safe pose와 calibration-quality pose를 구분한다.

현장 통합 calibration 실행 결과

확정한 Paradex2 19개 pose를 low-speed blocking move로 실행하고, 선택한 16개 camera에서 pose마다 frame을 수집했다. 총 304장(19×16)의 원본 evidence는 private local storage에 보존했다. public devlog에는 그중 Charuco corner 검출에 성공한 여섯 장 전체를 metadata를 제거하고 필요한 workcell 영역으로 crop해 싣는다.

First-pass 결과: 한 fixed camera가 4개의 유효 관측을 확보해 joint extrinsic/hand-eye solve의 최소 조건을 충족했다. translation RMS는 4.56 mm, rotation RMS는 0.184°였다. 이 값은 solver 경로가 실제 장비에서 닫혔다는 증거이지만, 최소 표본 4개 결과이므로 production calibration으로 확정하지 않는다.

Camera A만 네 관측을 확보해 solve됐고, Camera B는 두 관측이라 보류됐다. 다른 camera가 “고장”이라는 뜻은 아니다. 현재 board 위치·방향과 해당 camera의 fixed field of view가 겹치지 않았다는 뜻이다. serial, transform 행렬, raw frame, workcell 주소는 private local result에만 남긴다.

camera를 옮기지 않고 다음에 할 일

  1. pose 06–09 주변을 촘촘히 확장한다. board가 보인 네 pose 주변에서 작은 joint perturbation을 만든다. 각 후보는 기존 verifier로 한 개씩 안전·visibility를 확인한 뒤에만 batch에 넣는다.
  2. camera별 목표를 분리한다. A에는 8–12개 이상, B에는 최소 6개 이상의 유효 관측을 목표로 한다. 같은 위치만 반복하지 말고 board의 image 위치와 기울기가 달라지도록 선택한다.
  3. orientation diversity를 의도적으로 만든다. translation만 달라지고 board가 거의 같은 각도라면 RMS가 작아도 hand-eye 해가 불안정할 수 있다. corner가 화면의 여러 영역을 지나고 board normal이 여러 방향을 보게 한다.
  4. freshness gate를 유지한다. preview가 멈춘 frame은 새 robot pose와 절대 짝지으면 안 된다. 다음 session도 매 pose의 frame age 확인과 raw evidence 보존을 유지한다.

yaw-only visibility scan

board가 아래로 내려가거나 roll/pitch가 바뀌는 위험을 피하기 위해, pose 06–09에서 Cartesian x/y/z·roll·pitch를 고정하고 world-z yaw만 −15°, −5°, 0°, +5°, +15°로 바꿨다. 매 move 뒤 tool position이 2 mm 이내에 유지되는지 확인했고, 각 pose는 yaw 0°로 되돌린 뒤 다음 pose로 넘어갔다. 20개 후보 중 17개에서 유효 corner가 검출됐다.

reference = driver.read_cartesian_pose()
driver.move_yaw_blocking(reference, radians(yaw_deg), speed, acceleration, tolerance_mm)
images = fresh_viewer.read(camera_ids)
detections = {cam: detect(image, intrinsics[cam], board) for cam, image in images.items()}

move_yaw_blocking()은 reference의 x/y/z·roll·pitch를 그대로 controller에 보내고 yaw만 바꾼다. move 뒤 position tolerance를 넘으면 다음 frame을 저장하지 않고 오류로 중단한다.

이 scan으로 Camera B는 2개에서 8개의 유효 관측으로 늘어 first-pass solve가 가능해졌다. 반면 Camera A는 17개 관측에도 translation RMS가 10.42 mm로, 초기 4-pose 결과보다 커졌다. yaw 변화만으로는 hand-eye에 필요한 독립적인 3D 운동을 충분히 만들지 못하기 때문이다. 따라서 yaw 후보는 visibility를 확보하는 안전한 추가 pose로 채택하되, final calibration에는 서로 다른 기존 safe pose와 함께 사용하고 RMS·reprojection 품질을 다시 검토한다.

stale preview를 결과에 섞지 않은 이유

첫 실행에서는 viewer cache가 오래된 JPEG를 반환한다는 점이 드러났다. 이는 새 robot pose에 과거 image를 연결하는 심각한 오류다. runner는 이후 viewer의 frame-age metadata를 매 pose마다 확인하도록 보강됐다. stale frame은 session에 넣지 않고 즉시 중단하므로, 위 결과는 fresh preview가 확인된 뒤 다시 수집한 session에서만 계산했다.

3. geometry.py: transform을 안전하게 다룬다

transform()은 4×4 모양, 마지막 행, rotation matrix의 직교성을 검사한다. inverse()는 일반적인 matrix inverse 대신 rigid transform의 성질 R⁻¹ = Rᵀ를 이용한다. pose_error()는 두 pose의 translation 차이와 rotation-vector 차이를 각각 metre와 radian으로 반환한다.

이 검증이 없으면 image pose의 축 순서가 바뀌거나 잘못된 행렬이 들어와도 solver가 숫자를 내놓을 수 있다. calibration에서는 “결과가 있음”보다 “입력 convention이 맞음”이 먼저다.

4. handeye.py: 여러 자세를 하나의 고정 관계로 압축한다

두 pose i, j를 빼면 고정 camera와 고정 board mount 항이 사라져 상대 운동 관계 A X = X B가 된다. 구현은 모든 pose 쌍을 만들어 information을 늘린 뒤, 여섯 변수(회전 vector 3 + 이동 3)로 표현한 X를 찾는다.

for first in range(n - 1):
    for second in range(first + 1, n):
        A.append(inverse(base_to_tool[second]) @ base_to_tool[first])
        B.append(inverse(camera_to_board[second]) @ camera_to_board[first])
tool_to_board = solve_ax_xb(A, B)

solve_ax_xb()는 SciPy least_squares를 사용한다. 각 candidate X에 대해 A·X와 X·B가 얼마나 다른지를 rotation vector와 translation residual로 쌓는다. soft_l1 loss는 일부 image observation이 나빠도 한 장의 이상치가 전체 해를 과도하게 끌어가지 않도록 한다.

X를 얻으면 각 absolute pose가 base_to_camera 후보 하나를 만든다. 여러 후보의 translation 평균과 SVD 기반 rotation 평균을 취하고, 마지막으로 각 후보와 평균 사이의 translation·rotation RMS를 report한다.

candidate = robot_pose @ tool_to_board @ inverse(board_pose)
base_to_camera = average_transforms(candidates)
translation_rms, rotation_rms = residuals(base_to_camera, candidates)

5. session.py와 CLI: 재현 가능한 입출력

solve_session()은 portable JSON의 sample을 camera별로 모아, 네 장 이상 유효 observation이 있는 camera만 푼다. scripts/calibrate.py는 결과 transform, sample 수, RMS를 새 JSON으로 쓰고 console에도 요약한다. raw image나 network 설정은 session format에 포함하지 않는다.

python3 scripts/calibrate.py session.json --output calibration.json
# camera: samples=... translation_rms_mm=... rotation_rms_deg=...

실제 자동화 전의 gate

  1. camera live stream을 다시 확인하고 selected intrinsic을 board reprojection으로 검증한다.
  2. Charuco board를 tool에 강하게 고정하고, board가 여러 camera에서 충분히 크게 보이는 waypoint를 승인한다.
  3. xArm adapter가 move_joints 뒤 실제 정지와 base_to_tool timestamp를 보장하게 한다.
  4. camera adapter가 같은 순간의 frame 또는 허용 가능한 timestamp 차이를 기록하게 한다.
  5. RMS, corner 수, pose 다양성 기준을 통과한 camera만 M0 observation에 채택한다.

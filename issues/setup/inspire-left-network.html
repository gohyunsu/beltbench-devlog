ISSUE-004 · hand interface · 2026-07-29 · 해결

Inspire left hand의 제어 경로는 Ethernet이 아니라 USB–RS485였다.

초기 진단은 hand를 네트워크 장치로 가정해 link·route·TCP를 살폈다. 그러나 실제 연결은 USB–RS485 adapter를 통한 RH56 직렬 프로토콜이었다. 통신 계층을 바로잡은 뒤, hand를 움직이지 않는 actual angle 읽기로 여섯 관절의 응답을 검증했다.

검증 결과: adapter 열거, 직렬 포트 개방, RH56 상태 요청, 응답 헤더와 checksum 검증, 여섯 관절 값 복호화까지 성공했다. 이 검증에는 목표 자세를 쓰거나 hand를 움직이는 명령을 사용하지 않았다.

무엇이 잘못된 가정이었나

케이블의 physical link나 IP 응답은 Ethernet 경로가 살아 있는지를 보여 줄 뿐이다. 이번 hand의 실제 controller interface는 RS485였다. RS485는 두 선을 이용해 장치 사이에 직렬 데이터를 주고받는 산업용 통신 방식이다. USB adapter가 PC에서는 일반적인 serial device처럼 보이고, 그 위에서 RH56의 자체 frame 형식이 동작한다.

따라서 TCP port나 Modbus TCP service를 찾는 것은 이 구성의 병목을 해결하지 못한다. 이전의 timeout은 hand 고장이 아니라 잘못 선택한 transport를 검사한 결과였다. 연결 방식은 현장 adapter와 vendor protocol로 확인하고, 읽기 요청부터 최소 단위로 검증해야 한다.

USB–RS485 adapter

PC의 USB 데이터를 RS485 전기 신호로 바꾼다. adapter 자체는 hand를 제어하지 않으며, 바이트를 정확히 전달하는 통로다.

baud rate · 8-N-1

직렬 통신의 속도와 한 글자(frame bit)의 형식을 정하는 약속이다. 양쪽이 같은 설정을 써야 문자가 깨지지 않는다.

RH56 frame

시작 바이트, hand ID, 길이, 명령, register 주소, payload, checksum으로 이루어진 요청·응답 묶음이다. 길이와 checksum이 맞아야 받은 데이터가 온전하다고 판단한다.

register

controller 내부의 번호 붙은 값 저장소다. actual angle은 현재 손가락 관절 상태를 읽는 register이고, target angle은 움직임을 요청하는 별도 register다.

안전하게 검증한 순서

  1. OS가 USB–RS485 adapter를 인식하는지 확인했다.
  2. vendor manual의 직렬 설정으로 port를 열고, 입력 buffer를 비웠다.
  3. ANGLE_ACT register에 한 번의 read frame을 보냈다. 이 frame은 현재 상태만 요청하며 motion을 유발하지 않는다.
  4. 반환된 frame의 시작 바이트, hand ID, 명령, register 주소, checksum을 모두 확인했다.
  5. 12-byte payload를 little-endian signed integer 여섯 개로 해석해 관절 상태를 얻었다.

이 순서는 제어 전에 통신을 좁게 검증하는 방법이다. 응답이 온다와 안전하게 움직일 수 있다는 별개의 주장이다. motion은 workspace, xArm 상태, 사람이 확인한 목표 자세가 갖춰진 별도 단계에서만 실행한다.

손가락은 어떤 원리로 움직이나

상위 프로그램은 “잡아라”라는 모호한 명령을 바로 보내지 않는다. 먼저 grasp planner가 물체의 크기·방향·접근 자세를 보고 여섯 관절의 target angle을 만든다. 이 값은 hand controller의 target register에 쓰인다. controller는 각 손가락 내부 motor와 encoder를 이용해 실제 관절 angle을 계속 읽고, 목표 angle에 가까워지도록 servo loop를 수행한다.

단계입력출력안전 확인

따라서 status read는 단순한 “연결 시험” 이상이다. command 전후 actual angle을 남기면 hand가 명령을 받았는지, 물체에 닿아 닫힘이 멈췄는지, 혹은 통신 자체가 실패했는지를 구분하는 근거가 된다. force·error 같은 추가 상태는 다음 안전 단계에서 명시적으로 읽어야 하며, angle만으로 grasp 성공을 확정하지는 않는다.

BeltBench에 남긴 최소 구현

private BeltBench에는 InspireSerialHand라는 작은 hardware adapter를 추가했다. Python 표준 library만 사용해 외부 serial package에 의존하지 않고, import나 객체 생성만으로는 port를 열거나 명령을 보내지 않는다. 현재 CLI가 제공하는 것은 status 하나이며 read-only다.

driver는 요청 frame을 만들고 응답의 구조와 checksum을 확인한 뒤 상태만 반환한다. 쓰기 API는 향후 명시적이고 검토 가능한 action으로 제한할 수 있도록 분리했지만, benchmark 실행 경로에는 자동 motion이나 background loop를 넣지 않았다. 장치 경로·식별자·실측 관절 값은 local configuration과 trial evidence에만 두며 공개 기록에는 남기지 않는다.

다음 단계

  1. 상태 read를 trial 시작 전 health check로 연결한다.
  2. open/close 같은 단일 action은 사람이 승인한 안전 자세와 workspace 확인을 통과할 때만 추가한다.
  3. xArm motion, camera timestamp, hand state를 같은 evidence record에 묶는다.
  4. 그 뒤에만 정지 테이블탑 pick-place 평가의 grasp·place 성공 기준에 hand action을 포함한다.

관련 이슈

ISSUE-001은 xArm의 Ethernet 연결을 계층별로 진단한 사례다. 이번에는 같은 원칙—physical link, transport, protocol, application을 분리—을 적용해 interface 자체가 다르다는 점을 확인했다. ISSUE-005의 workcell calibration과 함께 완성되면, hand 상태도 camera·xArm 관측과 같은 trial 맥락에서 기록할 수 있다. 전체 closed-loop 제어 관점은 CONCEPT-001에서 한 장으로 설명한다.

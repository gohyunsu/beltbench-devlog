ISSUE-056 · 2026-08-11 · cuRobo resident collision gate

첫 inference demo는 resident path와 cuRobo GPU collision gate로 닫는다.

교수님의 practical real-time grasp demo 우선 지시와 사수님의 “왜 충돌 감지에 cuRobo를 사용하지 않는가”라는 질문을 기준으로 전체 방향을 다시 감사했다. 결론은 cuRobo를 단순 후보가 아니라 online collision hot path로 채택하되, 첫 데모에서 full online planning까지 한꺼번에 요구하지 않는 것이다. Source commit e2e0da4는 resident command 전용 collision workload와 후속 warm-start workload를 분리하고, 서버 capability probe와 fail-closed benchmark 조건을 명시했다.

2026-08-12 정정: 이 기록의 driver 580.65.06 원천 차단 결론은 CUDA 13 하한을 cuRobo V2 전체 하한으로 잘못 적용한 것이다. v0.8.0은 CUDA 12 extra를 제공하며 CUDA 12.x Linux minor-compatibility 하한은 525.60.13이다. Driver 535 host는 실제 kernel qualification 대상이다. 상세 원인과 수정은 ISSUE-058에 기록했다.
결론: 첫 데모는 offline 검증된 grasp와 resident path family를 재사용한다. 매 최신 observation마다 고정 크기 cuRobo gate가 self/static-world와 phase-specific moving-object collision을 검사한다. 범위를 벗어나거나 GPU 결과가 늦거나 없으면 command를 내지 않는다. HPP-FCL CPU planning fallback은 없으며, cuRobo arm-prefix warm start는 이 경로가 실제 p99를 통과한 다음 단계다.

질문의 타당성

사수님의 질문은 타당하다. Robot state와 수십 개 candidate 또는 trajectory sample을 동시에 검사하는 collision workload는 GPU 병렬화 효과가 크고, cuRobo는 batched FK, robot sphere collision, resident world와 CUDA graph를 제공한다. BeltBench가 목표로 하는 bounded candidate batch와 잘 맞는다. 따라서 실제 online collision을 Python loop의 Pinocchio/HPP-FCL로 수행하는 방향은 폐기해야 한다.

다만 “모든 module을 GPU화”는 실시간성의 동의어가 아니다. Timestamp join, generation ordering, deadline, cancel, lease ownership과 controller acknowledgement는 작은 branch-heavy I/O state machine이다. 이를 GPU kernel로 옮기면 host synchronization을 더 만들 뿐이다. 최적화 대상은 GPU module 수가 아니라 sensor-to-command p99와 host-device synchronization 횟수다.

기존 상태에서 확인한 문제

  1. 실제 cuRobo 결과 부재: Contract, fixed-shape input, collision lifecycle과 validation lease는 있었지만 actual cuRobo V2 kernel이 만든 source-closed output은 없었다.
  2. 서버 환경 차단: junjinyong A6000 allocation은 driver 535.161.07이다. 선택한 cuRobo V2 0.8.0의 공식 최소 driver 580.65.06보다 낮다.
  3. 두 workload의 혼합: 기존 full runtime policy는 IK, collision, trajectory optimization, dynamics와 reduction을 모두 요구했다. 이미 검증된 resident command를 최신 scene에서 다시 거르는 첫 데모 workload에도 이를 그대로 적용하면, 아직 하지 않은 planning operation까지 수행했다고 기록할 위험이 있었다.
  4. Stock API 불일치: cuRobo의 high-level grasp planner는 BeltBench의 arm-prefix write mask, immutable hand/suffix, waypoint별 translating object pose와 named contact mask를 그대로 제공하지 않는다. Custom rollout/cost adapter가 필요하다.
  5. 충돌 표현 권한 부족: cuRobo sphere model은 exact mesh가 아니다. xArm, Inspire hand, connector와 workcell의 동일 state corpus에서 HPP-FCL 대비 false negative 0을 입증하기 전에는 online authority가 될 수 없다.

선택한 단계적 구조

단계온라인 동작실패 동작
1. 첫 inference demoResident atlas/path 조회, fixed-shape cuRobo FK와 segmented collision, GPU hard mask/reductionUnsupported, late, collision, tube violation이면 no command
2. Bounded warm startMeasured arm state에서 certified latch까지 cuRobo arm-prefix IK/trajopt/dynamics 후 immutable suffix 결합Deadline 전에 완전 검증되지 않으면 no command
3. Hardware executionCPU freshness/safety gate와 future-start controller handoff, measured feedback/abortStale generation, ack timeout, tracking violation이면 cancel/stop

이 순서는 “항상 full replan”보다 빠르고, “offline path이므로 collision을 생략”하는 방식보다 설명 가능하다. Resident path certificate가 continuous path tube와 dynamics를 담당하고, online cuRobo sampled gate는 최신 robot/object/workcell state의 추가 guard를 담당한다. 둘 중 하나도 다른 하나의 증거를 대체하지 않는다.

첫 collision gate의 정확한 범위

  • dynamic_world: path start부터 attachment까지 constant-yaw translation object pose를 waypoint별로 검사한다.
  • attached_spheres: attachment부터 detachment까지 object를 hand attachment frame의 checksummed sphere set으로 검사한다.
  • conservative_release_envelope: drop 이후 return path를 bin 내부로 끝나는 보수적 swept volume과 검사한다.
  • Robot self/static-world collision, invalid candidate mask와 maximin survivor reduction을 같은 GPU worker에 둔다.
  • Host에는 winner 하나 또는 no-result와 축약 metric만 전달하고 deadline 안에서 JSON을 쓰지 않는다.

첫 policy는 의도적으로 batched IK, trajectory optimization, dynamics constraints와 continuous collision을 요구하지 않는다. 이들은 resident certificate 또는 후속 full warm-start policy의 책임이다. Sampled gate 결과를 continuous swept collision로 표기하는 것은 금지한다.

GPU residentCPU deterministic비동기 검증

Track filter와 constant-translation prediction은 arithmetic이 작으므로 우선 producer 가까이에 둔다. Perception output이 이미 GPU에 있고 profile에서 이득이 확인되면 fusion할 수 있지만, 별도 GPU round trip을 만들기 위해 옮기지는 않는다.

이번 구현

  1. curobo-v2-resident-collision-gate-policy.example.json을 추가했다. 64 이하 fixed batch, 10 ms draft deadline, 1 host-device round trip, 0 synchronous write, 1,000 post-warmup trial과 zero miss를 요구한다.
  2. Gate operation은 FK, self/world collision, dynamic target/contact, attachment, release envelope, GPU reduction, CUDA graph/stream으로 제한했다. IK/trajopt/continuous collision은 명시적으로 제외했다.
  3. 기존 curobo-v2-runtime-policy는 후속 full warm-start workload로 유지했다. CPU fallback은 두 policy 모두 reject다.
  4. PBS capability probe가 driver뿐 아니라 compute capability와 Python major/minor를 판정하고, 모두 통과할 때만 environment_compatible를 출력하게 했다.
  5. Architecture 문서의 첫 demo cycle을 “resident candidate마다 cuRobo gate 필수, no warm-start fallback”으로 수정했다.

발생한 문제, 원인, 해결

  1. 기본 Python test import 실패: 활성 base Python 3.13에 numpy가 없어 unittest import가 실패했다. 코드 문제와 환경 문제를 구분하고 기존 beltbench-planning conda 환경에서 재실행했다.
  2. Probe 상태명 과장: 처음에는 driver만 통과해도 install_probe_permitted라고 썼다. GPU architecture와 Python 조건을 검사하지 않은 상태에서 너무 강한 표현이었다. 세 조건을 각각 기록하고 전부 통과할 때만 environment_compatible로 바꿨다.
  3. Continuous collision 혼동: Resident gate policy에 continuous collision을 넣으면 sampled state gate가 swept proof처럼 보인다. 해당 operation을 제외하고 startup resident certificate의 별도 책임으로 문서와 테스트에 고정했다.
  4. 무차별 GPU화 위험: 모든 작은 state machine까지 GPU로 옮기라는 해석을 배제했다. GPU boundary는 numerical batch, CPU boundary는 causal I/O로 유지하고 end-to-end p99로 판단하도록 했다.

아직 주장할 수 없는 것

  1. 10 ms는 목표 policy이며 target GPU 측정값이 아니다.
  2. Actual cuRobo V2 collision pass, CUDA graph replay, parity와 p99 evidence는 없다.
  3. Connector-inclusive watertight collision envelope와 measured seating transform이 완료되지 않았다.
  4. Stock cuRobo API만으로 time-indexed moving target/contact semantics가 충족된다고 볼 수 없다. BeltBench adapter kernel이 필요하다.
  5. MuJoCo measured rollout은 physics diagnostic이며 cuRobo online collision authority를 대체하지 않는다.

  3. Exact xArm6, Inspire Left, connector sphere/ignore config를 생성하고 1,445-state HPP-FCL corpus에서 false negative 0 parity를 측정한다.

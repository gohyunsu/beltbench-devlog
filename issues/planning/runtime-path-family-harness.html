ISSUE-022 · 2026-08-10 · selection-to-controller boundary

검증된 grasp와 path-family를 최신 관측에서 실제 시간 순서로 선택한다.

문서와 개별 계약만 연결해 놓고 real-time pipeline이라고 부르지 않는다. 실제 projector, coordinator, bounded warm-start 경계, capacity-one scheduler와 causal recorder를 한 실행 경로로 묶고, 선택되거나 거부된 결과를 발생 시간 그대로 Viser가 재생할 수 있는 첫 production-shaped vertical slice를 구현했다.

현재 효력: 3e3de99이 runtime engine과 causal session, 697250e가 bounded multi-rate input-to-selection, 66f1061이 exact future-start whole-trajectory handoff를 구현한다. Receipt는 diagnostic evidence일 뿐이며 모든 trajectory는 계속 execution_blocked, execution_authorized=false다.

Grasp 선택 기준을 다시 연결한 결론

AutoDex source 감사 결과는 바뀌지 않았다. BODex residual과 provider 순서, zero-margin sampled sphere collision, squeeze overlap, 한 방향 gravity hold, scene set cover, coverage 순서의 첫 planning 성공은 proposal 생성과 static diagnostic에는 유용하지만 moving conveyor command의 승인 기준은 아니다.

모든 hard gate 뒤 후보 비교는 complete normalized-slack vector의 lexicographic maximin이다. 현재 active family가 유효하면 유지하고, switch는 certified latch와 hysteresis 개선을 모두 요구한다. Cutoff 뒤에는 grasp와 topology를 바꾸지 않으며 bounded correction을 벗어나면 stop을 권고한다.

실제로 연결한 실행 경로

  1. RuntimePlanningObservation이 같은 generation의 fused planar track, conveyor motion, stable pose, calibration, tracking policy, named robot motion snapshot과 commit deadline을 묶는다.
  2. PathFamilyRuntimeEngine이 실제 ResidentPathFamilyProjector를 호출하고 그 exact batch로 PathFamilyRuntimeCoordinator를 호출한다. 다른 bundle에 결합된 projector는 시작 시 거부한다.
  3. Retain·correct·latch·switch만 exact compiled path digest를 노출한다. stop_active는 stop 대상 identity가 있어도 reusable candidate를 노출하지 않는다.
  4. Warm start가 필요하면 한 번만 admission한다. Backend가 없거나 실패하면 artifact 없이 거부하고, 성공 결과도 exact trajectory·stop-path digest의 독립 validation을 통과해야 한다.
  5. LatestGenerationRuntimeHarness의 mailbox는 capacity one이다. 더 최신 observation은 pending과 in-flight generation을 supersede하고, 늦게 끝난 stale result를 recorder나 selection으로 되돌리지 않는다.
  6. RuntimePlanningSessionRecorder는 measured interval 동안 bounded object reference와 tracepoint만 메모리에 둔다. JSON, SHA-256과 filesystem write는 종료 뒤 수행한다.
  7. 모든 generation이 selected, rejected, superseded 또는 failed terminal을 가진 뒤에만 전체 session과 causal assessment를 만들고 staging tree를 atomic rename한다.

Scheduler와 evidence 불변식

  • 새 observation과 그것이 supersede하는 generation은 하나의 preflighted transaction이다. Event capacity가 부족하면 recorder와 mailbox 모두 바뀌지 않는다.
  • Harness 시작 시 8 × maximum_generation_count + 1 event를 담을 수 있어야 한다. 이전 generation이 complete trajectory rejection으로 끝나고 마지막 generation이 diagnostic selection되는 최악 경로를 예약한다.
  • Blocking Python backend를 강제 중단할 수 있다고 주장하지 않는다. Production solver는 cancellation latency를 측정한 nonblocking process/worker 뒤에 있어야 하며 late return은 폐기한다.
  • Observation artifact는 camera ID와 fused-track source를 기록하지만 raw sensor payload를 포함했다고 주장하지 않는다.
  • Viser playback은 arm, end effector, object, stable pose와 workcell이 runtime request와 모두 같아야 한다. Startup hash를 종료 시 다시 검사하며 중간 변조 시 session directory를 만들지 않는다.
  • 거부만 발생한 session도 fake playback 없이 보존한다. Playback이 있어도 planned_only이며 measured robot/object feedback으로 표시하지 않는다.

2026-08-10: multi-rate 입력에서 selection까지 조합

기존 engine과 capacity-one harness는 한 번 받은 RuntimePlanningObservation을 올바르게 처리했지만, 그 observation을 누가 어떤 encoder·robot snapshot으로 만드는지는 caller에게 열려 있었다. 실제 시스템에서는 camera fusion, encoder와 robot state가 서로 다른 rate로 도착하므로 이 경계를 수동 조립으로 남기면 최신 encoder를 잘못 붙이거나 clock과 deadline을 중복 정의하기 쉽다.

구현한 경계

  1. RuntimePlanningRunner가 independent conveyor-state publisher, latest synchronized robot-state publisher와 fused-track submission을 조합한다. Perception 자체는 구현하지 않고 typed fused-track adapter output만 소비한다.
  2. Track의 exact conveyor_state_id가 configured bounded history에 있을 때만 observation을 만든다. 더 최신 state가 있어도 대체하지 않으며 evicted/missing state는 hard error다.
  3. Robot state가 없으면 generation을 소비하지 않는다. Identity는 immutable이고 timestamp는 strictly increasing이며 zero derivative를 합성하지 않는다. 실제 freshness는 deployment policy가 query 시점에 다시 gate한다.
  4. PathFamilyRuntimeEngine이 finite 값을 강제하는 한 runtime clock을 소유하고 runner, harness와 coordinator가 같은 callable을 사용한다. Commit deadline은 recorder의 exact causality policy에서만 파생한다.
  5. Input-history policy를 첫 observation의 typed configured artifact로 기록한다. Materialization staging에서 모든 source digest, policy identity/ancestry와 causal assessment를 다시 검증한 뒤에만 atomic rename한다.
  6. Runner는 selection에서 끝난다. Blocking controller callback을 삽입하지 않았고 기존 pure-delay feedback generator를 live loop로 연결했다고 주장하지 않는다.

검증과 한계

  • Local focused runtime/session suite는 50개, 전체 planning suite는 493개, calibration suite는 9개가 통과했다.
  • junjinyong pinned planning environment에서 focused 50개와 전체 planning 493개가 각각 2.061초, 58.088초에 통과했다. 이는 CPU functional regression이며 p95 latency나 hard-real-time evidence가 아니다.
  • Local, GitHub main과 server source는 697250e로 일치한다. Server worktree에는 사전에 있던 BODex native output 3개만 untracked로 남았다.
  • Session의 conveyor_state_published는 raw encoder callback 시간이 아니라 exact snapshot을 planning generation에 넘긴 시간이다. Sensor/fusion/controller end-to-end latency에는 별도 bounded native trace가 필요하다.
  • 이 시점의 수직 슬라이스는 typed event request 선택에서 끝났다. 아래 갱신에서 controller-rate sampler 계획은 폐기하고 exact whole-trajectory diagnostic handoff와 bounded lifecycle fault injection을 구현했다.

2026-08-10: 선택 결과를 controller 경계까지 전달

처음 계획은 선택된 trajectory를 Python에서 controller rate로 sampling해 setpoint stream을 만드는 것이었다. 그러나 ROS 2 real-time proposal, ros2_control Controller Manager와 joint trajectory 표현·교체 의미를 다시 검토하면 이 구조는 planning process에 불필요한 jitter, scheduling과 interpolation 책임을 중복시킨다. 이미 event request가 arm과 end effector의 position·velocity·acceleration을 한 time axis에 담고 있으므로, planning은 그 exact whole trajectory를 한 번 넘기고 controller backend가 deterministic interpolation과 periodic loop를 소유하는 편이 더 작고 검증 가능하다.

구현한 controller handoff

  1. Path start 전 projection에서 요청 phase가 없으면 임의 mid-path가 아니라 path time 0의 certified latch만 평가한다. 현재 robot state가 그 latch와 request 첫 waypoint에 joint 이름·position·velocity·acceleration까지 exact 일치해야 하며 arm과 hand derivative는 모두 zero여야 한다.
  2. ControllerTrajectoryAdapterCapability은 future start, pre-start hold, exact arm/end-effector joints, position/velocity/acceleration, synchronized arm-hand, cancel, prevalidated stop, lead time과 bounded waypoint/duration을 선언한다. 두 독립 topic을 비슷한 시각에 publish하는 것은 atomicity로 인정하지 않는다.
  3. RuntimeSelectionControlCoordinator는 planner와 mailbox가 같은 clock callable을 사용할 때만 구성된다. 새 latch_precompiled만 publish하고, retain_active는 controller가 이미 소유한 trajectory를 재전송하지 않는다. Warm start와 switch_latch는 각각 event materialization과 replacement/splice protocol이 없어 명시적으로 차단한다.
  4. Mailbox는 capacity one이며 file I/O, serialization, ROS/backend callback을 lock 안에서 수행하지 않는다. Worker take와 adapter ack budget을 future-start lead time에서 함께 예약하고 deadline miss는 retry 없이 terminal expiry로 닫는다.
  5. Snapshot은 exact request·activation·correction·initial robot state와 lifecycle timestamp를 causal runtime session에 다시 결속한다. Viser는 실제 발생 시각과 terminal-to-start lead를 표시하지만 adapter acceptance를 execution authority로 표현하지 않는다.
  6. Normal acceptance, worker-take timeout, adapter-ack timeout과 explicit rejection은 sleep 없는 virtual clock으로 같은 mailbox 구현을 통과한다. 이는 lifecycle plumbing만 검증하며 perception·tracking·controller response·stop fault를 대체하지 않는다.

검증 결과와 남은 한계

  • Local은 새 handoff 16개, OpenCV 없는 planning 경로 509개, calibration 환경 14개가 통과했다. 전체 Python compile과 Viser CLI import도 통과했다.
  • junjinyong pinned planning 환경에서 handoff 16개는 2.013초, 전체 planning 509개는 최종 56.323초에 통과했다.
  • Local, GitHub main과 server는 66f1061로 일치한다. Server에는 기존 BODex native output 3개만 untracked로 남았다.
  • Concrete ROS 2/ros2_control adapter, combined arm-hand endpoint 또는 two-phase prepare/commit, measured controller feedback, cancellation/stop latency와 native p95/p99 trace는 아직 없다.
  • Warm-start 결과의 typed event request materialization과 active trajectory replacement/splice도 아직 없다. Diagnostic receipt는 어떤 경우에도 hardware execution을 승인하지 않는다.

남은 신뢰 경계와 다음 순서

ResidentPathFamilyProjector 생성자는 bundle과 atlas의 구조적 상속을 검사하고 engine은 exact bundle 결합을 검사한다. 그러나 이것만으로 source file을 다시 hash하지 않는다. Production bootstrap은 timing 시작 전에 verify_path_family_deployment_bundle_sources()로 atlas, compiler/policy, reusable/tracking/stop path, latch certificate와 validation report를 모두 재검증해야 한다. 이번 synthetic fixture는 그 production source evidence가 아니다.

  1. 실제 checksummed atlas에서 complete reusable path와 stop path를 만드는 production path compiler를 구현한다.
  2. Reference oracle과 비교 가능한 accelerated warm-start solver와 별도 continuous validator를 nonblocking worker로 연결한다.
  3. Recorded camera·encoder·controller snapshot을 원래 cadence로 replay해 p50/p95/p99, worst case, miss, supersession, cancellation과 memory high-water를 측정한다.
  4. ROS 2 경계에는 Python JSON recorder 대신 LTTng/ros2_tracing 또는 동등한 low-overhead tracepoint adapter를 둔다.
  5. Controller simulation에서 whole-trajectory prepare/commit, measured robot/object, watchdog, stop과 bin containment를 독립 feedback으로 기록한다.
  6. 실제 calibration·connector metrology·hardware reliability lower bound가 준비된 뒤에만 physical commit authority를 추가한다.

AutoDex와 BeltBench grasp authority 감사, bounded warm-start 경계, causal session 계약이 각각 이 runtime의 offline 입력, update 권한과 evidence 의미를 설명한다.

ISSUE-037 · 2026-08-10 · bounded retention selection

AutoDex squeeze 상수를 그대로 쓰지 않고, 통과 가능한 최소 폐쇄 상태를 증거로 선택한다.

AutoDex와 BeltBench의 grasp 탈락 기준을 production batch에서 다시 대조했다. Provider flag와 정적 simulation은 제안 provenance로 제한하고, 실제 배포 hand의 named mesh에서 접촉·관통·clearance·task wrench·retention/release path를 모두 통과하는 최소 command만 checksummed intrinsic evidence로 남긴다.

검토 범위

AutoDex 기준 source는 willi19/autodex-code:main@5ada1c077f60bae9af6f27b07619218f58422e50이다. BODex 생성, run_sim_filter.py, cross-pose order와 runtime planner를 다시 읽었다. BeltBench는 beltbench@fd6c8cc의 intrinsic, deployment, shortlist, atlas, complete-path와 runtime selection 경계를 대조했다.

Production batch에서 관찰한 문제

Pepsi Light upside-down stable pose와 Inspire Left 조합의 proposal 2,000개는 모두 provider_success=false였다. 이는 AutoDex가 독립 filter 전 seed를 모두 저장하는 구현과 일치하므로 provider flag만으로 폐기하지 않았다. 반대로 success로 재해석하지도 않았다. Endpoint screening은 exact identity, named contact, penetration, non-contact/self/support clearance와 signed task-wrench 기준으로 140개만 full evaluation worklist에 남겼다.

첫 full run은 변경된 intrinsic config와 이전 screening artifact의 evaluation_config checksum이 달라 compute 전에 중단됐다. 기존 artifact를 수정하거나 checksum 검사를 우회하지 않고 run을 실패 상태로 보존한 뒤, CPU-only screening부터 새 immutable chain을 만들었다.

고정 retention_gain=2.0을 사용한 full evaluation 결과는 명확했다.

  • 140개 중 failure-free 0개, diagnostic geometry-clear 0개
  • retention_contact_penetration: 140/140
  • retention_task_wrench_margin: 135/140
  • retention_noncontact_object_clearance와 retention_object_clearance: 각각 30/140
  • release_contact_penetration: 140/140
  • 한 예에서는 허용 0.5 mm에 대해 retention 관통이 약 38.7 mm였다.

따라서 원인은 관통 threshold가 지나치게 엄격한 것이 아니라, AutoDex의 hand별 squeeze 상수를 rigid CAD acceptance command로 전역 재사용한 데 있었다. Threshold를 완화하거나 임의의 더 작은 상수로 교체하면 같은 구조적 문제가 남는다.

해결한 선택 정책

Intrinsic config schema를 3.0으로 올리고 단일 retention_gain을 제거했다. 현재 protocol은 [1.0, 1.05, 1.1, 1.15, 1.2, 1.3, 1.4, 1.6, 1.8, 2.0]의 명시적 bounded grid를 오름차순으로 평가한다. 첫 항목은 provider의 first-contact command와 같고, 각 항목은 effective URDF command/mimic limit로 clip된다.

for gain in configured_grid_ascending:
    command = clip(pregrasp + gain * (grasp - pregrasp))
    evidence = evaluate_named_contacts_and_complete_local_paths(command)
    if every_hard_gate_passes(evidence):
        select(command)        # least-closed complete pass
        stop
if no command passed:
    reject("retention_command_not_found")

각 시도는 command, gain, contacts, selected named contacts, signed task-wrench margins, support/self clearance, grasp-to-retention samples, release samples와 command-local failure ledger를 보존한다. 통과 command가 없으면 가장 덜 닫힌 상태를 진단 표시용으로만 남기고 retention_command_not_found로 promotion을 차단한다. 이는 fallback이 아니다.

Full-batch verifier는 시도 gain이 config grid의 정확한 prefix인지 확인한다. Safe command 뒤에 후보를 덧붙이거나, 모두 실패한 grid를 중간에서 잘라낸 artifact는 거부한다. Deployment는 proposal과 config에서 squeeze를 다시 계산하지 않고, checksum 검증을 끝낸 intrinsic evaluation의 exact retention_command만 소비한다.

선택 기준의 권한 순서

  1. Provider output은 identity와 provenance만 제공한다.
  2. Intrinsic 단계가 arm-independent contact, wrench, support와 hand-local complete path를 hard-gate한다.
  3. Deployment가 exact arm·hand·connector·object·workcell에서 IK, joint/singularity, assembly/workcell/object clearance를 검사한다.
  4. Shortlist와 atlas는 통과 후보만 context coverage와 normalized lexicographic maximin으로 정리한다.
  5. Complete path와 runtime은 moving contact, collision, dynamics, deadline, fresh track/encoder/robot state, correction, latch와 stop을 다시 검사한다.
  6. Physical commit에는 force-limited controller profile, connector metrology와 exact-context moving-pick hardware reliability가 추가로 필요하다.

즉 최소 폐쇄 command는 rigid geometry에서 불필요한 overclosure를 피하는 선택일 뿐, 실제 grasp force를 입증하지 않는다. 손의 compliance, actuator current/force limit, 마찰 불확실성과 물체 질량·가속도는 hardware protocol에서 검증해야 한다.

검증과 실패 보존

  • Intrinsic, full batch, deployment, shortlist를 포함한 focused verifier 회귀 52개 통과
  • Grasp screening, reliability, atlas와 shortlist 계층 137개 통과
  • Planning 환경의 전체 discovery에서 기존 OpenCV 의존 모듈 3개만 import 실패했고, calibration 환경에서 해당 14개 회귀를 모두 통과
  • CPU-only PBS fixed-gain full run은 기능적으로 완료됐지만 compute/filesystem clock 차이가 약 -366초여서 timing evidence로는 채택하지 않음
  • Fixed-gain downstream deployment는 geometry-clear worklist가 비어 실패했고, shortlist와 portfolio dependency도 실행 없이 종료됨. 빈 후보를 fallback으로 채우지 않은 정상적인 fail-closed 결과다.

현재 상태와 다음 단계

junjinyong checkout은 checksum을 확인한 incremental Git bundle로 fd6c8cc까지 fast-forward했고 기존 BODex build output은 유지했다. Schema 3.0 config에 결속된 CPU-only screening, full evaluation, deployment, shortlist와 portfolio를 새 append-only ID로 제출했다. 각 downstream job은 afterok dependency로만 시작한다.

첫 schema 3.0 full evaluation은 geometry 판정 전에 gain=1.0을 거부하는 이전 hand joint helper 때문에 실패했다. Config는 first-contact command를 첫 후보로 요구하지만 helper는 extrapolation만 가정해 gain>1을 강제한 계약 불일치였다. c670857에서 1.0을 허용하고 산술 없이 exact contact command를 보존하도록 수정했다. Compute-node 회귀 16개를 통과한 뒤 full evaluation을 새 append-only ID로 재제출했다. 실패한 run과 실행되지 않은 dependency는 삭제하거나 success로 재해석하지 않았다.

그 재제출 115454도 수정 전 endpoint screening이 기록한 end_effector_joint_model checksum과 수정 후 source가 달라 full geometry 전에 중단됐다. 이는 false failure가 아니라 stale evidence 재사용을 막은 정상적인 provenance gate다. 수정 source로 endpoint screening 115458을 다시 실행해 2,000개 전부를 평가했고 같은 140개가 full-path worklist에 남았다. 이 exact artifact만 참조하는 full evaluation 115462를 새 ID로 제출했다.

115462는 exit 0으로 완료돼 140개 record 중 diagnostic geometry-clear 117개를 복구했다. Fixed gain=2.0 run의 0개와 달리 bounded least-closed 선택이 과도한 retention penetration을 피했다는 기능 결과다. Failure-free는 여전히 0개다. Validation protocol이 provisional이고 upside-down stable pose가 measured가 아니므로 모든 record에 context gate가 남으며, 117개를 실행 가능 grasp로 재해석하지 않는다. Compute/filesystem clock skew도 -367초여서 이 run의 timing evidence는 unauthorized다.

새 chain이 geometry-clear 후보를 만들더라도 즉시 실행 가능 grasp로 승격하지 않는다. Exact xArm6/Inspire/connector deployment, full-yaw/horizon support, complete moving pick/drop path와 독립 playback 검증을 모두 다시 생성해야 한다. 현재 stable pose와 validation protocol도 provisional이므로 physical execution은 계속 차단한다.

다음 판정: 새 intrinsic run에서 selected gain 분포와 per-gain failure ledger를 집계한다. 통과 후보가 없으면 grid나 관통 threshold를 임의 조정하지 않고 contact geometry, collision semantics, object mesh와 release capability 가정을 다시 진단한다. 통과 후보가 있으면 exact command를 유지한 채 xArm6 deployment와 complete-path search로 좁힌다.

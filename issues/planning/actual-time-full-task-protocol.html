ISSUE-070 · 2026-08-13 · actual-time full-task protocol

기하 경로 재생을 실제 제한으로 재타이밍한 명령과 단계별 시간 증거로 교체했다.

구형 13.03초 Viser animation은 실제 arm 속도·가속도 제한과 source time mapping을 증명하지 못했다. 이번 단계에서는 움직이는 접촉 prefix의 도함수를 보존하고 lift·transfer·release·return suffix를 정지 경계별로 재타이밍해 26.288853초의 exact q/qd/qdd 명령을 만들었다. Viser는 1.0배속 자동 반복하며 현재 단계, 단계 진행률, event 시각, 전체·현재 프레임 검증을 분리해 보여준다.

현재 판정: 최신 v3는 planned-command actual-time diagnostic이며 measured physics simulation이 아니다. 연속 운동학은 통과하지만 60 FPS HPP-FCL은 release 직전 1/1,590 frame을 거부한다. 따라서 execution은 계속 차단한다.

발생한 문제

문제원인잘못된 처리의 위험
구형 재생 시간이 13.03초였고 명령 도함수가 없었다.308-frame sampled path를 시각화 시간축으로만 재생했다.보기에는 자연스럽지만 robot limit과 controller가 소비할 command를 증명하지 못한다.
전체 dense derivative recovery가 boundary velocity 2.509 rad/s로 실패했다.Moving-contact prefix는 비영속 속도를 갖지만 suffix는 phase별 rest-to-rest geometry였다.전체 경로를 한 spline으로 억지로 평활화하면 contact timing과 source 의미가 변한다.
첫 full-task playback에서 source timing이 어긋났다.26.29초 retimed command를 10.23초 source frame index로 직접 조회했다.로봇과 물체가 서로 다른 시간축을 따라가고도 같은 재생으로 보일 수 있다.
v2 HPP-FCL이 53 frame을 거부했다.Attach 이후 object pose는 source 보간, arm pose는 retimed command를 사용해 rigid attachment가 분리됐다.충돌 임계값을 완화하면 실제 계보 오류를 숨기게 된다.
v3에도 release 1 frame이 남았다.기존 release-contact schedule은 30 FPS dense frame에서 유도돼 60 FPS 중간 시각의 접촉 손실을 놓쳤다.Object state만 일찍 releasing으로 바꾸면 schedule provenance와 물리 의미가 사라진다.

선택한 구현

  1. Contact까지는 source에서 복원한 derivative-aware moving prefix를 그대로 보존했다.
  2. Attach 이후 arm은 phase 시작, 정지 뒤 재운동, terminal을 semantic boundary로 찾아 robot motion limit의 80% utilization에서 rest-to-rest 재타이밍했다.
  3. Source-relative time과 compiled time의 piecewise mapping을 generation evidence에 저장하고 object lifecycle과 phase가 같은 mapping을 사용하게 했다.
  4. Attach부터 detach 직전까지 object pose를 arm FK × connector × inverse(object-from-tool)로 계산했다. Detach 이후에는 그 실제 detach pose에서 source drop 변위만 이어간다.
  5. Grasp SHA, connector transform SHA, robot joint identity와 source path SHA가 모두 맞아야 playback을 생성하도록 fail closed했다.
  6. Viser는 run-level validation을 항상 표시하고 현재 frame validation을 별도로 표시한다. 정상 frame을 보고 전체 성공으로 오해할 수 없게 했다.

검증 결과

  • Continuous quintic kinematics: 모든 arm·hand position/velocity/acceleration/jerk limit 통과
  • 관련 server regression: 29 tests, 모두 통과
  • v2 exact mesh: 53/1,590 invalid frames, attach 52 + release 1
  • v3 FK-bound exact mesh: 1/1,590 invalid frame, release 11.361849초
  • 남은 원인: minimum admissible hand contact 3개 중 2개만 남았지만 retention-end는 10.36 ms 뒤로 선언됨
  • v3 HPP-FCL wall time: 335.25초, command 대비 약 0.078x realtime

HPP-FCL 수치는 online loop에 넣을 수 없음을 직접 보여준다. Exact mesh 검사는 offline false-negative oracle로 유지하고, runtime은 parity와 p99가 검증된 fixed-shape cuRobo batch를 사용해야 한다.

남은 gate

  1. Grasp-specific release schedule을 30 FPS frame 선택이 아니라 고해상도 또는 연속 collision threshold로 다시 산출하고 checksummed source로 결속한다.
  2. 같은 command를 resident full-command output·producer lease·validated lease·lifecycle scenario로 materialize해야 기존 MuJoCo measured backend가 받을 수 있다. 가짜 controller receipt는 만들지 않는다.
  3. MuJoCo에서는 measured q/qd, object SE(3), contact, retention, detach, containment와 end-to-end realtime factor를 기록한다. 성공 animation이 아니라 실패 trace도 그대로 공개한다.
  4. Runtime collision은 cuRobo fixed-shape batch의 dynamic object parity와 p99를 통과한 뒤에만 활성화한다.

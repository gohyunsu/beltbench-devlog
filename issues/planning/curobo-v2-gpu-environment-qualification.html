ISSUE-059 · 2026-08-12 · cuRobo V2 GPU qualification

RTX 3090에서 cuRobo V2 CUDA 12 kernel 경로를 재현하되 실행 권한과 분리한다.

새 GPU host가 cuRobo V2를 구동할 수 있는지 추측으로 판단하지 않고, private project root 아래 exact source와 별도 venv를 만들고 실패를 포함한 immutable run을 남겼다. v0.8.0 tag의 API 결함을 공식 main@8e734f3과 비교한 뒤 후자를 adapter 후보로 선택했다. Actual xArm6·Inspire Left·paired connector model은 먼저 개발 corpus를 통과했지만 독립 holdout에서 false negative가 발견됐다. 이 실패를 보존하고 일반 surface coverage를 보강한 5,882-sphere model을 새 holdout과 resident latency로 다시 검증했다. Moving object, attachment, continuous collision, arm-prefix optimization과 full-command validation은 아직 없어 controller 실행은 계속 차단한다.

2026-08-12 현재 판정: 모델 수정에 사용하지 않은 v2 holdout 생성 상태 1,522개에서 false negative 0, false positive 42/916=4.585%를 확인했다. 이 상태들은 원 개발 corpus와 실패한 v1 holdout 양쪽 모두와 SHA-256 중복 0개다. Batch 8 host p99는 1.449 ms, batch 64 host p99는 8.527 ms였고 각 1,000회에서 10 ms miss는 0회였다. Static self/world collision gate만 통과했으며 output preallocation, CUDA graph, dynamic object와 source-closed full command가 없어 runtime activation은 승인하지 않는다.

작업 checkout, venv와 run은 모두 사용자 전용 private project root 아래에 두었다. 공용 Python과 system package는 수정하지 않았고, private repository 인증 정보를 host에 새로 저장하지 않았다.

Editable shallow checkout 설치는 두 source 모두 distribution version을 nvidia-curobo==0.0.0으로 기록했다. 이 값은 release identity로 신뢰하지 않는다. Runtime contract의 required_backend_version=0.8.0은 API baseline이고, schema 1.7의 full required_source_revision이 실제 code identity를 별도로 강제한다.

재현 절차를 분리한 이유

첫 구현은 venv 설치와 kernel probe를 한 shell script에 묶었다. Probe source를 고칠 때마다 약 5.9 GB venv를 다시 만들게 되어 유지보수와 실패 비교에 불리했다. 이를 다음 두 단계로 분리했다.

  1. setup_curobo_v2_direct.sh는 exact clean checkout을 확인하고 새 venv에 package를 설치한 뒤 commit, nvidia-smi, pip freeze, exit status를 기록한다.
  2. run_curobo_v2_environment_probe.sh는 기존 venv를 변경하지 않고 매번 새 run directory에서 source revision, package consistency와 GPU를 다시 확인하고 probe JSON을 생성한다.

두 script 모두 project root 밖 경로, 기존 output directory, dirty checkout과 source SHA 불일치를 거부한다. 실패 run도 삭제하거나 성공으로 덮어쓰지 않는다.

발생한 문제, 원인과 해결

  1. SSH 공개키 불일치: Host는 응답했지만 현재 작업 shell의 key를 처음에는 거부했다. 비밀번호나 token을 로그에 넣지 않고 공개키를 등록한 뒤 batch authentication만 사용했다.
  2. Private checkout 인증 부재: Host에 GitHub credential이 없어 HTTPS clone이 실패했다. Local에서 exact commit bundle을 생성해 검증한 뒤 전송하고, 원격 checkout은 --ff-only로만 갱신했다.
  3. Warp 최신 버전 비호환: v0.8.0의 warp-lang>=0.10.0가 1.16.0을 선택했고 module 'warp' has no attribute 'torch'로 scene 초기화가 실패했다. cuRobo 공식 changelog는 Warp 1.13의 API 변경을 기록하므로 1.13 직전 최신 patch인 1.12.1을 pin하고 probe가 exact version을 강제하게 했다.
  4. World distance wrapper type 불일치: 공개 문서는 sphere tensor 입력을 설명하지만 내부 cost는 KinematicsState를 요구해 'Tensor' object has no attribute 'robot_spheres'가 발생했다. Environment smoke는 공개 FK가 만든 state를 cost primitive에 직접 전달하고 wrapper 실패를 별도 진단으로 보존했다.
  5. World sphere cache가 0개로 초기화: Robot state에는 65 sphere가 있었지만 world cost buffer는 num_spheres=0이었다. Probe가 실제 kinematics sphere 수로 cost와 constraint buffer를 명시 초기화하고 초기값 0과 적용값 65를 JSON에 남겼다.
  6. Trajectory helper의 2D/3D shape 불일치: v0.8.0의 get_scene_self_collision_distance_from_joint_trajectory와 validate_trajectory는 batched 3D joint tensor를 내부 2D 경로처럼 unpack해 실패했다. Probe는 이 실패를 숨기지 않고 helper별 오류로 기록했고, official 8e734f3에서 같은 입력이 성공하는지 재검증했다.
  7. Cost tensor 형상 불일치: World는 [8,8,65], self collision은 [8,8,1], joint bound는 [8,8,7]을 반환해 wrapper식 직접 덧셈이 실패했다. Smoke는 각 trailing cost 축을 state별로 합산해 zero_cost 진단만 계산하며 이를 collision validation이나 signed clearance로 표기하지 않는다.
  8. Tag를 local patch할 유혹: v0.8.0 결함을 BeltBench probe에서 우회할 수는 있지만 실제 adapter까지 private patch에 의존하면 provenance와 재현성을 잃는다. Upstream 파일은 수정하지 않고 official 8e734f3 checkout을 별도 venv로 설치해 같은 probe를 재실행했다. Sphere cache가 처음부터 65개였고 세 공개 helper가 모두 성공해 이 exact commit을 선택했다.

각 measured call은 FK, world collision cost, self collision cost와 world constraint를 수행한 뒤 torch.cuda.synchronize()까지 포함한다. Runtime policy에 반영한 경계

BeltBench realtime planning policy schema를 1.7로 올리고 full required_source_revision을 필수화했다. Backend family와 API version이 같더라도 capability가 다른 commit을 보고하면 backend_source_revision_disagrees로 거부한다. 이 변경은 전체 745 tests를 통과했으며 source commit fa1591d로 push했다. Official main이 향후 갱신돼도 자동 추종하지 않고, 새 revision은 별도 setup, probe, parity와 latency qualification을 다시 거쳐야 한다.

경로를 제외한 이유는 서로 다른 immutable run directory가 같은 model을 생성했는지 비교하기 위해서다. 반대로 sphere 순서는 GPU 배열 배치와 성능에 영향을 줄 수 있으므로 정렬해 숨기지 않고 원 직렬화 순서를 digest에 포함했다. Strict geometric build quality는 아직 false다. Palm base 최대 uncovered gap은 11.65 mm에서 5.16 mm로 줄었지만 2.5 mm policy를 통과하지 못했고, volume coverage metric도 여러 link에서 남았다. Holdout decision parity 통과를 mesh-envelope 품질 완료로 확대 해석하지 않는다.

아직 주장할 수 없는 것

  1. Moving Pepsi pose update, phase-specific allowed contact, attachment, release envelope와 continuous swept collision을 검사하지 않았다.
  2. CUDA graph replay, preallocated output buffer와 concurrent perception load를 측정하지 않았다.
  3. Static state holdout은 통과했지만 strict surface-envelope build quality, signed cuRobo clearance와 continuous path-tube false-negative 0은 확인하지 않았다.
  4. cuRobo arm-prefix optimizer가 immutable hand/suffix를 보존해 source-closed full command를 생성하지 않았다.
  5. 독립 validator의 nominal·abort 전 구간 lease가 없어 같은 command의 MuJoCo rollout과 measured Viser replay를 아직 실행하지 못했다.

다음 실행 순서

  1. Immutable hand/suffix write mask를 지키는 actual cuRobo arm-prefix producer와 별도 validator를 구현한다.
  2. Time-indexed dynamic world, allowed contact, attached object와 release envelope를 separately warmed fixed-shape pass로 구현한다.
  3. Strict palm-base surface gap을 줄이되 batch 8 latency 예산을 지키는 link-aware sphere pruning/repair를 offline HPP-FCL oracle로 검증한다.
  4. Preallocated output과 CUDA graph를 적용하고 concurrent perception 조건에서 full collision/planning p99를 다시 측정한다.
  5. 같은 validated full command를 MuJoCo와 Viser에 넘겨 contact, retention, release와 bin containment를 비동기 검증한다.

Runtime admission contract, Resident cuRobo 방향, Assembly와 physics 경계를 함께 참고한다.

ISSUE-059 · 2026-08-12 · cuRobo V2 GPU qualification

RTX 3090에서 cuRobo V2 CUDA 12 kernel 경로를 재현하되 실행 권한과 분리한다.

새 Tailscale GPU host가 cuRobo V2를 구동할 수 있는지 추측으로 판단하지 않고, private project root 아래 exact source와 별도 venv를 만들고 실패를 포함한 immutable run을 남겼다. Source commit 0968d4c에서 Franka/table 기준 FK·world collision·self collision·joint-bound CUDA smoke가 통과했다. 그러나 xArm6/Inspire Left/connector, moving object, continuous collision, parity와 deadline은 검사하지 않았으므로 controller 실행은 계속 차단한다.

판정: 이 host는 cuRobo V2 CUDA 12 adapter 개발과 후속 qualification에 사용할 수 있다. 약 0.96 ms smoke 수치를 resident collision gate의 10 ms 달성 증거로 쓰면 안 된다. 실제 assembly와 동일 workload의 1,000회 p99, false-negative parity와 CUDA graph evidence가 별도로 필요하다.

작업 checkout, venv와 run은 모두 사용자 전용 ~/.agile/projects 아래에 두었다. 공용 Python과 system package는 수정하지 않았고, private repository 인증 정보를 host에 새로 저장하지 않았다.

고정한 source와 package

  • BeltBench final probe source: 0968d4c1ec08abc7766811c4464691342ff04a8e
  • cuRobo V2 tag v0.8.0: 4ea77366ca48ee453e7df139e39fa6532af49f3b
  • PyTorch: 2.5.1+cu121, reported CUDA 12.1
  • cuda-core==1.1.1, warp-lang==1.12.1

Editable shallow tag 설치는 distribution version을 nvidia-curobo==0.0.0으로 기록했다. 이 값은 release identity로 신뢰하지 않고 checkout commit을 권위 source로 사용한다. 향후 lock 생성에서는 이 packaging 이상도 제거해야 한다.

재현 절차를 분리한 이유

첫 구현은 venv 설치와 kernel probe를 한 shell script에 묶었다. Probe source를 고칠 때마다 약 5.9 GB venv를 다시 만들게 되어 유지보수와 실패 비교에 불리했다. 이를 다음 두 단계로 분리했다.

  1. setup_curobo_v2_direct.sh는 exact clean checkout을 확인하고 새 venv에 package를 설치한 뒤 commit, nvidia-smi, pip freeze, exit status를 기록한다.
  2. run_curobo_v2_environment_probe.sh는 기존 venv를 변경하지 않고 매번 새 run directory에서 source revision, package consistency와 GPU를 다시 확인하고 probe JSON을 생성한다.

두 script 모두 project root 밖 경로, 기존 output directory, dirty checkout과 source SHA 불일치를 거부한다. 실패 run도 삭제하거나 성공으로 덮어쓰지 않는다.

발생한 문제, 원인과 해결

  1. SSH 공개키 불일치: Host는 응답했지만 현재 작업 shell의 key를 처음에는 거부했다. 비밀번호나 token을 로그에 넣지 않고 공개키를 등록한 뒤 batch authentication만 사용했다.
  2. Private checkout 인증 부재: Host에 GitHub credential이 없어 HTTPS clone이 실패했다. Local에서 exact commit bundle을 생성해 검증한 뒤 전송하고, 원격 checkout은 --ff-only로만 갱신했다.
  3. Warp 최신 버전 비호환: v0.8.0의 warp-lang>=0.10.0가 1.16.0을 선택했고 module 'warp' has no attribute 'torch'로 scene 초기화가 실패했다. cuRobo 공식 changelog는 Warp 1.13의 API 변경을 기록하므로 1.13 직전 최신 patch인 1.12.1을 pin하고 probe가 exact version을 강제하게 했다.
  4. World distance wrapper type 불일치: 공개 문서는 sphere tensor 입력을 설명하지만 내부 cost는 KinematicsState를 요구해 'Tensor' object has no attribute 'robot_spheres'가 발생했다. Environment smoke는 공개 FK가 만든 state를 cost primitive에 직접 전달하고 wrapper 실패를 별도 진단으로 보존했다.
  5. World sphere cache가 0개로 초기화: Robot state에는 65 sphere가 있었지만 world cost buffer는 num_spheres=0이었다. Probe가 실제 kinematics sphere 수로 cost와 constraint buffer를 명시 초기화하고 초기값 0과 적용값 65를 JSON에 남겼다.
  6. Cost tensor 형상 불일치: World는 [8,8,65], self collision은 [8,8,1], joint bound는 [8,8,7]을 반환해 wrapper식 직접 덧셈이 실패했다. Smoke는 각 trailing cost 축을 state별로 합산해 zero_cost 진단만 계산하며 이를 collision validation이나 signed clearance로 표기하지 않는다.

각 measured call은 FK, world collision cost, self collision cost와 world constraint를 수행한 뒤 torch.cuda.synchronize()까지 포함한다. Joint-bound와 깨진 API 진단은 timing loop 밖이다. Trial 수가 20개뿐이고 Franka 정지 pose와 static table만 사용했으므로 real-time benchmark로 승격하지 않는다.

확인된 upstream API 위험

고정한 v0.8.0에서 다음 세 공개 helper가 모두 실패했다.

  • get_scene_self_collision_distance_from_joint_trajectory: 2D/3D joint tensor unpack 불일치
  • get_collision_distance의 문서화된 tensor 입력: 내부 KinematicsState 요구와 불일치
  • validate_trajectory: 같은 2D/3D unpack 불일치

따라서 actual BeltBench adapter는 이 helper를 그대로 감싸면 안 된다. v0.8.0 primitive를 얇게 고정할지, 해당 결함이 수정된 공식 후속 commit을 새로 pin할지 먼저 비교하고 동일 smoke·parity corpus로 결정한다. Upstream source를 무기록 local patch로 고치는 방식은 채택하지 않는다.

아직 주장할 수 없는 것

  1. xArm6, Inspire Left와 두 CAD connector가 하나의 실제 collision model로 로드된다는 증거는 없다.
  2. Moving Pepsi pose update, phase-specific allowed contact, attachment, release envelope와 continuous swept collision을 검사하지 않았다.
  3. CUDA graph replay, resident scene/catalog/buffer reuse와 host-device round-trip 수를 측정하지 않았다.
  4. HPP-FCL exact-mesh corpus 대비 false negative 0을 확인하지 않았다.
  5. 1,000회 p50/p95/p99, deadline miss와 concurrent perception load를 측정하지 않았다.

다음 실행 순서

  1. v0.8.0과 공식 후속 source의 API 결함 수정 여부를 exact commit으로 비교해 adapter 기준 revision을 선택한다.
  2. xArm6/Inspire Left/connector sphere model과 static workcell scene을 실제 manifest digest에서 생성한다.
  3. Dynamic-world, attached-sphere, release-envelope pass와 allowed-contact semantics를 fixed-shape GPU workload로 구현한다.
  4. 동일 state/path corpus를 HPP-FCL과 비교해 false negative 0 gate를 통과시킨다.
  5. CUDA graph와 resident buffer를 켠 1,000회 benchmark가 policy p99와 zero miss를 통과한 뒤에만 runtime collision adapter를 activation한다.

Runtime admission contract, Resident cuRobo 방향, Assembly와 physics 경계를 함께 참고한다.

ISSUE-053 · 2026-08-11 · resident MuJoCo admission and cuRobo authority

MuJoCo 진단을 source-bound하고 cuRobo를 online collision authority로 유지한다.

실시간 grasp demo에서 collision을 CPU mesh checker로 계속 처리하는 것으로 보이면 cuRobo를 쓰지 않는 이유를 설명할 수 없다. 반대로 모든 작은 상태 머신까지 GPU로 옮기면 kernel launch와 동기화가 늘어 end-to-end p99가 나빠질 수 있다. 이번 단계는 GPU 수치 hot path, CPU causal control, offline oracle와 asynchronous physics의 권한을 분리하고, planning-validated resident command가 정확히 같은 MuJoCo 모델에만 들어가도록 admission을 닫았다.

현재 효력: source afc22c1은 backend-neutral full-command source join과 exact-MJB admission을 구현한다. MuJoCo는 항상 online_collision_authority=false이고, 실제 cuRobo V2 kernel·parity·target-GPU p99 또는 hardware 실행을 증명하지 않는다.
2026-08-12 정정: 아래의 V2 최소 driver 580.65.06 결론은 CUDA 13 하한을 V2 전체에 적용한 오류다. v0.8.0 CUDA 12 extra의 server qualification과 실제 kernel 검증이 올바른 다음 단계다. ISSUE-058에 원인과 수정 내용을 기록했다.

질문을 다시 정의한 이유

“GPU로 바꿀 수 있는 모든 모듈을 GPU로 바꾼다”는 구현 목표는 잘못됐다. 목표는 GPU 모듈 수가 아니라 sensor timestamp부터 controller command까지의 p99 latency, deadline miss와 collision false negative다. 작은 timestamp 비교, lease generation, deadline/cancel state와 controller acknowledgement는 host I/O 순서를 소유한다. 이를 GPU kernel로 보내면 병렬 이득 없이 host-device synchronization만 추가된다.

책임배치이유와 권한

기존 구조의 문제

  1. 공통 source join이 visualization 아래에 존재: MuJoCo가 그대로 재사용하면 simulation이 Viser 계층을 import하고 display pose가 physics input처럼 보인다.
  2. 구형 event backend와 새 full command의 계보 불일치: 기존 MJB는 event handoff와 offline planar observation으로 생성됐다. 새 resident output·producer lease·validated lease·lifecycle을 확인하지 않고 연결하면 서로 다른 initial object state와 command를 섞는다.
  3. 파일 hash만으로 compiled model을 설명할 수 없음: 같은 MJB라도 actuator target 순서, position-servo coverage, free joint 배치, geometry namespace와 collision pair가 예상과 다를 수 있다.
  4. 진단 가능과 physics-valid의 혼합: Provisional mass, friction, servo gain, connector와 calibration은 모델 실행 자체를 막지 않지만 물리 검증 결과로 승격되어서는 안 된다.
  5. cuRobo block의 최신성: 과거 driver 측정만 인용하면 환경이 바뀌었을 때 V2 구현을 계속 미루는 오류가 생긴다. Compute node에서 다시 측정해야 했다.

구현한 source 경계

Planning command의 공통 8-source semantic join을 beltbench/runtime/resident_full_command_inputs.py로 이동했다. Output, producer lease, validated lease, arm-prefix request, object lifecycle, robot manifest, object manifest와 workcell의 payload/tensor/session/template/slot/event/scene identity를 재계산한다. Viser는 이 runtime loader를 호출할 뿐 수치 권한을 소유하지 않는다.

MuJoCo scenario는 여기에 arm/assembly collision semantics, assembly MJCF/report, conveyor calibration, stable pose, physics config, actuation config, simulation policy, simulator capability, workcell preflight와 exact MJB를 추가한다. Loose-source override나 runtime fallback은 없다. Workcell preflight가 기록한 각 source digest, canonical assembly report와 MJB digest가 scenario와 다르면 모델을 열기 전에 거부한다.

Exact MJB admission

  • MuJoCo family/version, deterministic reset, mjb capability, fixed 2 ms step와 command duration policy를 확인한다.
  • Compiled body/joint/qpos/qvel/geometry/actuator dimensions을 workcell preflight와 대조한다.
  • Actuator order가 arm joint 뒤 mimic-expanded full-hand joint 순서와 정확히 같고 전부 bounded position servo인지 확인한다.
  • Free joint가 하나뿐인지, 그 joint가 이름만 같은 것이 아니라 실제 object body에 속하는지 읽어 확인한다.
  • Arm, hand, 흰색 paired connector, workcell, object visual/collision geometry의 누락과 추가를 모두 거부한다.
  • Semantic checked pair와 compiled explicit pair를 대조하고 checked와 ignored의 합이 assembly 전체 pair partition인지 확인한다.
  • Robot/connector CAD와 transform digest가 assembly report와 같은지 확인한다.
  • Compiled model의 default object SE(3)를 mj_forward 후 읽고 resident lifecycle sample 0과 translation·rotation 각각 1e-8 이내인지 확인한다.

diagnostic_rollout_ready는 위 executable-model 조건만 나타낸다. physics_validation_ready는 여기에 모든 non-informational preflight limitation과 measured calibration/stable pose/physics/actuation 상태를 추가한다. 두 경우 모두 hardware execution과 online collision authority는 false다.

실제 자산 probe

Local v7 MJB SHA-256은 96e8dafa0af197841a3b11163d1c7407e7780c72fa0dfb9b5c751cd939cc0e26이다. 새 probe로 MuJoCo 3.10.0, timestep 0.002 s, actuator 18개, 유일한 object/pepsi_light/free가 실제 object/pepsi_light body에 속함을 읽었다. Default object translation은 (0.620000, -0.400000, 0.141052)다.

이 결과는 모델 introspection smoke일 뿐이다. 실제 cuRobo producer/validator가 만든 resident five-artifact set이 없어 closed scenario를 만들지 않았고, 따라서 새 backend rollout이나 measured trace도 주장하지 않는다. Fixture를 실제 Pepsi planning output으로 포장하지 않았다.

junjinyong A6000 재측정

SERVER_GUIDE.md 절차대로 public-key SSH, ssu_a6gpu helper/queue를 확인한 뒤 repository의 capability-only PBS probe를 제출했다. Job 115818은 A6000 compute node에서 exit 0으로 완료됐고 source commit과 tracked worktree가 실행 전후 같았다. 원격 checkout에 이미 있던 untracked BODex build 산출물은 수정하거나 삭제하지 않았다.

  • GPU: NVIDIA RTX A6000, memory 49,140 MiB, compute capability 8.6
  • Driver: 535.161.07
  • 선택한 cuRobo V2 0.8.0 policy 최소 driver: 580.65.06

따라서 현재 서버에서 V2를 억지로 설치해 나온 실패나 legacy V1 결과를 production collision authority로 바꾸지 않는다. Driver가 갱신되면 sphere fitting, HPP-FCL parity, fixed-shape CUDA graph와 1,000-trial p99를 우선 실행한다.

발생한 문제, 원인과 해결

  1. compileall read-only 실패: 현재 도구 sandbox가 __pycache__ 쓰기를 막았다. Syntax 문제로 오판하지 않고 AST parse와 승인된 conda test 실행으로 분리했다.
  2. MuJoCo capability에 MJB 누락: 기존 example은 MJCF/URDF/OBJ/STL만 선언하면서 실제 backend는 MJB를 읽었다. Admission이 binary format을 요구하도록 하고 capability에 mjb를 명시했다.
  3. 첫 admission의 collision partition 누락: Checked pair를 비교했지만 ignored pair와 전체 pair의 완전성은 확인하지 않았다. 누락 pair가 broad ignore처럼 작동할 수 있어 complete/disjoint partition hard gate와 regression을 추가했다.
  4. Free joint 이름만 검사: 다른 body에 동일 관례 이름이 있어도 통과할 여지가 있었다. Compiled body_jntadr/body_jntnum에서 object body joint 소유권을 읽도록 보강했다.
  5. PBS login shell에서 qsub 미발견: Non-interactive SSH가 profile PATH를 제공하지 않았다. Guide에 기록된 PBS 설치 경로의 /opt/pbs/bin/qsub를 사용했다.
  6. 완료 직후 결과 디렉터리 지연: PBS state가 exiting일 때 shared filesystem 목록이 잠시 비어 있었다. Job을 재제출하지 않고 completion과 directory materialization을 분리해 poll했다.
  7. Server checkout fast-forward 실패: junjinyong의 HTTPS Git credential과 local gh CLI token이 만료돼 GitHub read pull이 인증 단계에서 거부됐다. Credential을 shell에 노출하거나 server 설정을 바꾸지 않았다. Source/devlog push는 local Git credential 경로로 완료됐고, capability probe는 checkout의 기존 tracked script만 사용했으며 remote worktree는 그대로 유지했다.
  8. Planning env의 cv2 부재: 전체 suite의 calibration, pickplace, pose artifact 세 import 오류는 기존 환경 분리 문제였다. Calibration conda 환경에서 해당 14개를 별도 실행했다.

검증 결과

  • 새 scenario/admission regression은 source closure, exact admission, actuator order, free-joint uniqueness/body ownership, initial pose, pair partition과 provisional readiness 분리를 검증한다.
  • 최종 focused admission·Viser·legacy MuJoCo admission 22개가 모두 통과했다.
  • 최종 pushed commit의 expanded resident/MuJoCo 회귀 52개는 50개 통과, MuJoCo optional 2개 skip이었다.
  • Planning 전체는 보강 전 706개 중 701개 통과, 2개 skip, 기존 cv2 import 오류 3개였다. 새 코드는 해당 오류와 무관하다.
  • Calibration 환경의 OpenCV 의존 14개와 MuJoCo 환경 전용 31개가 모두 통과했다.
  • Public runtime/simulation imports, 두 CLI --help, AST parse, 88-column Python 검사와 git diff --check가 통과했다.

남은 순서

  1. 관리자 승인 아래 target driver를 V2 요구사항 이상으로 갱신하거나 별도 지원 GPU worker를 확보한다.
  2. Exact xArm/Inspire/connector sphere model을 만들고 HPP-FCL mesh corpus에서 false negative 0과 허용 false-positive budget을 통과시킨다.
  3. Custom fixed-shape cuRobo V2 producer/independent validator를 구현해 dynamic-world, attached-sphere와 release-envelope continuous collision을 한 resident session에서 실행한다.
  4. 실제 output·producer/validated lease·lifecycle로 MuJoCo scenario를 만들고 position-servo backend가 measured state/contact/containment trace를 별도 생성하게 한다.
  5. Physics parameter를 측정하기 전 결과는 diagnostic으로만 유지하고, hardware가 준비되면 controller lease, latency, moving contact와 grasp/drop reliability를 검증한다.

cuRobo real-time collision audit, Full-command actual-asset diagnostic, Full-task resident validation을 함께 참고한다.

ISSUE-038 · 2026-08-10 · inference demo / physics validation

Grasp 학습보다 실제 inference demo를 먼저 완성하고, 충돌과 접촉을 독립 physics backend로 재검증한다.

연구 우선순위를 AutoDex training과 추가 data collection에서 벗어나, 이미 제공되거나 어떤 generator에서 생성된 grasp를 사용해 움직이는 물체를 실시간으로 잡고 큰 bin에 떨어뜨리는 end-to-end demo로 옮겼다. Online IK·collision·trajectory optimization은 policy로 승인된 pinned cuRobo GPU backend를 목표로 하고, HPP-FCL은 독립 mesh oracle, MuJoCo와 Isaac Sim은 같은 immutable trajectory의 physics validation backend로 역할을 분리한다. Current V2는 target server driver 때문에 아직 실행할 수 없다.

방향 전환의 근거

지도 의견의 핵심은 grasp data source를 연구 병목으로 두지 말고, 현재 흩어진 perception·planning·controller 구성요소가 실제로 한 번의 grasp demo를 완주하게 만드는 것이다. 따라서 AutoDex/BODex는 검증 grasp가 없을 때 사용하는 offline provider 중 하나로 축소한다. Runtime은 provider 종류를 알 필요가 없고 정규화된 object-relative grasp, scope와 checksum만 소비한다.

offline: any grasp source → normalized library → independent validation
online : track + encoder + robot state → bounded path update → one handoff
backend: exact handoff → measured state/contact → release → bin containment
replay : the same evidence → Viser

현재 bounded-retention production batch는 한 개의 입력 grasp source를 검수하는 작업으로만 마무리한다. 이 batch를 더 확장하거나 AutoDex training을 반복하는 일은 end-to-end demo보다 우선하지 않는다.

따라서 “collision filtering이 있다”와 “실행 중 collision-free다”는 같은 주장이 아니다. 현행 actual-asset playback도 301 frame 중 163 frame이 hard gate를 실패하므로 practical demo가 아직 완성됐다고 말할 수 없다. Object attach animation으로 mesh 교차를 숨기거나 충돌 threshold를 임의 완화하지 않는다.

왜 cuRobo를 online collision backend로 택하는가

기존 Pinocchio/HPP-FCL 구현은 full named mesh와 pair별 signed distance를 제공해 기준 자료로 적합하지만, 현재 production batch의 CPU coarse pass가 순차 실행될 때 수백 초가 필요했다. 이 경로를 그대로 camera cadence의 online planner로 사용하는 것은 현실적이지 않다. cuRoboV2는 batched FK/IK, robot self/world collision과 trajectory optimization을 GPU에서 실행하고, CUDA graph·stream, resident scene, runtime obstacle pose update를 지원하므로 grasp × yaw × intercept time × seed 후보를 fixed-shape batch로 평가하는 본 문제와 맞는다.

그러나 모든 모듈을 CUDA로 옮기는 것은 목표가 아니다. Timestamp join, freshness, 작은 Kalman state, atlas lookup, controller serialization은 branch와 I/O가 지배적이며 별도 kernel launch와 host-device synchronization이 더 비쌀 수 있다. GPU는 image inference와 batched planning hot path에 사용하고, 한 compact result만 CPU controller boundary로 돌려보낸다. 실제 배치는 1,000회 post-warmup raw trial, deadline miss, host-device 왕복 수와 output validation으로 결정한다.

cuRobo의 robot collision은 sphere approximation과 self-collision ignore를 사용한다. 따라서 sphere fit, padding과 ignore pair를 자동 생성 후 그대로 신뢰하지 않는다. 동일한 checksummed robot/workcell state corpus를 HPP-FCL full mesh와 비교해 false negative는 release blocker로, false positive는 workspace 손실로 계량한다. Physics simulator contact와 hardware stop은 다시 별도 계층이다.

third_party/bodex 안의 수정 cuRobo는 BODex offline grasp generator 의존성이다. Current cuRoboV2는 2026년 v0.8.0에서 API가 크게 바뀌었고 Apache-2.0으로 공개됐다. 기존 fork의 local patch와 provenance를 online authority로 상속하지 않고, 모든 runtime backend를 별도 pinned environment와 BeltBench adapter 뒤에 격리한다.

문제: target server에서 cuRoboV2를 바로 쓸 수 없다

기존 target-server GPU evidence는 RTX A6000과 NVIDIA driver 535.161.07을 기록한다. 현재 공식 cuRoboV2 설치 조건은 driver 580.65.06 이상이므로, A6000의 연산 성능과 별개로 현 driver에서는 V2 설치를 production 방향으로 강행할 수 없다. Driver upgrade 또는 호환 host가 가장 유지보수 가능한 해결이다.

공식 repository가 V1 API 필요 시 제시하는 v0.7.8은 현 서버의 임시 호환 후보지만, 해당 tag의 package metadata와 source header는 current Apache-2.0이 아니라 NVIDIA license를 사용한다. 이를 “예전 버전이니 설치 가능”으로 해석하지 않는다. 연구실 사용 승인 근거를 확인하기 전에는 설치·benchmark를 진행하지 않고, 승인 후에도 clean upstream tag를 별도 adapter로 평가한다. BODex 내부 수정 fork는 진단 비교 대상일 뿐 runtime planner가 아니다.

cuRobo가 매 frame 반드시 필요한가

고정 workcell에서 exact robot·connector·stop path·correction tube와 continuous path collision을 offline 검증한 resident path family가 있고, 측정 robot state와 object correction이 그 tube 안에 있다면 매 camera frame마다 같은 global collision을 반복할 필요는 없다. Runtime은 checksummed family를 bounded lookup하고 tube 밖이면 reject한다. 이 경로가 첫 실기 demo의 최저 latency fast path다.

cuRobo는 path family 생성과 batched screening, atlas가 지지하지만 certified family가 없는 context의 단 한 번 bounded warm start, 또는 static scene 가정 밖의 pose update에 사용한다. 첫 demo에서는 online warm start를 비활성화하고 atlas coverage를 충분히 확보하는 편이 타당하다. 새 trajectory를 즉석 생성해 독립 검증 없이 실행하는 것보다 명확하게 거부하는 편이 안전하고 재현 가능하다.

Simulator 선택

현재 하드웨어와 완성 workcell이 없으므로 MuJoCo를 첫 headless backend로 앞당겼다. 실제 URDF/connector가 하나의 articulation으로 compile되는지, full hand joint가 보존되는지, contact/dynamics loop가 real-time factor를 만족하는지를 Isaac 설치보다 가볍게 검증할 수 있다. 다만 MuJoCo는 oracle이 아니며 inertia, mimic, actuator, friction, contact solver를 모두 명시해야 한다.

Primary integrated workcell backend는 이후 Isaac Sim/Isaac Lab으로 유지한다. 공식 URDF importer 문서는 URDF를 USD articulation으로 가져오고 collision mesh, self-collision, fixed base와 joint drive를 구성하는 경로를 제공한다. sensor schema에는 contact force를 관측하는 contact sensor가 있다. 추후 ROS 2 bridge와 scene rendering을 연결하기에도 적합하다.

새 구현을 Isaac Gym Preview에 두지는 않는다. 공식 Isaac Lab migration 문서가 Isaac Gym Preview와 IsaacGymEnvs를 deprecated로 명시한다. 두 simulator의 force 수치를 같게 만드는 대신 동일한 failure taxonomy와 lifecycle을 재현한다.

새로 구현한 경계

beltbench@c670857에 simulator-neutral 계약을 추가했다.

  • InferenceSimulationScenario: runtime session, causality, accepted handoff, normalized grasp library, robot/hand/connector, collision semantics, object, workcell, limits와 moving-contact source를 SHA-256으로 고정
  • InferenceSimulatorCapability: articulation, rigid dynamics, conveyor, joint/rigid-body feedback, contact pair/force와 deterministic reset 지원을 명시
  • InferenceSimulationReport: planning-to-dispatch latency, real-time factor, arm/hand tracking, event timing, contact pair, observed lifecycle와 terminal containment를 저장
  • VerifiedInferenceSimulationInputs: request와 grasp digest, arm/hand/object/workcell ID, connector transform, URDF collision checksum, joint ordering, motion-limit digest와 moving-contact trajectory를 교차 검증
  • InferenceSimulationBackend: Isaac/MuJoCo가 구현할 dependency-free protocol. Planning core는 simulator package를 import하지 않음

Backend의 passed와 contact label도 신뢰하지 않는다. Geometry는 arm/, end_effector/, object/, workcell/ namespace로 정규화한다. BeltBench가 checksummed object-interaction semantics로 fingertip/object, belt support와 bin support만 다시 허용하고 나머지는 unintended collision으로 분류한다. 모든 simulation report는 execution_authorized=false다.

Pinned cuRobo acceptance 계약과 실제 MuJoCo assembly

beltbench@53a3a1a에서 accelerated runtime과 actual-asset preflight를 추가했다.

  • RealtimePlanningPolicy: required_backend_family=curobo_v2, fixed batch, resident world, preallocated buffer, CUDA graph, 최대 host-device 왕복과 reject-only fallback을 선언
  • RealtimePlanningBackendCapability: exact backend revision, device, batched IK/collision/trajopt, dynamic world update와 collision representation을 고정
  • RealtimePlanningBenchmarkReport: target GPU/driver와 robot/world digest에 대해 1,000개 이상 raw post-warmup trial, p50/p95/p99/max, deadline miss와 output validation을 보존
  • Stored pass/failure flag는 신뢰하지 않고 capability·policy·raw trial에서 failure를 다시 계산한다. CPU fallback, family 위조, warm-up 누락과 전송 budget 초과는 hard failure다.
  • preflight_mujoco_assembly: actual xArm6 URDF, Inspire Left 12 joints, xArm-side/Inspire-side connector OBJ를 compile하고 semantic geometry identity와 XML/MJB 재로드를 검사

실제 local preflight는 MuJoCo 3.10.0에서 19 bodies, 18 joints, 18 qpos와 22 named collision geometries를 만들었다. Arm 7, hand 13, connector 2 geometry가 arm/, end_effector/, connector/ namespace로 보존됐다. 결과는 import evidence일 뿐이며 execution_authorized=false다.

beltbench@220d5a7에서 발견된 server incompatibility를 fail-closed 계약으로 반영했다.

  • Policy가 exact backend version과 minimum driver를 고정하므로 driver 535에서 V2 policy는 driver_version_unsupported로 실패한다.
  • 별도 curobo_v1_pinned compatibility policy는 v0.7.8만 받지만, usage approval reference가 없으면 backend_usage_not_approved로 실패한다.
  • Capability digest에 source revision, software license, approval 상태를 포함하며 저장된 pass flag는 여전히 raw trial에서 재계산한다.
  • V1/V2 타입은 core contract로 유출하지 않는다. 동일 warm-start/backend protocol 뒤에서 교체하며 implicit CPU 또는 BODex-fork fallback은 없다.

Actual workcell 조합과 contact audit

beltbench@f78c175에서 assembly importer를 재사용하는 MuJoCo workcell composer를 추가했다. Backend-neutral physics/report 계약은 beltbench/contracts, MuJoCo scene 생성은 beltbench/simulation에 분리했다. Composer는 checksummed xArm6·Inspire Left·양쪽 connector assembly에 calibrated perpendicular conveyor, robot mounting table, floor와 네 벽으로 구성된 큰 drop bin, upside-down stable pose와 provisional planar observation이 적용된 실제 Pepsi Light visual/collision mesh를 추가한다.

실제 append-only preflight 결과는 MuJoCo 3.10.0에서 20 bodies, 19 joints, 25 qpos, 24 qvel, 31 geometries로 XML과 MJB 재로드를 통과했다. Conveyor deck top과 calibration frame도 수치적으로 일치했다. 이 결과는 scene composition만 검증하며 conveyor dynamics, actuator, contact lifecycle과 trajectory는 검증하지 않으므로 report는 항상 execution_authorized=false다.

문제 또는 관찰원인 분석조치와 결과
Workcell composition에서 trimesh import 실패environment/mujoco.yml에는 의존성이 선언됐지만 이미 만들어진 실제 environment에는 설치되지 않아 선언과 실행 상태가 달랐다.새 environment로 교체하지 않고 기존 environment에 exact trimesh 4.8.3을 설치했다. 이후 실제 GLB visual/collision instance를 OBJ로 변환하고 compile·reload했다.

따라서 다음 physics 구현은 actuator와 moving belt를 먼저 덧붙이는 일이 아니다. Collision-free initial arm/hand command와 backend pair mapping을 확정하고, saved trajectory를 다시 생성·검증한 뒤 그 exact trajectory에 actuator tracking, moving object support, contact → retention → release → bin containment 관측을 단계적으로 추가한다.

HPP-FCL mesh와 cuRobo sphere를 같은 corpus에서 비교하는 gate

beltbench@954b03e에서 backend-neutral collision corpus, raw observation report, acceptance policy와 comparison report를 구현했다. Corpus/observation과 acceptance/comparison 계약을 별도 모듈로 분리하고, vendor import는 edge adapter에만 남겼다. Stored pass flag는 신뢰하지 않으며 각 state의 minimum pair-specific margin에서 safe/unsafe를 다시 계산한다.

Draft acceptance는 exact sphere·ignore·world configuration SHA-256, 1,000개 이상 unique state, trajectory·joint-limit·workspace·near-boundary·known-collision sample, mesh-clear 250개, mesh-unsafe 250개, ±2 mm boundary 100개를 요구한다. HPP-FCL unsafe를 cuRobo가 safe로 판단하는 false negative는 0개만 허용하고, false positive는 mesh-clear state의 5% 이하로 제한한다. 이 geometry parity와 별개로 target GPU의 warm-up·fixed batch·CUDA graph·host-device transfer·p99/deadline benchmark를 통과해야 한다.

2026-08-10 확장: 1,265-state 진단에서 1,445-state oracle까지

beltbench@4a45e56에서 첫 corpus의 부족한 coverage를 임의 random sampling으로 메우지 않는 결정론적 augmentation을 구현했다. Schema 2.0은 parent corpus, HPP-FCL seed report, named motion-limit profile, generation policy와 실행한 augmentation source 자체를 SHA-256으로 고정한다. 평가 시 같은 입력에서 corpus 전체를 다시 생성해 payload가 다르면 거부한다. 따라서 sample 수만 같게 만든 forged JSON이나 변경된 generator는 oracle 입력이 될 수 없다.

ParaDex cuRobo 경로 재감사

ParaDex에 MotionGen과 IKSolver wrapper가 있으므로 cuRobo를 새로 발견한 것은 아니다. 그러나 현 코드는 motion-generator CUDA graph를 끄고 object update마다 world cache를 clear/rebuild하며, 별도 IK solver에서는 self_collision_check=False이고 batch start state를 첫 6축으로 slice한다. Source-bound sphere/ignore parity나 latency evidence도 없다. 이는 원래 static collection demo의 구현 참고자료이지, moving xArm+Inspire의 online collision authority로 그대로 복사할 코드가 아니다.

더 직접적인 blocker는 exact assembly collision model 부재다. BODex에는 Inspire-only sphere와 xArm+Allegro sphere가 있고, ParaDex에도 xArm+Allegro sphere가 남아 있다. 이를 단순 병합하면 connector mount와 arm-hand cross-collision을 누락하거나 broad ignore로 숨길 수 있다. Connector metrology 후 exact checksummed combined model에서 sphere를 fitting하고 mounted base를 명시적으로 clip하며 seed·fit metric·padding을 고정해야 한다. Random self-collision sampling이 만든 auto-ignore도 그대로 신뢰하지 않고 named HPP-FCL semantics와 corrected 1,445-state oracle에 대해 false negative 0을 확인한다.

결론적으로 GPU 가속 대상은 image inference와 fixed-shape batched IK·self/world collision·trajectory optimization·candidate reduction이다. Timestamp/encoder join, 작은 track filter, atlas lookup, controller serialization은 CPU에 남긴다. HPP-FCL은 병렬 offline oracle이고 MuJoCo/Isaac은 physics validator다. 현재 target driver와 exact sphere model이 해결되기 전까지 “cuRobo collision이 적용됐다”거나 real-time end-to-end가 완성됐다고 주장하지 않는다.

발생한 문제: retention gain 1.0

Bounded policy의 첫 후보는 first-contact command 자체인 gain=1.0이다. 그러나 compute-node full evaluation은 시작 후 다음 오류로 종료됐다.

ValueError: retention gain must be finite and greater than one

원인은 schema 3.0은 gain=1.0을 요구하지만, 이전 hand joint helper는 squeeze extrapolation만 가정해 gain>1을 강제한 계약 불일치였다. Grasp geometry 실패나 scheduler 문제는 아니었다. Helper를 gain>=1로 수정했고, 1.0에서는 부동소수점 extrapolation을 하지 않고 검증된 contact command를 그대로 보존한다. 처음에는 산술 결과가 0.9 대신 0.899999...가 되어 checksum 안정성 문제를 단위 테스트가 잡았다. Tolerance로 숨기지 않고 identity path를 분기해 해결했다.

Full evaluation의 117개는 grasp/path atlas 입력 후보일 뿐 execution-ready grasp가 아니다. Isaac은 같은 immutable scenario를 소비하는 두 번째 physics backend이며, controller stop, measured calibration/latency, continuous swept collision과 moving hardware reliability는 계속 별도 hard gate로 둔다.

ISSUE-058 · 2026-08-12 · runtime GPU collision admission

매 observation의 cuRobo 충돌 승인을 controller publish 앞에 강제한다.

Resident cuRobo 방향과 recorded planning runner는 있었지만 실제 조합에서는 선택된 trajectory가 그 generation의 GPU collision 결과 없이 publish되거나, active trajectory가 남은 구간 재검사 없이 유지될 수 있었다. Source commit 5d2a464은 exact request-bound collision assessment를 planning과 controller 사이의 필수 admission boundary로 만들고, 잘못된 cuRobo V2 driver 전제를 공식 패키지와 NVIDIA CUDA 문서에 맞게 정정한다.

결론: cuRobo를 사용하지 않는 것이 아니라 online numerical collision authority로 사용한다. 다만 모든 module을 GPU로 옮기지는 않는다. Image inference, batched FK/IK/collision/trajopt와 device-side reduction은 resident GPU hot path에 두고, timestamp join, freshness, deadline, cancel, controller ACK는 CPU causal state machine으로 유지한다.

발견한 안전성 공백

  1. Latch publish 우회: 기존 RuntimeSelectionControlCoordinator는 latch_precompiled selection을 GPU collision 결과 없이 controller mailbox에 publish할 수 있었다.
  2. Active retain 공백: controller가 이미 소유한 path는 redispatch하지 않는 것이 맞지만, 최신 robot/object state에 대한 남은 trajectory collision 재검사가 없었다.
  3. 호출자 신뢰: 초기 수정안은 caller가 계산한 빈 failure tuple을 mailbox에 넘겼다. Caller가 검증을 생략하면 accepted assessment만으로 publish될 수 있었다.
  4. 허위 margin 위험: Gate 결과를 minimum_normalized_margin으로 표현하면 cuRobo decision/cost를 exact mesh signed clearance처럼 오해할 수 있었다.
  5. Source 결속 부족: Assessment가 trajectory ID만 가지면 같은 ID의 다른 request payload나 다른 generation 결과를 재사용할 수 있다.

Gate deadline은 planning completion에 policy budget을 더한 시각과 observation commit deadline 중 이른 값이다. Planning runner, gate와 mailbox는 같은 monotonic clock object를 사용하고, gate와 mailbox는 같은 exact policy를 사용해야 한다.

구현한 계약

  1. RuntimeTrajectoryCollisionGateAssessment가 generation, canonical runtime-request SHA-256, activation, action, path family, event-trajectory digest, policy digest, collision-configuration digest와 검사 시간 구간을 결속한다.
  2. 결과는 collision_free decision으로 기록한다. Exact signed clearance를 만들지 않으며, unavailable/error/collision은 reason code와 함께 fail-closed한다.
  3. Fixed batch, 실행 operation, CUDA graph, resident world/catalog, preallocated buffer, host-device round trip과 synchronous write 수를 policy와 독립적으로 다시 검사한다.
  4. 보고된 검사 sample 수가 exact event request의 명시 waypoint 수보다 작으면 collision_gate_waypoint_coverage_incomplete로 거부한다. Continuous/swept 밀도는 이후 backend session evidence가 추가로 책임진다.
  5. RuntimeControllerHandoffMailbox가 collision policy를 소유하고 publish 직전에 failure를 재계산한다. 외부 caller는 빈 failure 목록을 넘겨 우회할 수 없다.
  6. Accepted handoff schema 1.1은 exact gate assessment를 포함한다. Causal loader는 runtime request digest와 selection/gate/publish timestamp 순서를 다시 검증한다.
  7. Viser handoff panel은 gate backend, evidence scope, clear/reject decision, trajectory interval, sample count, latency와 deadline을 표시한다.

실제 adapter가 없을 때의 동작

UnavailableRuntimeTrajectoryCollisionGate는 CUDA operation, resident cache나 graph replay를 허위로 기록하지 않는다. Device를 unavailable로 표시하고 항상 reject한다. 따라서 run_recorded_path_family.py는 collision policy와 configuration을 필수 입력으로 받지만, 현재 product CLI는 실제 cuRobo adapter가 주입되기 전까지 accepted handoff를 생성하지 않고 exit 2로 끝난다. Test double의 accepted 결과는 contract 회귀용이며 target-GPU evidence가 아니다.

작은 branch-heavy state machine까지 CUDA kernel로 옮기면 launch와 synchronization이 늘어난다. 목표 지표는 GPU module 개수가 아니라 sensor-to-command p99, deadline miss, host-device round trip과 cancellation latency다.

Driver 전제 정정

이전 ISSUE-056은 cuRobo V2 0.8.0이 driver 580.65.06 이상만 지원한다고 기록했다. 원인은 CUDA 13 driver 하한을 V2 전체 하한으로 해석한 것이다. 공식 v0.8.0 pyproject는 cu12와 cu13 extra를 별도로 제공한다. NVIDIA는 CUDA 12.x Linux minor compatibility 하한을 525.60.13으로 문서화한다.

따라서 driver 535.161.07 A6000은 CUDA 12 자격 검증 대상이지 원천 차단 대상이 아니다. 두 V2 policy는 새 ID와 525.60.13 하한으로 바꿨다. 단, cuRobo의 runtime CUDA compilation은 minor compatibility의 feature restriction을 받을 수 있으므로 실제 cu12 install, FK/self/world/dynamic-object kernel smoke와 benchmark가 통과하기 전에는 compatible하다고 주장하지 않는다.

2026-08-12 후속: 별도 RTX 3090 host에서 CUDA 12 FK·static world/self collision primitive smoke는 통과했다. v0.8.0의 Warp pin과 공개 wrapper 결함, 측정 범위는 ISSUE-059에 기록했다. 이는 actual xArm/Inspire collision adapter나 runtime deadline 승인으로 승격되지 않는다.

발생한 문제, 원인, 해결

  1. Accepted assessment timestamp 실패: Controller lead-time test가 gate deadline 뒤에 accepted assessment를 만들었다. Gate contract가 올바르게 거부한 것이므로, gate evidence는 제시간에 생성하고 publish만 늦추도록 fixture를 수정했다.
  2. 기본 Python import 실패: base Python 3.13에는 numpy가 없어 test import가 중단됐다. 코드 실패와 환경 실패를 분리하고 beltbench-planning conda 환경에서 재실행했다.
  3. 잘못된 test module 이름: 광범위 회귀 명령에 존재하지 않는 두 module을 지정해 77개 통과 후 loader error가 났다. rg --files tests로 실제 이름을 찾아 97-test 묶음으로 재실행했다.
  4. Lint 도구 부재: planning 환경에는 ruff가 없었다. 임의 설치로 lock을 바꾸지 않고 compile, 99-column scan, git diff --check와 unittest로 검증했다.
  5. 새 GPU 서버 인증 실패: Tailscale host는 응답했지만 현재 작업 shell의 key를 처음에는 거부했다. 비밀번호나 token을 명령·로그에 넣지 않고 공개키를 등록한 뒤 모든 작업을 ~/.agile/projects 아래에서 수행했다.

아직 주장할 수 없는 것

  1. 실제 cuRobo V2 kernel adapter, CUDA graph replay output, HPP-FCL parity와 1,000회 p99 evidence는 없다.
  2. 10 ms resident gate deadline과 50 ms warm-start deadline은 정책 가설이지 측정값이 아니다.
  3. Accepted retain assessment는 현재 in-memory result이며 별도 active-controller evidence snapshot과 실제 cancel protocol은 아직 없다.
  4. Actual source-closed continuous Pepsi/xArm/Inspire path-family bundle이 없어 1.0x full vertical slice를 아직 실행하지 못했다.
  5. RTX 3090 환경 kernel smoke는 통과했지만 actual xArm/Inspire assembly, moving-object semantics와 runtime workload는 아직 검증하지 않았다.

다음 실행 순서

  1. v0.8.0의 공개 wrapper 결함과 공식 후속 source를 비교해 actual adapter의 exact revision을 선택한다.
  2. Evidence-gated actual collision adapter를 구현해 resident full command의 dynamic-world, attached-sphere, release-envelope pass를 실행한다.
  3. Exact xArm6/Inspire/connector sphere config를 HPP-FCL corpus와 비교해 false negative 0 gate를 통과시킨다.
  4. 1,000회 post-warmup p50/p95/p99, deadline miss, graph/cache/buffer reuse와 transfer 수를 측정한다.
  5. 실제 continuous Pepsi bundle을 만들고 accepted gate, diagnostic handoff, MuJoCo feedback과 1.0x Viser를 한 source-closed vertical slice로 연결한다.

ISSUE-011 · 2026-08-07 · GPU smoke 완료, production 후보 생성 필요

검증 grasp가 없을 때 BODex 후보를 재현 가능하게 생성하고, 독립 평가로 넘긴다.

정확히 같은 object, stable pose, hand, task capability로 검증된 grasp가 있으면 재사용한다. 그런 항목이 없으면 offline 생성이 필요하다. 이번 작업은 Pepsi Light upside-down pose와 Inspire left hand를 예로 들어, BODex 입력 자산부터 GPU runtime, 후보 import, intrinsic 평가까지의 경계를 checksummed artifact로 고정하는 과정이다.

문제와 영향

기존 코드에는 BODex source가 있었지만, 현재 환경에서 그대로 실행 가능한 생성 pipeline은 아니었다. object mesh를 provider가 요구하는 디렉터리와 URDF로 만드는 절차, exact stable pose만 입력했다는 증거, Python·CUDA·native extension 조합, 생성 결과를 provider 판단과 분리해 import하는 규칙이 빠져 있었다. 이 상태에서 한 번 실행에 성공해도 다른 서버나 다음 환경에서 재현하기 어렵고, BODex의 success 값을 BeltBench의 grasp 검증으로 잘못 해석할 위험이 있었다.

Object layout 불일치

BeltBench의 checksummed GLB manifest와 BODex의 OBJ·URDF·scene layout이 달랐다. collision decomposition을 한 mesh로 합치면 provider의 거리 질의 의미도 바뀐다.

Stable pose 혼합 위험

provider output 디렉터리는 여러 tabletop pose를 담을 수 있다. 한 run을 나중에 특정 pose로 이름만 바꾸면 어떤 support orientation에서 생성했는지 증명할 수 없다.

GPU package만으로 부족

torch가 설치됐다는 사실은 CUDA tensor, cuRobo extension, Coal wrapper가 같은 worker에서 실제 load된다는 증거가 아니다.

Provider 판단과 검증 혼합

BODex native success, contact count, metric은 생성 provenance다. BeltBench의 contact·task-wrench·support·approach·closure·release acceptance를 대신할 수 없다.

구현한 계약

  1. Checksummed asset adapter: object manifest의 scale과 transform을 적용해 BODex-native OBJ, URDF, geometry info를 만든다.
  2. Collision component 보존: Pepsi collision GLB의 connected component 94개를 각각 별도 URDF mesh로 유지한다.
  3. 단일 pose staging: 한 staging manifest에는 한 object와 한 stable-pose identity만 넣고, source와 생성 파일을 모두 다시 hash한다.
  4. Runtime preflight: exact Python에서 NumPy, SciPy, trimesh, Torch, Warp, cuRobo CUDA extension, Coal wrapper를 import한다. GPU mode에서는 CUDA tensor 연산과 synchronize까지 수행한다.
  5. Same-worker gate: generator, output schema, manipulator config, environment lock, object list, staging manifest digest가 preflight와 generation 사이에 같아야 한다.
  6. Provider-neutral import: 모든 seed와 native metric shape를 보존하되 상태는 unvalidated_proposal로 고정한다.
  7. 독립 intrinsic 평가: 실제 hand URDF와 object collision mesh로 접촉과 경로를 다시 계산하고, 통과한 후보만 별도 robot deployment 평가로 넘긴다.

GPU smoke와 wrist-stage A/B 검증

고정한 환경은 Python 3.10, Torch 2.5.1+CUDA 12.4, Warp 1.6.2, torch-scatter 2.1.2+pt25cu124, vendored cuRobo와 Coal native extension을 같은 A6000 worker에서 import하고 CUDA tensor 연산까지 통과했다. 동일한 Pepsi Light upside-down staging과 Inspire left config에서 seed 8개를 생성했으며, 각 seed의 native array shape와 모든 source digest를 보존했다.

v1 hybrid pose

8개 모두 provider success는 false였다. 더 중요한 문제는 provider contact count 5와 달리 독립 mesh 평가에서 접촉이 0~1개, task-wrench quality가 전부 0이었다. 생성 품질 이전에 저장 pose가 일관되지 않았다.

v2 final wrist

같은 설정으로 재생성한 결과 중간 root와 최종 root 차이는 2.8~8.6 mm, 1.9~4.2°였다. final root로 평가하자 독립 접촉이 2~4개로 회복됐고 2개 후보는 task-wrench 최소값 0.01을 통과했다.

v2에서도 provider success는 0/8이었고 최종 승인 후보는 없었다. task-wrench를 통과한 두 후보의 quality는 약 0.0849와 0.0147이었지만 허용 contact penetration을 크게 넘었다. 경로 관통이 없던 후보는 접촉 2개와 quality 0으로 탈락했고, endpoint 관통이 0.5 mm 이하였던 다른 후보도 quality 0과 release 관통으로 탈락했다. 따라서 threshold를 낮추거나 “가장 덜 나쁜” 후보를 자동 선택하지 않았다.

해석: 8 seeds는 실행 경로와 evidence schema를 확인하는 smoke budget이지 grasp 탐색 budget이 아니다. adapter 수정으로 올바른 기하가 복원됐지만 usable grasp가 생성됐다는 뜻은 아니다. production seed batch를 별도 immutable run으로 만들고, provider 결과와 무관한 hard gate를 통과한 후보만 library 승격 대상으로 삼아야 한다.

평가 evidence 시각화

상세 intrinsic JSON만으로는 contact와 경로 실패를 빠르게 검토하기 어려워 read-only Viser viewer도 추가했다. viewer는 checksummed proposal과 config에서 approach·closure·release interpolation만 복원하고, 저장된 contact point, inward normal, clearance, penetration 판정을 실제 Inspire hand와 Pepsi mesh 위에 표시한다. 자동 반복 재생과 일괄 label toggle을 제공하지만 품질을 재계산하거나 후보를 rank·promote하지 않는다.

final-wrist 후보의 44개 approach·closure·release 상태를 load해 HTTP 응답을 확인했다. 기존 playback과 포트가 겹쳤을 때 Viser가 다음 포트를 자동 선택하면서 CLI가 요청 포트를 잘못 출력하는 문제도 발견했다. 모든 Viser entry point가 server.get_port()로 실제 bind 포트를 보고하도록 수정했고, 출력 URL과 HTTP 200 응답이 일치하는지 재검증했다.

시각화 경계: 색상과 애니메이션은 저장된 evidence를 읽는 검토 도구다. Viser에서 자연스럽게 보인다는 사실은 grasp 성공, robot reachability, moving interception timing을 증명하지 않는다.

현재 검증과 남은 일

BeltBench revision 9c70b62에서 planning/core test 169개와 OpenCV 분리 test 14개, 총 183개가 통과했다. BODex asset·staging·runtime·output schema·import와 Viser 관련 회귀도 전체 suite에 포함했다. 최종 endpoint screening v3의 source 16개와 기존 proposal source를 다시 검증했다.

비용이 큰 전체 path 평가 전에 독립 endpoint contact·penetration·self/support clearance·task-wrench를 계산하는 O(N) batch evaluator를 구현했다. 실제 8개는 기존 full 결과와 8/8 일치하며 모두 조기 탈락해 352개 path state를 생략했다. 다음 production 생성은 provider config의 충분한 seed budget을 명시한 별도 immutable run으로 수행하고, exact survivor worklist에 포함된 후보만 full path로 넘긴다. provider success는 평가 순서나 acceptance에 사용하지 않는다.

현재 upside-down stable pose는 mesh bounds 기반 provisional이고 task protocol도 provisional이다. 따라서 geometry가 좋아도 진단 결과만 만들 수 있다. measured stable pose와 approved protocol을 확보하고 intrinsic gate를 통과한 뒤에만 offline_intrinsic library로 승격하며, xArm mount·IK·combined collision·moving timing은 그 다음의 별도 deployment gate다.

Arm-independent intrinsic grasp 평가에서 후보 acceptance 기준을, Offline planning과 Viser 구현에서 이후 xArm deployment와 moving interception 연결을 계속 관리한다.

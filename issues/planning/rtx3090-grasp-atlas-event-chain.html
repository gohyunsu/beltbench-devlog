ISSUE-062 · 2026-08-12 · RTX 3090 candidate-to-event diagnostic chain

새 GPU worker에서 grasp 후보부터 event trajectory까지 다시 닫는다.

실제 로봇을 사용할 수 없는 동안에도 생성기 출력만 확인하고 멈추지 않는다. Pepsi Light upside-down stable pose와 Inspire left hand를 대상으로 BODex 후보를 새로 생성하고, 독립 intrinsic 평가, xArm6·connector 배치, full-path portfolio, full-yaw context atlas, synchronized event trajectory까지 checksummed source chain으로 연결했다. 이후 “학습보다 실제 inference demo를 우선하라”는 연구 방향과 “충돌을 어떻게 걸렀고 cuRobo를 왜 사용하지 않는가”라는 검토 의견에 맞춰, full-command dynamics와 resident GPU collision 경계를 다시 감사했다. 결과는 진단 자료이며 measured stable pose, 승인 protocol, connector 계측과 실제 dynamic lifecycle CUDA kernel이 없으므로 실행 권한은 부여하지 않았다.

환경과 목표

이전 연구 환경을 사용할 수 없게 되어 RTX 3090 24 GB worker를 별도 프로젝트 영역으로 구성했다. 시스템 driver가 지원하는 범위 안에서 Python 3.10, Torch 2.5.1+CUDA 12.1, CUDA toolkit 12.1.105, NumPy 1.26.4, SciPy 1.13.1, trimesh 4.8.3, Warp 1.6.2를 고정했다. BODex 환경과 planning·HPP-FCL 환경을 분리해 한쪽의 native dependency 변경이 다른 쪽을 암묵적으로 바꾸지 않게 했다.

CUDA tensor 연산, Coal wrapper와 다섯 cuRobo extension import를 같은 환경에서 통과시켰다. 이 검증은 BODex 생성 runtime의 준비 상태를 뜻할 뿐, cuRobo moving full-command latency나 grasp 성공률을 증명하지 않는다.

연구 방향을 inference demo 중심으로 재정의

교수님 의견에 따라 AutoDex training과 데이터 수집은 주 경로에서 분리했다. Runtime은 이미 검증된 grasp library, AutoDex 계열 산출물, 또는 별도 grasp generator 중 어느 공급자에서든 object-relative grasp를 받을 수 있다. 현재 object·stable tabletop pose·planar 위치·초기 yaw가 주어지면 compatible grasp와 resident path family를 조회하고, coverage가 없을 때만 offline synthesis request를 발행한다. 온라인 제어 주기에서 grasp 생성이나 재학습을 시작하지 않는다.

사수님 의견은 두 개의 독립 질문으로 처리했다. 첫째, planner collision은 GPU에서 빠르게 판정하되 exact mesh HPP-FCL을 offline oracle로 유지한다. 둘째, MuJoCo와 Isaac Sim은 같은 source-bound command의 tracking, contact, attachment, release, bin containment를 검증하는 backend이며 planner 승인 boolean을 대신하지 않는다. Isaac Gym Preview 계열은 신규 목표로 두지 않는다.

결정: 모든 코드를 기계적으로 CUDA로 옮기지 않는다. Batched IK, trajectory optimization, self/static-world collision, time-indexed object collision과 candidate reduction은 resident GPU worker에 둔다. Timestamp causality, encoder join, atlas lookup, deadline·cancel state machine과 robot transport는 CPU에 남긴다. 작은 분기 작업을 GPU로 옮기면 kernel launch와 synchronization이 오히려 latency를 늘린다.

후보 생성과 독립 선별

과거 후보 8개는 현행 독립 기준에서 모두 탈락했으므로 재사용하지 않았다. 새 immutable run은 64 seeds를 약 29.6초에 생성했다. Provider-native success는 0/64였지만 이를 acceptance로 사용하지 않고 모든 seed를 unvalidated_proposal로 import했다. 독립 geometry screen에서는 4개가 남았고 task-wrench quality는 약 0.0125~0.0944였다.

로봇 배치와 full-path 선택

로봇 모델은 xArm6 arm, Inspire left hand와 두 CAD로 정의한 paired connector를 사용했다. Arm tip에서 hand root까지의 transform은 명시적 manifest로 결속했지만 z offset 47.5 mm는 아직 계측 전 값이다. 네 grasp를 3개 intercept horizon에 배치한 nominal endpoint 평가는 12/12를 통과했다.

Shortlist는 hard gate를 모두 통과한 네 후보만 유지하고 normalized maximin으로 정렬했다. 이후 HPP-FCL reference planner로 네 candidate path를 비교하고 한 candidate를 full-frame refinement했다. 선택된 diagnostic은 4.6초 intercept에서 전체 71 frame을 통과했다. Coarse search는 약 304.0초, refinement는 약 71.6초가 걸렸으므로 이 CPU reference planner를 online loop에 둘 수는 없다.

실시간 방향: HPP-FCL은 offline oracle과 회귀 검증에 남긴다. 첫 demo는 full-yaw grasp atlas와 bounded path family를 조회하고, cuRobo GPU가 same-command collision admission을 담당한다. Atlas 밖이지만 지원 가능한 context에 대해서만 이후 한 번의 bounded arm-prefix warm start를 추가한다. CPU reference planner나 무제한 online fallback은 두지 않는다.

Full-yaw atlas

같은 4 grasps를 30° 간격 12 yaw와 3 horizons, 총 36 context에서 다시 평가했다. 0~120°와 330°는 12/12, 300°는 3/12가 feasible했다. 150~270°는 모두 pregrasp IK에서 탈락했다. 144 grasp-context 조합 중 75개가 허용되었지만, yaw uncertainty까지 요구하는 10,000회 query의 accepted 비율은 43.95%로 더 낮았다.

Lookup 자체는 충분히 빠르지만 coverage는 부족하다. 이 실패를 IK threshold 완화로 숨기지 않는다. 반대쪽 접근이나 다른 손 자세를 제공하는 추가 grasp를 생성하고 같은 intrinsic·deployment·path gate를 통과시켜야 한다. Runtime은 관측 yaw와 uncertainty가 atlas support 밖이면 fail-closed한다.

Event-native trajectory

선택 portfolio와 atlas를 직접 join하는 compiler를 추가했다. Compiler는 두 source set을 각각 checksum 검증한 뒤 grasp의 pose, joint order, pregrasp, closure와 object-relative semantics가 같은지 비교한다. 서로 다른 evaluation에서 만들어진 evidence 파일 경로와 digest까지 같다고 요구하지는 않는다. Operational semantics는 같아야 하고 provenance는 양쪽에서 독립적으로 닫혀야 한다.

최종 event request는 71개 arm-hand waypoint와 6개 사건을 포함한다. hand_close_start 4.1초, first_contact 4.4초, close_complete와 attach 4.6초, release_open 7.2초, detach 7.233초다. Artifact SHA-256은 8f3869ef3d01…137a4f1이며 source revision 3f39e71에서 재현했다.

cuRobo를 사용하지 않은 것이 아니라 역할을 분리했다

현재 arm-prefix producer는 cuRobo를 사용하지만 self collision을 끈 world-only optimizer다. 이유는 self collision이 중요하지 않아서가 아니다. Producer와 동일한 conservative b512 proxy를 1,673개 holdout state에 적용하면 모든 state에서 self cost가 양수여서, 그 모델을 그대로 켠 optimizer는 모든 solve를 infeasible로 만든다. 이를 broad ignore pair로 숨기지 않고 model-qualification failure로 기록했다.

Self/static-world admission은 별도의 v28 xArm6·Inspire validator가 담당한다. 독립 1,522-state holdout에서 mesh oracle false negative는 0, oracle-clear 937개 중 false positive는 37개(3.95%)였다. World-only b512 proxy도 별도 1,673-state corpus에서 false negative 0, clear 1,113개 중 false positive 51개(4.58%)였다. 두 결과의 scope를 합쳐 하나의 “완전한 collision checker”라고 부르지 않는다.

따라서 1.449 ms 결과를 moving grasp 전체의 10 ms 보장으로 확대 해석할 수 없다. 실제 온라인 권한에는 translating object, named contact transition, attached object, release envelope, dynamics, abort와 controller handoff가 같은 command와 lifecycle digest로 연결되어야 한다.

Full-command 재검증에서 발견한 dynamics 오류

Nominal과 10개 correction boundary cell은 HPP-FCL geometry/contact 검사에서 11/11을 통과했다. 그러나 같은 command를 dynamics까지 다시 평가하자 11개 모두 실패했다. Position margin은 약 +0.270으로 통과했지만 velocity, acceleration, jerk margin은 각각 약 -6.998, -15.371, -17.693이었다.

원인은 로봇 성능 자체가 아니라 trajectory 표현이었다. 30 Hz dense IK waypoint를 playback request에 넣었고, playback은 인접한 모든 점을 서로 독립적인 rest-to-rest minimum-jerk segment로 해석했다. 연속적인 geometry sample을 실행 가능한 q/qd/qdd command로 잘못 취급한 것이다.

이를 보정 계수나 fallback으로 덮지 않았다. Intercept candidate가 playback과 collision 검증으로 넘어가기 전에 full-request dynamics backend가 전체 request를 source-bound 방식으로 평가하도록 변경했다. 실패한 candidate는 joint_dynamics로 즉시 거절되고 request/playback evidence를 생성하지 않는다. 다음 compiler는 cuRobo가 만든 derivative-aware arm prefix를 event-bound hand suffix와 결합해야 한다.

Source-bound cuRobo runtime gate

이미 warm-up된 resident backend를 위한 production boundary를 추가했다. Compact result는 generation, path family, exact event trajectory digest, collision lifecycle digest, collision-geometry bundle digest, 검사 interval, collision configuration, backend family/version/source revision, kernel, required operations, device residency, CUDA graph, preallocated buffer, host-device transfer와 deadline을 모두 결속한다. Backend exception, 오래된 lifecycle 또는 geometry bundle, operation 누락, source mismatch, filesystem transport나 deadline miss는 모두 fail-closed하며 HPP-FCL CPU fallback을 호출하지 않는다.

Online assessment schema도 lifecycle과 bundle digest를 보존한다. Backend가 실행되지 않은 unavailable_fail_closed 결과는 두 digest를 모두 null로 강제한다. 즉 검사하지 않은 payload를 검사한 것처럼 기록할 수 없다. 다만 이것은 backend adapter와 정책 경계이지 time-indexed lifecycle CUDA kernel 자체는 아니다.

실제 collision geometry payload 결속

기존 lifecycle은 호출자가 전달한 SHA-256 문자열만 저장해 어떤 bytes를 GPU가 검사해야 하는지 역추적할 수 없었다. 이를 schema 2.0으로 교체하고 이전 hash-only schema fallback은 두지 않았다. 새 ResidentCollisionGeometryBundle은 object manifest, 실제 collision GLB, object-frame attached sphere JSON, 선택적 release envelope JSON을 각각 상대경로와 SHA-256으로 결속한다. Full-command loader는 nested source를 다시 읽어 manifest scale·transform, mesh digest, sphere source mesh digest, lifecycle component digest와 workcell obstacle identity까지 비교한다.

실제 Pepsi source의 collision GLB SHA-256은 6605184c5cf3985fba8fa8d8d4146a5a17b293ecdfc52a348e62cafcdb47af86이다. Object-frame bounds는 대략 x ±34.05 mm, y ±61.00 mm, z ±33.92 mm였고 가장 긴 y축을 6개 동일 slab으로 나눴다. 각 sphere 반경은 1 mm padding을 포함해 36.6024 mm이며, mesh vertex 최대 coverage residual은 -1.0850 mm였다. Generator는 vertex만 감싸는 것이 아니라 각 slab의 전체 bounding cylinder를 외접하므로 빈 표면 샘플 때문에 내부 영역이 빠지지 않는다. Sphere artifact SHA-256은 7a813d784e4ad14e05d2d33fd85bea4df392d4f2a6fffb7cddd080fbe9c2fff7이다.

권한 제한: 이 sphere set은 candidate_outer_collision_proxy이고 online_collision_authority=false다. 실제 pick-and-drop command가 아직 derivative-aware full lifecycle로 materialize되지 않았기 때문에 detach pose, release velocity, gravity duration과 bin containment에 종속되는 release envelope는 만들지 않았다. 임의 박스를 넣어 complete bundle이라고 주장하는 것보다 이 blocker를 명시적으로 유지하는 편이 타당하다.

검증 범위와 남은 차단 조건

Geometry bundle, lifecycle, full-command source join, Viser/MuJoCo scenario, runtime cuRobo gate와 controller handoff를 함께 실행한 직접 관련 suite는 GPU worker에서 81개가 통과했고 선택 MuJoCo 환경 test 1개만 skip되었다. 타임라인 exact-sample 검증 중에는 releasing 상태를 attached로 다시 추론하는 별도 버그를 발견했다. Exact sample은 선언 상태를 보존하고 비정확 시각만 retention_end부터 detach까지 releasing으로 보간하도록 수정했다. OpenCV ABI 수정 후 저장소 전체 suite는 852개가 통과했고 선택 backend test 14개가 skip되었다. Online assessment round-trip은 exact lifecycle/bundle digest를 보존했고 stale bundle은 거부했으며 backend exception은 두 digest가 없는 typed rejection으로 남았다. 이 결과는 actual asset 기반 offline diagnostic과 fail-closed runtime edge가 닫혔다는 뜻이지 실제 grasp 성공이나 controller-ready trajectory가 생겼다는 뜻은 아니다.

  1. 현재 11-cell geometry samples를 폐기하는 대신 참고 자료로만 남기고, nonzero derivative를 보존하는 cuRobo q/qd/qdd command로 다시 compile해야 한다.
  2. 실제 Pepsi world mesh와 object-frame attached spheres는 결속했다. Derivative-aware drop command에서 detach state와 release motion을 확정한 뒤 conservative release envelope를 만들고 complete pick-and-drop bundle을 materialize해야 한다.
  3. 세 collision phase를 fixed-shape buffer와 CUDA graph로 구현하고, graph replay·preallocation을 켠 same-command full-task benchmark에서 deadline miss 0을 입증해야 한다.
  4. 그 exact command로만 MuJoCo measured rollout과 actual-asset Viser 1.0x 반복 재생을 만들어야 한다. 별도 animation을 실행 증거로 재분류하지 않는다.
  5. Upside-down stable pose, task protocol과 connector bolt-hole transform을 실물 계측·승인하고, hardware가 돌아오면 multi-camera pose·yaw, belt plane·axis·speed·latency, robot-base와 controller timing을 검증해야 한다.

Arbitrary geometry hash 제거와 typed payload bundle은 완료했다. 다음 구현 단위는 derivative-aware arm-prefix compiler, 그 exact detach/release state에서 파생한 envelope, 그리고 bundle을 실제 device tensor로 upload해 소비하는 세 fixed-shape cuRobo lifecycle pass다. 첫 demo는 atlas hit만 허용하고 이 gate를 매 observation generation마다 실행한다. Full warm start는 이 경로가 target GPU에서 안정된 뒤 별도 50 ms policy로 추가한다.

Correction cell production gate, Resident full-command materialization, cuRobo producer·validator 측정에서 후속 경계를 관리한다.

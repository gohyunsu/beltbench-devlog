프로젝트이슈
ISSUE-009 · 2026-08-06 · 진행 중

실제 로봇 없이 planning 결과와 실패 원인을 Viser에서 검증한다.

현재 가능한 연구 범위를 offline planning과 visualization까지로 제한했다. 목표는 conveyor animation을 빠르게 만드는 것이 아니라, 저장된 scene과 plan만으로 grasp 후보가 왜 가능하거나 불가능한지 재현하고 검사할 수 있는 기반을 만드는 것이다.

현재 구현에서 확인한 한계

기존 xArm trajectory는 URDF의 여섯 revolute joint를 읽어 numerical IK와 cubic interpolation을 수행한다. joint limit과 velocity는 확인하지만 fixed joint를 포함한 전체 robot geometry, self-collision, table·conveyor collision, 여러 grasp 후보 비교, object motion과 intercept time은 다루지 않는다. 기존 visualizer는 최종 상태와 tool path를 GLB로 내보내므로 공유에는 적합하지만 timeline과 실패 진단을 대화형으로 확인할 수 없다.

설계 원칙

Artifact가 기준이다

scene, request, plan, validation을 versioned JSON으로 먼저 저장한다. planner와 Viser는 같은 artifact를 사용하며 UI가 pose나 trajectory를 임의로 다시 계산하지 않는다.

Viewer는 계산하지 않는다

Viser는 robot·hand·object·conveyor, candidate, trajectory, collision 진단을 표시할 뿐이다. FK, IK, collision, candidate ranking과 timing은 planning module이 담당한다.

검증기는 planner와 독립적이다

planner가 성공을 선언해도 별도 validator가 joint, velocity, acceleration, clearance와 timing margin을 다시 계산한다. validator를 통과하지 못한 plan은 항상 execution-blocked다.

실환경 입력은 adapter다

지금은 synthetic object state를 사용한다. 이후 FoundationPose·GoTrack 결과는 같은 ObjectState contract로 변환하므로 planning과 Viser 내부를 바꾸지 않는다.

구현 단계

  1. P0 · fixture와 contract: frame, unit, asset checksum을 가진 planning scene과 request/result schema를 고정하고 synthetic fixture를 만든다.
  2. P1 · Viser scene: robot link, Inspire hand, object, conveyor, collision proxy와 좌표계를 표시한다. joint slider 결과와 Pinocchio FK가 일치하는지 검사한다.
  3. P2 · static grasp feasibility: 여러 object-frame grasp를 workspace, approach, multi-seed IK, joint limit, self/environment collision 순서로 거르고 rejection reason을 색으로 표시한다.
  4. P3 · collision-aware motion: start, pre-grasp, grasp, lift, retreat를 계획하고 time parameterization 후 더 촘촘한 sample로 독립 재검증한다.
  5. P4 · plan playback: play/pause, scrubber, phase 이동, tool/object path, minimum-clearance pair, score와 timing을 표시하고 두 plan을 비교한다.
  6. P5 · moving interception: 일정 속도 object의 미래 pose와 후보 intercept time을 탐색하고 latency를 포함한 도착 가능성과 dynamic collision을 검사한다.
  7. P6 · 반복 평가: object pose, belt speed, robot start, latency, obstacle, grasp set을 seeded matrix로 실행해 feasibility, failure taxonomy, planning time, clearance와 timing margin을 집계한다.

도구의 역할

Pinocchio는 robot kinematics와 geometry model, hpp-fcl은 collision과 distance query에 사용한다. sampling planner와 time parameterizer는 교체 가능한 interface 뒤에 둔다. Viser는 interactive diagnostic frontend로만 사용하고 기존 GLB export는 정적 공유 수단으로 유지한다. CPU core, offline planning, GoTrack GPU 환경은 서로 분리해 pinning한다.

첫 번째 완료 기준

첫 milestone: 저장된 static scene 하나를 Viser에서 열고, 모든 grasp 후보의 accepted/rejected 상태와 이유를 확인하며, 같은 결과를 독립 validation artifact로 재현한다.

그 다음에만 collision-aware trajectory와 playback을 추가한다. 움직이는 object는 static planning의 FK·collision·timing 검증이 끝난 뒤 도입해 원인 혼합을 방지한다. 현재 단계는 계획 수립이며 Pinocchio, hpp-fcl, Viser dependency 설치 smoke와 license 확인은 아직 수행하지 않았다.

2026-08-06 · P0/P1 첫 vertical slice

PlanningScene, entity, trajectory frame을 versioned JSON으로 정의하고 arm, hand, target, distractor, conveyor가 반드시 존재하는지 검증하도록 구현했다. synthetic selective-pick fixture는 target만 들어 올려 destination으로 옮기고 다른 object는 belt를 따라 계속 이동한다. live Viser에는 play/pause, timeline, speed와 arm·hand·target·other objects·conveyor·environment·trajectory·frame toggle을 추가했다.

같은 scene adapter를 live viewer와 exporter가 공유한다. 121 frame, 8초 trajectory를 JSON으로 저장하고 Viser serializer로 timeline이 포함된 self-contained HTML animation을 만들었다. UI는 FK나 trajectory를 다시 계산하지 않고 저장된 frame pose만 표시한다.

구현 중 발생한 문제

가변 link처럼 보이는 fixture

초기 arm pose 계산은 elbow를 wrist 위치의 비율로 정해 link 길이가 trajectory 동안 달라질 수 있었다. 실제 planning과 혼동되는 잘못된 표현이므로 고정 길이 two-link 기하를 도입하고 모든 wrist waypoint에 reachability guard를 적용했다.

reachability 실패

첫 artifact 생성에서 최대 wrist 거리가 설정 reach를 약간 초과해 즉시 실패했다. guard를 우회하지 않고 link 길이와 workcell fixture를 함께 검토해 모든 waypoint가 명시적 reach 안에 들도록 수정했다.

회전 경고

한 vector만으로 link orientation을 맞추자 roll이 유일하지 않다는 SciPy 경고가 발생했다. local Z를 link 방향으로 보내는 최소 회전을 axis-angle로 직접 계산해 결정적 orientation으로 교체했다.

중복 가능성

live viewer와 animation exporter가 scene 생성 코드를 각각 가지면 display가 달라질 수 있다. 공통 Viser scene adapter를 만들고 두 command가 같은 entity handle과 frame 적용 함수를 사용하도록 정리했다.

검증 결과와 경계

로컬에 별도 Python 3.10 visualization 환경과 Viser 1.0.29를 생성했다. 신규 planning contract·playback test 5개가 통과했고, GPU 서버에서는 기존 test와 합쳐 23개가 통과했다. live server의 HTTP 응답과 121-frame standalone animation 생성을 확인했다.

아직 실행 불가: 현재 arm과 hand는 contract·playback 검증을 위한 schematic geometry다. xArm URDF FK, 실제 Inspire mesh, grasp candidate IK, self/environment collision은 아직 연결하지 않았다. artifact의 execution-blocked reason에 이 경계를 기록한다.

2026-08-06 · 외부 robot asset 연결

특정 checkout 경로를 코드에 넣지 않고 arm URDF, hand URDF, arm tip link, hand root link, world transform과 mount transform을 별도 manifest로 정의했다. 실제 xArm mesh와 Inspire left-hand mesh를 Viser에 로드해 각각 6개의 independent joint control을 확인했고, mimic finger joint는 URDF 정의에 따라 확장된다. arm joint가 바뀔 때 arm tip FK로 hand root frame도 함께 갱신한다.

첫 실행에서 xArm 6축과 Inspire 6축이 모두 로드되고 local Viser endpoint가 정상 응답했다. joint lower limit이 정확히 0인 경우 일반적인 or 표현을 사용하면 fallback 값으로 바뀔 수 있는 문제를 코드 검토에서 발견해, None만 대체하도록 수정했다.

검증 경계: 현재 local manifest의 arm-tip-to-hand-root 값은 표시 경로 검증용 identity다. 실제 mount 측정값, collision geometry 승인, IK와 trajectory validation 전에는 execution에 사용할 수 없다.

2026-08-06 · 실제 URDF joint trajectory playback

planner와 executor가 함께 사용할 수 있도록 arm·hand joint 상태를 이름 기반으로 저장하는 versioned trajectory contract를 추가했다. frame마다 time, phase, arm joints, hand joints를 기록하고 시간 증가, joint set 불변, finite radian 값과 execution-block reason을 검증한다.

URDF joint limit에서 안전한 표시용 121-frame fixture를 생성하고 기존 xArm·Inspire inspector에 timeline, play/pause, speed와 phase 표시를 연결했다. trajectory joint 이름이 로드된 URDF와 다르면 표시 전에 거부한다. playback 중 arm configuration, Inspire mimic configuration, arm-tip FK와 hand mount가 같은 frame에서 갱신된다.

로컬 포트 8092에서 xArm 6축과 Inspire 6축 playback startup 및 HTTP 응답을 확인했다. 이 fixture는 IK와 collision이 없는 UI 검증이므로 실행 차단 상태를 유지한다.

2026-08-06 · playback 코드 재검토

전체 연결을 다시 검토해 외부 trajectory가 URDF joint 이름만 맞으면 position limit를 넘더라도 표시될 수 있는 누락을 발견했다. 모든 frame을 URDF lower·upper limit와 다시 대조하는 독립 validator를 추가하고 limit 초과 regression test를 작성했다.

trajectory playback 중 manual joint slider가 활성화되어 두 입력 source가 경쟁할 수 있었으므로 playback mode에서는 slider를 비활성화했다. timeline callback마다 timestamp 배열을 다시 만들던 불필요한 처리도 초기화 시 한 번만 계산하도록 정리했다. 수정 후 로컬 관련 테스트 11개와 GPU 서버 전체 테스트 29개가 통과했다.

2026-08-06 · 특정 robot·hand 의존성 재검토

core PlanningScene이 arm, hand, target, distractor, conveyor category를 모두 요구하고 live viewer도 같은 이름으로 toggle과 path를 만들고 있었다. 이는 synthetic demo의 구체적 구성을 공통 계약으로 잘못 끌어올린 것이다. entity category를 scene-safe한 개방형 문자열로 바꾸고, viewer는 실제 scene에 존재하는 category와 움직이는 entity를 탐색해 toggle과 path를 자동 생성하도록 리팩터링했다.

hand demo도 모든 관절이 0에서 양의 upper 방향으로 닫힌다고 가정했다. 각 URDF joint의 lower·upper 안에서 0에 가장 가까운 neutral을 구하고 neutral에서 upper 방향으로 이동하도록 수정해 음수 범위나 0을 포함하지 않는 joint에도 적용 가능하게 했다. 외부 trajectory는 표시 전 모든 frame을 URDF position limit와 다시 대조한다.

구체적인 xArm·Inspire 이름과 conveyor 치수는 검증 fixture와 local manifest에만 남는다. 공통 contract, Viser adapter, trajectory validator에는 joint 수, joint 이름, entity category 목록을 하드코딩하지 않는다. 관련 로컬 테스트 13개와 서버 전체 테스트 31개가 통과했다.

모듈 재구축 감사와 초기 pose·tracking 연결이 이 계획의 선행 기록이다.

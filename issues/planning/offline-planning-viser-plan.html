ISSUE-009 · 2026-08-07 · robust reference 검증

실제 로봇 없이 planning 결과와 실패 원인을 Viser에서 검증한다.

현재 가능한 연구 범위를 offline planning과 visualization까지로 제한했다. 목표는 conveyor animation을 빠르게 만드는 것이 아니라, 저장된 scene과 plan만으로 grasp 후보가 왜 가능하거나 불가능한지 재현하고 검사할 수 있는 기반을 만드는 것이다.

현재 구현에서 확인한 한계

기존 xArm trajectory는 URDF의 여섯 revolute joint를 읽어 numerical IK와 cubic interpolation을 수행한다. joint limit과 velocity는 확인하지만 fixed joint를 포함한 전체 robot geometry, self-collision, table·conveyor collision, 여러 grasp 후보 비교, object motion과 intercept time은 다루지 않는다. 기존 visualizer는 최종 상태와 tool path를 GLB로 내보내므로 공유에는 적합하지만 timeline과 실패 진단을 대화형으로 확인할 수 없다.

설계 원칙

Artifact가 기준이다

scene, request, plan, validation을 versioned JSON으로 먼저 저장한다. planner와 Viser는 같은 artifact를 사용하며 UI가 pose나 trajectory를 임의로 다시 계산하지 않는다.

Viewer는 계산하지 않는다

Viser는 robot·hand·object·conveyor, candidate, trajectory, collision 진단을 표시할 뿐이다. FK, IK, collision, candidate ranking과 timing은 planning module이 담당한다.

검증기는 planner와 독립적이다

planner가 성공을 선언해도 별도 validator가 joint, velocity, acceleration, clearance와 timing margin을 다시 계산한다. validator를 통과하지 못한 plan은 항상 execution-blocked다.

실환경 입력은 adapter다

지금은 synthetic object state를 사용한다. 이후 FoundationPose·GoTrack 결과는 같은 ObjectState contract로 변환하므로 planning과 Viser 내부를 바꾸지 않는다.

구현 단계

  1. P0 · fixture와 contract: frame, unit, asset checksum을 가진 planning scene과 request/result schema를 고정하고 synthetic fixture를 만든다.
  2. P1 · Viser scene: robot link, Inspire hand, object, conveyor, collision proxy와 좌표계를 표시한다. joint slider 결과와 Pinocchio FK가 일치하는지 검사한다.
  3. P2 · static grasp feasibility: 여러 object-frame grasp를 workspace, approach, multi-seed IK, joint limit, self/environment collision 순서로 거르고 rejection reason을 색으로 표시한다.
  4. P3 · collision-aware motion: start, pre-grasp, grasp, lift, retreat를 계획하고 time parameterization 후 더 촘촘한 sample로 독립 재검증한다.
  5. P4 · plan playback: play/pause, scrubber, phase 이동, tool/object path, minimum-clearance pair, score와 timing을 표시하고 두 plan을 비교한다.
  6. P5 · moving interception: 일정 속도 object의 미래 pose와 후보 intercept time을 탐색하고 latency를 포함한 도착 가능성과 dynamic collision을 검사한다.
  7. P6 · 반복 평가: object pose, belt speed, robot start, latency, obstacle, grasp set을 seeded matrix로 실행해 feasibility, failure taxonomy, planning time, clearance와 timing margin을 집계한다.

도구의 역할

Pinocchio는 robot kinematics와 geometry model, hpp-fcl은 collision과 distance query에 사용한다. sampling planner와 time parameterizer는 교체 가능한 interface 뒤에 둔다. Viser는 interactive diagnostic frontend로만 사용하고 기존 GLB export는 정적 공유 수단으로 유지한다. CPU core, offline planning, GoTrack GPU 환경은 서로 분리해 pinning한다.

첫 번째 완료 기준

첫 milestone: 저장된 static scene 하나를 Viser에서 열고, 모든 grasp 후보의 accepted/rejected 상태와 이유를 확인하며, 같은 결과를 독립 validation artifact로 재현한다.

그 다음에만 collision-aware trajectory와 playback을 추가한다. 움직이는 object는 static planning의 FK·collision·timing 검증이 끝난 뒤 도입해 원인 혼합을 방지한다. 현재 단계는 계획 수립이며 Pinocchio, hpp-fcl, Viser dependency 설치 smoke와 license 확인은 아직 수행하지 않았다.

2026-08-06 · P0/P1 첫 vertical slice

PlanningScene, entity, trajectory frame을 versioned JSON으로 정의하고 arm, hand, target, distractor, conveyor가 반드시 존재하는지 검증하도록 구현했다. synthetic selective-pick fixture는 target만 들어 올려 destination으로 옮기고 다른 object는 belt를 따라 계속 이동한다. live Viser에는 play/pause, timeline, speed와 arm·hand·target·other objects·conveyor·environment·trajectory·frame toggle을 추가했다.

같은 scene adapter를 live viewer와 exporter가 공유한다. 121 frame, 8초 trajectory를 JSON으로 저장하고 Viser serializer로 timeline이 포함된 self-contained HTML animation을 만들었다. UI는 FK나 trajectory를 다시 계산하지 않고 저장된 frame pose만 표시한다.

구현 중 발생한 문제

가변 link처럼 보이는 fixture

초기 arm pose 계산은 elbow를 wrist 위치의 비율로 정해 link 길이가 trajectory 동안 달라질 수 있었다. 실제 planning과 혼동되는 잘못된 표현이므로 고정 길이 two-link 기하를 도입하고 모든 wrist waypoint에 reachability guard를 적용했다.

reachability 실패

첫 artifact 생성에서 최대 wrist 거리가 설정 reach를 약간 초과해 즉시 실패했다. guard를 우회하지 않고 link 길이와 workcell fixture를 함께 검토해 모든 waypoint가 명시적 reach 안에 들도록 수정했다.

회전 경고

한 vector만으로 link orientation을 맞추자 roll이 유일하지 않다는 SciPy 경고가 발생했다. local Z를 link 방향으로 보내는 최소 회전을 axis-angle로 직접 계산해 결정적 orientation으로 교체했다.

중복 가능성

live viewer와 animation exporter가 scene 생성 코드를 각각 가지면 display가 달라질 수 있다. 공통 Viser scene adapter를 만들고 두 command가 같은 entity handle과 frame 적용 함수를 사용하도록 정리했다.

검증 결과와 경계

로컬에 별도 Python 3.10 visualization 환경과 Viser 1.0.29를 생성했다. 신규 planning contract·playback test 5개가 통과했고, GPU 서버에서는 기존 test와 합쳐 23개가 통과했다. live server의 HTTP 응답과 121-frame standalone animation 생성을 확인했다.

아직 실행 불가: 현재 arm과 hand는 contract·playback 검증을 위한 schematic geometry다. xArm URDF FK, 실제 Inspire mesh, grasp candidate IK, self/environment collision은 아직 연결하지 않았다. artifact의 execution-blocked reason에 이 경계를 기록한다.

2026-08-06 · 외부 robot asset 연결

특정 checkout 경로를 코드에 넣지 않고 arm URDF, hand URDF, arm tip link, hand root link, world transform과 mount transform을 별도 manifest로 정의했다. 실제 xArm mesh와 Inspire left-hand mesh를 Viser에 로드해 각각 6개의 independent joint control을 확인했고, mimic finger joint는 URDF 정의에 따라 확장된다. arm joint가 바뀔 때 arm tip FK로 hand root frame도 함께 갱신한다.

첫 실행에서 xArm 6축과 Inspire 6축이 모두 로드되고 local Viser endpoint가 정상 응답했다. joint lower limit이 정확히 0인 경우 일반적인 or 표현을 사용하면 fallback 값으로 바뀔 수 있는 문제를 코드 검토에서 발견해, None만 대체하도록 수정했다.

검증 경계: 현재 local manifest의 arm-tip-to-hand-root 값은 표시 경로 검증용 identity다. 실제 mount 측정값, collision geometry 승인, IK와 trajectory validation 전에는 execution에 사용할 수 없다.

2026-08-06 · 실제 URDF joint trajectory playback

planner와 executor가 함께 사용할 수 있도록 arm·hand joint 상태를 이름 기반으로 저장하는 versioned trajectory contract를 추가했다. frame마다 time, phase, arm joints, hand joints를 기록하고 시간 증가, joint set 불변, finite radian 값과 execution-block reason을 검증한다.

URDF joint limit에서 안전한 표시용 121-frame fixture를 생성하고 기존 xArm·Inspire inspector에 timeline, play/pause, speed와 phase 표시를 연결했다. trajectory joint 이름이 로드된 URDF와 다르면 표시 전에 거부한다. playback 중 arm configuration, Inspire mimic configuration, arm-tip FK와 hand mount가 같은 frame에서 갱신된다.

로컬 포트 8092에서 xArm 6축과 Inspire 6축 playback startup 및 HTTP 응답을 확인했다. 이 fixture는 IK와 collision이 없는 UI 검증이므로 실행 차단 상태를 유지한다.

2026-08-06 · playback 코드 재검토

전체 연결을 다시 검토해 외부 trajectory가 URDF joint 이름만 맞으면 position limit를 넘더라도 표시될 수 있는 누락을 발견했다. 모든 frame을 URDF lower·upper limit와 다시 대조하는 독립 validator를 추가하고 limit 초과 regression test를 작성했다.

trajectory playback 중 manual joint slider가 활성화되어 두 입력 source가 경쟁할 수 있었으므로 playback mode에서는 slider를 비활성화했다. timeline callback마다 timestamp 배열을 다시 만들던 불필요한 처리도 초기화 시 한 번만 계산하도록 정리했다. 수정 후 로컬 관련 테스트 11개와 GPU 서버 전체 테스트 29개가 통과했다.

2026-08-06 · 특정 robot·hand 의존성 재검토

core PlanningScene이 arm, hand, target, distractor, conveyor category를 모두 요구하고 live viewer도 같은 이름으로 toggle과 path를 만들고 있었다. 이는 synthetic demo의 구체적 구성을 공통 계약으로 잘못 끌어올린 것이다. entity category를 scene-safe한 개방형 문자열로 바꾸고, viewer는 실제 scene에 존재하는 category와 움직이는 entity를 탐색해 toggle과 path를 자동 생성하도록 리팩터링했다.

hand demo도 모든 관절이 0에서 양의 upper 방향으로 닫힌다고 가정했다. 각 URDF joint의 lower·upper 안에서 0에 가장 가까운 neutral을 구하고 neutral에서 upper 방향으로 이동하도록 수정해 음수 범위나 0을 포함하지 않는 joint에도 적용 가능하게 했다. 외부 trajectory는 표시 전 모든 frame을 URDF position limit와 다시 대조한다.

구체적인 xArm·Inspire 이름과 conveyor 치수는 검증 fixture와 local manifest에만 남는다. 공통 contract, Viser adapter, trajectory validator에는 joint 수, joint 이름, entity category 목록을 하드코딩하지 않는다. 관련 로컬 테스트 13개와 서버 전체 테스트 31개가 통과했다.

2026-08-06 · P2 kinematic feasibility 경계

기존 xarm_trajectory.py에 기능을 더 붙이지 않고 공통 RobotModel과 SingleSeedIK interface를 만들었다. object frame grasp에서 pre-grasp와 grasp tool target을 구성하고, 여러 seed의 IK를 결정적으로 비교하며, 두 target이 모두 통과할 때만 kinematic_feasible로 기록한다. pre-grasp 실패와 grasp 실패는 후보별 attempt와 함께 구분해 저장한다.

IK 오차를 하나의 무차원 residual로 합치지 않고 translation metre와 rotation radian으로 분리했다. backend가 limit 밖 configuration, NaN 또는 예외를 반환해도 통과하지 못하며, 실패값은 JSON의 비표준 Infinity 대신 null로 저장한다. 이 결과는 collision clearance를 뜻하지 않으므로 valid나 executable이라는 이름을 사용하지 않았다.

Pinocchio adapter와 환경 문제

Conda solver 조기 종료

최초 환경 생성은 설정된 libmamba plugin을 찾지 못해 실제 환경 없이 종료됐다. CONDA_NO_PLUGINS=true 진단에서 원인을 확인하고 classic solver로 재실행했다. 생성이 늦게 완료된 뒤 Pinocchio 3.4.0, hpp-fcl 3.0.1, NumPy 1.26.4를 확인했다.

서버 pip 설치 중단

junjinyong 공용 Python에는 Pinocchio가 없었다. 임시 pip 설치는 binary wheel이 아니라 약 100MB source package와 build dependency를 받아 적합하지 않아 중단했다. source build fallback을 남기지 않고 conda-forge binary를 쓰는 별도 planning environment만 공식 경로로 유지했다.

private Git 인증 부재

서버 checkout은 GitHub credential이 없어 pull할 수 없었다. 로컬 main의 Git bundle을 전송하고 clean server tree를 fast-forward하여 소스 revision을 정확히 4448ad3으로 맞췄다.

테스트 skip 은폐 위험

초기 dependency guard가 넓은 ImportError를 잡으면 adapter 내부 import 오류도 package 부재처럼 skip될 수 있었다. Pinocchio module 존재만 먼저 검사하고, 존재할 때 adapter import 오류는 그대로 실패하도록 수정했다.

검증 결과와 다음 gate

로컬 beltbench-planning 환경에서 generic revolute·prismatic 2-joint URDF의 joint name, limit, FK와 reachable IK를 포함한 10개 테스트가 통과했다. junjinyong에서는 OpenCV가 격리된 기존 CPU 경로로 전체 41개 테스트가 통과했고, 공용 Python에 Pinocchio가 없어 adapter 전용 3개만 명시적으로 skip됐다. 두 결과를 합쳐 core 회귀와 실제 Pinocchio 수치 경로를 각각 검증했다.

아직 P2 완료가 아니다: 현재 결과는 robot-independent kinematic feasibility까지다. 다음 구현은 hpp-fcl self/environment collision, 후보 ranking, 독립 revalidation과 Viser rejection diagnostics이며, 이 gate 전에는 실제 robot 실행으로 연결하지 않는다.

2026-08-06 · hpp-fcl collision gate

pre-grasp와 grasp configuration 각각에 대해 explicit self-collision pair와 모든 robot-to-environment pair의 signed distance를 계산하는 CollisionChecker 경계를 추가했다. 결과는 clearance margin, 모든 geometry pair의 거리·판정, minimum pair를 저장한다. 하나라도 margin을 만족하지 못하면 최종 static evaluation은 실패하며, IK-only 결과는 계속 kinematic_feasible로만 남는다.

독립 validator는 minimum distance만 보지 않고 저장된 pair 집합 전체, pair별 거리·판정, margin과 minimum pair를 다시 계산한다. 한 pair의 결과라도 바뀌면 validation이 실패한다. infeasible IK 후보에는 collision checker를 호출하지 않아 존재하지 않는 configuration을 검사하는 fallback도 두지 않았다.

실제 xArm collision asset smoke

mesh package root 누락

첫 실제 URDF load는 xarm/meshes/base.obj를 찾지 못했다. parent directory를 탐색하는 fallback 대신 robot asset manifest에 package_directories를 필수 key로 추가하고 ParaDex rsc/robot root를 명시했다.

geometry 이름 불일치

URDF의 collision name이 그대로 유지될 것으로 예상했지만 Pinocchio는 link_base_0부터 link6_0까지 link 기반 이름을 생성했다. 실제 loader 결과를 확인하고 semantic config가 geometry sequence 전체를 고정하도록 했다.

model drift 방지

이름만 같은 변경 URDF가 semantic pair를 재사용하지 못하도록 외부 xArm URDF SHA-256도 config에 고정했다. checksum 또는 geometry 순서가 달라지면 planning 전에 즉시 실패한다.

실행 command import

파일 경로로 script를 실행하면 checkout root가 import path에 없어 실패했다. sys.path fallback을 추가하지 않고 새 planning command를 모두 python -m scripts... 형식으로 통일했다.

실제 xArm collision mesh 7개와 비인접 self pair 15개를 확인했다. neutral configuration에서 5 mm margin을 적용한 최소 거리는 link4_0–link6_0의 41.466 mm였고 clearance를 통과했다. 이 검사는 neutral state 하나의 asset smoke이며 trajectory clearance를 의미하지 않는다.

후보 ranking과 Viser rejection diagnostics

collision-feasible 후보만 grasp prior, minimum clearance(m), start→pre-grasp→grasp joint-range-normalized travel로 ranking한다. revolute와 prismatic joint를 같은 radian 단위로 오해하지 않도록 각 joint half range로 정규화한다. rejected 후보는 score 경쟁에서 제외하고 IK 또는 clearance 실패 이유를 그대로 보존한다.

StaticGraspDiagnostics artifact에 object pose, 후보 target, IK attempt, collision pair evidence, ranking과 execution block reason을 저장한다. Viser는 이 artifact만 읽어 accepted는 녹색, IK rejected는 빨간색, clearance rejected는 주황색으로 표시하며 세 그룹을 독립적으로 켜고 끈다. viewer는 IK, collision, ranking module을 import하지 않는다.

로컬 포트 8093에서 synthetic artifact를 로드해 HTTP 200을 확인했다. planning 환경의 collision·asset 관련 20개 테스트와 artifact·ranking·Viser 관련 16개 테스트가 통과했다. junjinyong revision 3cf0530에서는 전체 54개 테스트가 통과했고, 공용 Python에 Pinocchio가 없어 전용 5개만 명시적으로 skip됐다.

다음 gate: P2의 contract와 visualization은 연결됐지만 실제 BODex grasp set을 xArm+Inspire combined collision model에 적용하지 않았다. 다음 단계는 hand collision geometry, measured mount transform, conveyor/table obstacle 변환과 실제 후보 artifact를 연결한 뒤 P3 collision-aware motion으로 진행하는 것이다.

2026-08-06 · arm과 hand를 하나의 collision state로 결합

arm-only NumPy configuration에 hand 처리를 덧붙이지 않고 collision 입력을 이름 기반 RobotCollisionState로 교체했다. arm과 end-effector joint group을 분리하며 arm-only checker는 hand state가 들어오면 무시하지 않고 실패한다. static evaluator는 후보에 저장된 pre-grasp·grasp hand command를 각각 arm IK state와 결합해 두 상태를 모두 검사한다.

Inspire URDF는 6개 독립 command joint와 6개 mimic joint를 가지지만 Pinocchio는 full 12-joint model을 만든다. generic URDF adapter가 mimic source, multiplier, offset과 limit를 검증해 6-command state를 12-joint collision state로 확장한다. mimic joint를 hardware command처럼 직접 입력하면 거부한다.

combined model 구현 중 발견한 frame·policy 문제

Pinocchio joint 순서

실제 hand에서 Pinocchio tree traversal 순서와 URDF 선언 순서가 달라 첫 smoke가 중단됐다. 순서가 같다고 가정하지 않고 joint 이름 집합을 검증한 뒤 Pinocchio order로 명시적으로 재정렬했다.

hand root frame 가정

AutoDex grasp가 없을 때의 처리

grasp library는 object_id + stable_pose_id + end_effector_id + task capability의 exact match, support clearance, evidence status를 hard gate로 사용한다. 검증된 AutoDex grasp가 있으면 object-relative pose를 재사용할 수 있다. 없다면 online에서 임의 fallback을 만들지 않고 unsupported를 반환한 뒤 offline synthesis job을 생성한다.

synthesis는 접촉, force closure 또는 task quality, support clearance, approach, hand closure, IK, self/cross/environment collision을 확인하고 source와 evidence를 저장한다. static AutoDex 결과가 있다는 사실과 moving pick, drop_release, tabletop_release capability는 서로 다른 claim이다. provisional 후보는 필요한 검증과 review 후에만 validated library로 승격한다.

실시간성에 대한 냉정한 평가

현재 reference backend는 실시간이 아니다. 세 bin-drop 후보를 순차 multi-seed Pinocchio IK와 Python sampled collision로 검사하는 데 분 단위가 걸렸고, 301-frame full mesh validation도 분 단위였다. full validator는 regression/certification 용도이며 online loop에 넣어서는 안 된다.

실시간 backend는 같은 contract 아래 batched GPU planning, static workcell SDF, grasp/terminal IK seed cache, warm start, stale generation 취소, event 주변 adaptive densification을 사용해야 한다. perception부터 dispatch까지 p95 120 ms 이내를 목표로 측정하고 10–20 Hz로 rolling replan한다. hand closing과 arm motion time은 computation latency가 아니라 intercept deadline에서 별도로 빼야 한다.

후보 선택은 metre, joint coordinate, second, Jacobian 값을 임의 weighted sum으로 합치지 않는다. deadline, uncertainty-adjusted clearance, certified workspace boundary, normalized joint-limit, normalized singularity, prediction freshness를 각각 hard gate한 뒤 threshold-normalized 최소 여유가 가장 큰 후보를 선택하는 maximin rule을 구현하고 unit test했다. 이 시점의 intercept search에는 아직 legacy score가 남아 있었으며 다음 기록에서 schema 2.0으로 제거했다.

2026-08-07 · legacy intercept score를 schema 2.0 robust gate로 교체

기존 search는 nominal environment clearance, joint travel, intercept time에 임의 weight를 곱해 더했다. 서로 다른 단위의 값이므로 weight를 바꾸면 안전 근거 없이 선택이 바뀔 수 있고, pose covariance와 workspace boundary, singularity, latency evidence도 후보 판정에 연결되지 않았다. 기존 selector를 보정하지 않고 schema를 2.0으로 올려 legacy score field와 세 weight를 제거했다.

각 후보는 deadline slack, uncertainty-adjusted collision slack, Cartesian workspace-boundary margin, normalized joint-limit margin, normalized spatial-Jacobian singular value, prediction freshness, measured latency evidence를 독립적으로 저장한다. 하나라도 threshold를 통과하지 못하면 탈락하고, 통과 후보 중 threshold-normalized 최소 여유가 가장 큰 후보만 maximin으로 선택한다. tie-break는 deadline slack과 stable candidate ID뿐이다.

nominal collision 통과가 robust clearance를 뜻하지 않았다

관측한 증상

4.6, 4.8, 5.0초 후보는 모두 sampled collision gate를 통과했다. 그러나 최소 environment margin은 약 0.163 mm뿐이었다. 최소 쌍은 grasp phase의 end_effector/left_ring_1_0과 environment/conveyor-deck였다.

원인

combined checker의 environment clearance 5 mm에 대해 실제 거리는 약 5.163 mm였다. 기존 판정은 0보다 큰 차이만 확인해 calibration·pose prediction 오차가 들어갈 공간이 거의 없는 trajectory도 valid로 남겼다.

latency 목표값을 측정값처럼 사용하지 않는다

120 ms p95는 GPU online backend의 설계 목표이지 측정 결과가 아니다. 숫자가 config에 있다는 이유만으로 deadline gate가 통과하는 문제를 막기 위해 pipeline_latency_evidence_status를 추가했다. 현재 값은 provisional이며 이는 pipeline latency p95 is not measured라는 독립 hard failure다. backend별 반복 benchmark로 p95를 얻은 뒤에만 measured로 승격할 수 있다.

현재 Pinocchio/HPP-FCL CPU reference는 세 후보에 119.942초가 걸렸다. exact duplicate arm+hand state의 collision result만 재사용하는 cache를 넣기 전 같은 실행은 166.084초였다. 약 28% 감소했지만 둘 다 단일 local 관측이며 실시간 benchmark가 아니다. tolerance 기반 근사 cache나 stale 결과 fallback은 사용하지 않았다.

특정 arm 단위 가정을 제거했다

generic contract가 모든 joint 값을 radian으로 부르던 문제도 함께 수정했다. revolute는 radian, prismatic은 metre인 URDF SI coordinate를 그대로 유지하고, joint-limit margin과 trajectory travel은 각 joint half range로 정규화한다. Jacobian은 world-aligned linear/angular 6D row를 사용하고 angular row에는 0.25 m characteristic length, column에는 joint half range를 적용한 뒤 최소 singular value를 계산한다. Pinocchio Jacobian의 linear row는 finite difference와 비교해 일치함을 확인했다.

최종 후보 evidence와 해석

workspace-boundary margin은 약 46.127 mm, normalized joint-limit margin은 약 0.576, normalized Jacobian singular value는 0.189–0.196 m로 설정 threshold를 통과했다. deadline 계산값도 목표 budget 아래에서는 양수였고 prediction은 fresh였다. 하지만 latency p95가 미측정이고 collision slack이 음수이므로 schema 2.0 report의 선택 결과는 none이다.

v3와 v4의 관계: v3의 301-frame animation은 nominal geometry와 object-state transition이 일관됨을 보여 주는 visualization evidence다. v4 schema-2.0 report는 uncertainty와 latency evidence를 포함한 safety decision이며 같은 grasp를 선택하지 않는다. v3를 robust 또는 executable trajectory로 소급 해석하지 않는다.

AutoDex grasp가 없거나 clearance가 부족할 때

먼저 object_id + stable_pose_id + end_effector_id + task capability가 정확히 일치하는 validated grasp library를 조회한다. 현재처럼 support clearance가 부족하거나 exact match가 없으면 online request는 unsupported로 끝낸다. 임의 pose fallback이나 threshold 완화로 animation을 통과시키지 않는다.

그 다음 offline synthesis request를 만들어 object-relative hand pose를 생성하고 contact, task quality, support clearance, approach, closure, IK, self/cross/environment collision, release capability를 검증한다. 모든 evidence가 통과하고 review된 후보만 validated library로 등록한다. 즉, 검증된 AutoDex pose가 있으면 선택하고 없으면 생성해야 하지만 생성은 intercept 실시간 loop 밖에서 수행한다.

source revision 843e74a에서 기존 intercept 설정을 다시 감사했다. 같은 Pepsi pose 행렬, object-frame 접근 방향, pre-grasp 거리와 Inspire open/closed command가 grasp 출처와 분리된 search config와 playback template에 중복되어 있었다. 이 구조에서는 library의 grasp를 바꾸어도 stale hand command나 wrist transform이 남을 수 있고, legacy ParaDex pose를 검증된 AutoDex grasp처럼 오해할 수 있다.

관측 evidence

현재 pose의 source는 legacy ParaDex 변환이며 검증된 AutoDex provenance가 없다. task-quality 값과 metric ID도 없어서 각각 null로 기록했다. v4에서 확인한 최소 hand-to-belt 여유는 약 0.163 mm이고 drop 요청의 최소 support clearance는 9 mm이므로 exact compatible grasp는 0개다.

원인

grasp candidate, static feasibility, intercept config가 서로 다른 시대의 schema로 존재했지만, “이 요청에 사용할 pose가 실제로 검증되었는가”를 planner 시작 전에 판정하는 artifact가 없었다. 그 결과 문서상 unsupported 처리와 실제 search 입력 사이에 강제 경계가 없었다.

수정

object-relative hand pose, open/closed command, 접근 벡터, pre-grasp offset, capability, quality metric과 provenance를 grasp library schema 2.0에 모았다. resolver는 exact identity와 threshold를 적용해 validated, provisional_diagnostic, synthesis_required 중 하나를 immutable artifact로 기록하고 source library SHA-256을 고정한다.

planner 연결

intercept schema 3.0은 resolution artifact만 받는다. hand-root pose와 manifest mount transform으로 arm-tip target을 계산하고, grasp 접근 방향은 예측 object pose로 회전한다. belt에서 이탈하는 lift·transfer·retreat 방향은 workcell clearance 방향으로 별도 유지한다. provisional grasp는 진단 계산은 가능하지만 grasp evidence is not validated hard failure 때문에 선택되지 않는다.

synthesis request와 승격 경계

실제 Pepsi drop resolver는 synthesis_required, selected_grasp: null을 반환했다. 동시에 최소 contact 3개와 contact geometry, task quality, support clearance, approach path, hand closure, robot IK, robot self collision, end-effector self collision, arm-hand cross collision, environment collision, task capability의 11개 필수 evidence를 가진 synthesis request를 생성했다.

BODex 또는 다른 generator의 optimizer success는 proposal 생성 결과일 뿐 validated library 승격 근거가 아니다. 생성 pose는 위 evidence를 모두 통과하고 review되기 전까지 provisional이다. 9 mm clearance 요구값은 현재 최대 3-sigma inflation 약 6.39 mm와 2 mm 최소 robust clearance를 합친 뒤 올림한 값이다. 반면 task-wrench-margin-v1의 0.01 threshold는 아직 승인된 실험 기준이 아니므로, metric 정의와 threshold 정당화를 synthesis 과정에서 확정해야 한다.

실행 결과: 현재 resolution을 search CLI에 주면 Pinocchio/FCL model을 구성하거나 report/playback을 쓰기 전에 run offline synthesis and validation first로 종료한다. 임의 fallback grasp, threshold 완화, legacy pose 자동 선택은 없다.

문제 발생과 검증 절차

첫 unit test는 base Python에 NumPy가 없어 import 단계에서 실패했다. dependency를 base에 추가하지 않고 beltbench-planning interpreter로 재실행했다. 전체 discovery에서는 restricted sandbox가 /tmp를 쓰지 못해 TemporaryDirectory test가 실패했고, planning 환경에 OpenCV가 없어 세 module이 import되지 않았다. 쓰기 가능한 임시 경로에서 planning test를 실행하고 OpenCV module은 beltbench-calibration로 분리해 코드 회귀와 환경 실패를 구분했다.

최종 결과는 planning 89개와 OpenCV 14개, 총 103개 test 통과다. mount transform으로 새 hand-root library pose를 기존 arm-tip target과 비교해 1e-12 tolerance로 일치했고, grasp 접근 offset과 workcell vertical lift offset이 독립적으로 계산됨을 확인했다. resolver JSON round-trip은 status, source hash, evidence 11개와 contact count 3을 보존했고, unsupported preflight는 출력 artifact를 남기지 않았다.

2026-08-07 · 생성 pose를 validated grasp와 분리한 NPZ proposal 경계

source revision c10a322에서 resolver 다음 단계를 구현했다. exact object·stable pose·hand·task capability에 맞는 검증 grasp가 있으면 library에서 선택하고, 없으면 BODex 같은 offline generator로 생성한다. 단, 생성 성공은 검증 성공이 아니며 생성 결과를 곧바로 intercept planner에 넣지 않는다.

기존 candidate import가 안전 근거를 잃고 있었다

pickle metadata

기존 importer는 bodex_info.npy의 Python dict를 allow_pickle=True로 읽었다. provider output을 신뢰해야 하고 schema drift를 검출하기 어려운 경로라 삭제했다. 새 adapter는 고정 key를 가진 pickle-free bodex_info.npz만 허용한다.

metric 축 손실

기존 코드는 grasp_error와 dist_error의 첫 값만 float로 평탄화했다. 새 proposal은 native array의 전체 값, shape, unit, metric ID와 “provider 내부 값이며 BeltBench acceptance metric이 아님”이라는 해석을 함께 보존한다.

provider success 오해

--allow-unsuccessful 선택에 따라 seed를 버리거나 남겼다. 이제 모든 complete seed를 import하고 provider success boolean을 evidence로만 저장한다. true도 planning 허가가 아니고 false도 import 누락의 근거가 아니다.

release command 혼동

BODex pregrasp_pose는 손이 물체에 접근하기 전 posture이지 bin에서 놓을 때의 open command가 아니다. grasp library schema 3.0은 pregrasp_command, grasp_command, release_command를 분리하고 drop/place capability가 release command 없이 선언되면 거부한다.

exact stable-pose staging과 provenance

첫 staging 구현은 object의 모든 tabletop pose를 한 provider run에 넣을 수 있었다. importer가 run 전체에 하나의 stable_pose_id를 부여하면 다른 자세의 seed까지 upside-down으로 오표기되는 문제다. 이를 수정해 synthesis request가 지정한 stable pose artifact 하나만 scene으로 만들고, scene 이름도 stable pose ID로 고정했다.

staging manifest는 copied mesh, COACD URDF와 관련 파일, object info, stable-pose JSON, 생성 scene의 상대경로와 SHA-256을 모두 기록한다. importer는 이 manifest의 object/stable-pose identity와 모든 file hash를 확인한다. provider code, world-config loader, Inspire config, manipulator config, 원 stable-pose artifact도 별도 checksum으로 고정한다. proposal batch는 seed별 wrist transform, pregrasp/grasp command, contact count, native metrics, 네 source file checksum, provider revision과 random seed를 저장하고 status를 항상 unvalidated_proposal로 둔다.

BODex output 경로 재감사

관측

vendored BODex는 과거 디렉터리 깊이를 전제로 root를 세 단계 위로 계산해 log와 default output을 BeltBench 밖에 만들 수 있었다. custom output을 주면 skip checker와 writer가 서로 다른 seed root를 사용해 resume 판정도 일치하지 않았다.

수정

BODex root를 현재 source 위치로 계산하고 log를 각 output의 logs/에 둔다. dataset skip checker와 writer가 같은 explicit output root를 사용하며, seed는 네 파일을 temporary sibling에 모두 쓴 뒤 rename한다. 일부 파일만 있는 seed와 stale temporary directory는 자동 보정하지 않고 실패한다.

hand contact tensor 의미도 source까지 추적했다. contact point는 (contact, xyz), frame은 (contact, 3, 3), force는 (task wrench, contact, xyz)다. 첫 adapter가 force 첫 축을 contact 수로 본 오류를 수정하고 회귀 test로 고정했다.

실행 환경과 CLI 정리

새 importer를 문서처럼 file path로 실행했을 때 checkout root가 Python path에 없어 import가 실패했다. 일부 script만 sys.path.insert를 가진 상태에 또 fallback을 추가하지 않고, 표준 pyproject.toml과 pip install --no-deps -e .로 project를 설치하도록 통일했다. 기존 project-root path mutation 25개를 제거했고 FoundationPose 외부 checkout을 명시적으로 adapter에 추가하는 한 지점만 유지했다.

planning, calibration, visualization 세 환경에 editable install을 적용하고 대표 grasp, intercept, calibration, pose, Viser CLI의 --help import matrix를 통과했다. dependency는 계속 환경 YAML이 소유하며 editable install에 --no-deps를 사용한다.

GPU scheduler smoke와 남은 운영 문제

server guide에 따라 login node에서는 GPU를 조회하지 않고 account, helper, scheduler, 기존 job과 storage 상태만 확인했다. 기존 job은 변경하지 않았고 storage pressure가 높은 상태에서 새 BODex image나 대용량 asset 복사를 시작하지 않았다.

첫 smoke · 실패

첫 job은 GPU compute node까지 할당됐지만 exit 1이었다. job script가 set -u 뒤 /etc/profile을 source한 불필요한 순서가 원인 후보였고 PBS stdout은 stage-out되지 않아 확정 증거가 부족하다. 성공으로 해석하지 않았다.

v2 smoke · 구조 통과

compute job에서 profile source를 제거하고 PBS PATH의 nvidia-smi 존재를 검사했다. v2는 GPU 1개를 할당받아 Exit_status=0으로 끝났다. 다만 scheduler stage-out이 완료되지 않아 GPU 이름·driver stdout은 회수하지 못했다.

따라서 GPU allocation smoke는 통과했지만 BODex runtime smoke는 아직 아니다. 원격 checkout은 이전 revision이고 기존 BODex conda environment가 없으며, 로컬에도 Pepsi Light의 BODex용 simplified.obj, COACD URDF, simplified info가 없다. 임의 대형 설치나 synthetic Pepsi output으로 대체하지 않고 이 조건을 blocker로 남겼다.

검증 결과와 다음 단계

planning 환경에서 exact staging, NPZ import, proposal contract, release semantics, 기존 IK·collision·intercept 경로를 포함한 108개 test가 통과했다. OpenCV 의존 calibration·pose·legacy pilot 14개는 calibration 환경에서 별도로 통과해 총 122개 경로를 확인했다. Python compileall, PBS bash -n, Git whitespace 검사와 세 환경 CLI matrix도 통과했다.

현재 정확한 경계: Pepsi upside-down/Inspire Left/drop resolution v2는 여전히 synthesis_required이고 selected grasp는 없다. 실제 provider proposal을 확보한 뒤에도 contact count만으로 승격하지 않는다. 독립 task-wrench quality, support clearance, approach sweep, hand closure, xArm IK, arm/hand/cross/workcell collision, release capability를 평가하고 review된 항목만 schema-3 validated library에 추가한다.

남은 조치는 support clearance가 큰 validated grasp 조회 또는 synthesis, measured conveyor/camera covariance, online GPU planner adapter의 p50/p95/p99 benchmark, full-frame selected playback validation, connector 측정과 hardware release test다. 현재 결과는 실패를 숨기지 않는 offline planning evidence이며 robot 실행은 계속 차단한다.

모듈 재구축 감사와 초기 pose·tracking 연결이 이 계획의 선행 기록이다.

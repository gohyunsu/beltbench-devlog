ISSUE-039 · 2026-08-11 · production sampled evidence

Nominal animation을 runtime 경로로 오인하지 않고, 독립 재계획된 correction cell만 path-family evidence로 조립한다.

Runtime selection과 MuJoCo rollout을 현행 schema로 재생성하려 했지만, 서버에 남은 최신 Pepsi portfolio는 execution candidate가 아니었고 path-family 자료도 nominal 한 cell뿐이었다. 누락된 evidence를 fixture나 사후 좌표 변형으로 채우지 않고, planner output 재현부터 HPP-FCL 검증과 bundle 조립까지 production CLI 경계를 구현했다.

현재 효력: source commit 2085f4c를 GitHub와 junjinyong:~/projects/beltbench에 반영했다. 코드 경계는 준비됐지만 correction boundary 10개가 아직 독립 재계획되지 않았으므로 sampled bundle, runtime handoff, 물리 rollout은 생성하지 않았다. 실행 권한도 없다.

판단을 수정한 과정

처음에는 generator가 correction 값을 manifest에만 기록하는 점을 결함으로 의심했다. 그러나 canonical_sampled_task_path는 의도적으로 phase label과 시작 시간만 바꾸며 robot, hand, object pose를 수정하지 않는다. Object pose만 사후 이동시키면 robot path가 그 조건에서 재계획됐다는 거짓 주장이 된다.

따라서 올바른 절차는 각 boundary에서 motion prediction과 intercept 조건을 바꾸고 planner를 다시 실행한 뒤, 그 playback을 별도 task/stop generation으로 변환하는 것이다. 같은 nominal robot path를 복사하거나 transform만 바꾼 cell은 허용하지 않는다. 11개 axis sample도 full Cartesian 또는 continuous tube proof가 아니다.

구현한 production 경계

  1. SampledPathFamilyPlan과 bundle spec에 strict JSON round-trip과 immutable writer를 추가했다. 알 수 없는 field는 거부한다.
  2. load_verified_sampled_path_generation이 generation manifest의 schema, numeric type, source digest와 exact task/stop bytes를 다시 검사하고 planner-derived path를 재생성한다.
  3. load_verified_sampled_validation_cells이 하나의 generation/task, 공통 robot·object·phase-map·calibration·motion-limit digest, unique cell/coordinate/path digest와 필수 11축 좌표를 검사한다.
  4. Portfolio와 sampled validator가 같은 ReferenceSampledPathValidationBackends factory에서 Pinocchio robot, HPP-FCL assembly checker와 object mesh model을 얻는다. Private planner state를 꺼내 쓰지 않는다.
  5. validate_sampled_path_family CLI는 bundle source set에 고정된 atlas, policy, collision semantics, workcell, calibration과 motion limits만 사용한다. 다른 validator 파일이나 source fallback은 거부한다.
  6. compile_sampled_path_family_bundle CLI는 accepted assessment를 family ID로 일대일 결합하고, 임시 sibling directory에서 complete startup source verifier를 통과한 뒤 directory rename한다.
  7. 최종 scope는 계속 sampled_reference다. Production runtime coordinator는 continuous_path_tube가 아니면 계속 거부한다.

경로 기준과 원자성

Source reference는 spec 파일 위치가 아니라 미래의 --bundle-output 위치를 기준으로 해석한다. Validation과 compilation 사이에 상대경로가 바뀌어 deployment-context SHA가 달라지는 문제를 막기 위해서다. Compiler는 최종 output과 같은 depth의 임시 directory를 사용하므로 외부 source와 내부 validation report reference를 그대로 재검증할 수 있다.

python -m scripts.validate_sampled_path_family \
  --plan PLAN.json --bundle-spec SPEC.json \
  --bundle-output RUN/bundle.json --atlas ATLAS.json \
  --cell-manifest CELL_00/generation-manifest.json ... \
  --assessment-id ASSESSMENT_ID --output ASSESSMENT.json

python -m scripts.compile_sampled_path_family_bundle \
  --bundle-spec SPEC.json --atlas ATLAS.json \
  --plan PLAN.json --assessment ASSESSMENT.json \
  --output-directory RUN

GPU와 cuRobo 방향

실시간성이 중요하다고 모든 모듈을 GPU로 옮기지는 않는다. Multi-camera neural pose, fixed-shape batched FK/IK, robot self/world collision, time-indexed target collision, arm-prefix trajectory optimization과 candidate reduction은 GPU resident pipeline이 적합하다. Timestamp/encoder join, freshness·deadline·cancel 상태기계, constant-translation predictor와 controller I/O는 작고 branch가 많아 CPU에 남기는 편이 전송과 kernel launch 비용을 줄인다.

cuRobo V2는 온라인 arm-prefix planner와 collision authority 후보로 유지한다. HPP-FCL은 offline full-mesh oracle, MuJoCo와 Isaac은 asynchronous physics validation, Viser는 asynchronous replay다. 현재 A6000은 존재하지만 driver 535.161.07이 pinned cuRobo V2 정책의 최소 580.65.06보다 낮다. Exact arm·hand·connector sphere model의 zero-false-negative parity와 target GPU deadline evidence도 없으므로 cuRobo를 지금 runtime에 연결하면 빠르지만 검증되지 않은 fallback이 된다.

검증 결과

  • Sampled generation, validation, compiler, path-family projection/runtime, bounded warm-start와 arm-prefix planning을 포함한 집중 회귀 79개가 13.293초에 통과했다.
  • 새 validation/compile CLI는 beltbench-planning 환경에서 import와 argument contract를 확인했다.
  • GitHub main과 junjinyong source HEAD는 모두 2085f4c다.
  • 서버의 기존 native BODex/cuRobo build 산출물은 삭제하거나 수정하지 않았다.

남은 순서

  1. Current atlas와 planner source가 같은 portfolio를 생성하고 execution-selected request가 없으면 그 이유를 결과로 유지한다.
  2. Nominal과 correction boundary 10개를 각각 재계획한다. 실패 cell은 bound를 줄이거나 path family를 폐기하며 nominal path를 복사하지 않는다.
  3. Accepted sampled assessment와 diagnostic bundle을 만든 뒤에만 현행 runtime selection/handoff evidence를 재생성한다.
  4. Exact admitted event trajectory를 MuJoCo에서 actuated rollout하고 measured contact lifecycle을 분류한다.
  5. 측정 trace만 1x Viser auto-loop로 재생한다. 예쁜 animation을 execution evidence로 부르지 않는다.
  6. Driver와 parity가 준비되면 cuRobo resident arm-prefix solver를 benchmark하고 activation gate를 통과시킨다.

Sampled oracle의 이전 단계, cuRobo와 physics validation 경계, Runtime handoff와 replay 경계를 함께 참고한다.

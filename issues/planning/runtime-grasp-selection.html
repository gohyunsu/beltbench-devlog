ISSUE-013 · 2026-08-08 · fail-closed rolling planner 구현

AutoDex 필터는 후보 근거로 감사하고, 움직이는 물체의 실행 가능성은 최신 상태에서 다시 판정한다.

정적 scene에서 성공한 grasp와 conveyor 위 움직이는 물체를 지금 잡을 수 있는 trajectory는 같은 판정이 아니다. AutoDex의 생성·simulation·runtime 필터를 실제 source revision에서 다시 확인하고, BeltBench에서는 offline grasp 자격, deployment context, exact rolling planning, controller commit을 서로 다른 권한 경계로 분리했다.

현재 효력: revision 78b2d50에서 AutoDex 선택 규칙과 hardware outcome ranking을 최신 source까지 다시 감사했다. BeltBench는 물리 성공률을 grasp-library 점수가 아닌 exact-context hard gate로 분리했고, hardware_static과 hardware_moving_pick을 단조 순위로 취급하지 않는다. rolling planner 출력은 계속 diagnostic_only다. 현재 CPU Pinocchio/HPP-FCL backend와 full-mesh validator는 실시간이 아니며 robot command를 보낼 수 없다.

감사 기준과 repository 혼동

알고리즘 source는 public willi19/autodex-code:main의 commit 5ada1c로 고정했고 로컬에서는 autodex-code:upstream/main commit object로 읽었다. Public remote가 2026-08-08에 노출한 branch는 main 하나다. 체크아웃된 gohyunsu/autodex-code:main은 source와 merge base가 없는 site/document history이고 interactive-3d-glb-export는 더 오래된 source ancestor다. willi19/AutoDex와 gohyunsu/autodex는 project site이므로 working tree 이름이나 현재 branch를 알고리즘 source로 간주하지 않는다.

감사한 AutoDex source revision과 BeltBench reliability 구현 commit을 각각 기준점으로 사용한다.

BeltBench가 채택한 계층

  1. Proposal: provider threshold와 source checksum을 보존하지만 권한은 없다.
  2. Intrinsic: exact identity, named contact, contact count, penetration, non-contact/self/support clearance, 최소 12개의 full-rank antipodal signed force·moment wrench, approach·closure·release capability를 arm과 독립적으로 검사한다. 양수로 설정된 각 path clearance는 이름 있는 normalized slack으로 보존한다.
  3. Deployment: arm·hand·connector·workcell 조합의 IK, self/cross/environment/object collision, joint·singularity margin을 yaw×horizon context별로 검사한다.
  4. Atlas: 모든 hard gate 뒤 context coverage와 maximin slack으로 bounded resident 후보를 만든다. 측정 yaw uncertainty가 지지하는 cell 교집합이 비면 거부한다.
  5. Path-family production 경로: startup에서 검증한 resident path family만 사용하고 최신 track·encoder·robot state에서 retain, certified latch, 한 번의 bounded warm start 또는 stop만 선택한다.
  6. Rolling exact diagnostic: 최신 planar pose와 timestamped arm·hand state를 사용하는 exact planning과 dense playback 검증은 offline regression oracle로만 유지한다. 유효한 후보가 없어도 fallback하지 않으며 command authority는 없다.
  7. Empirical reliability: grasp·object·stable pose·arm·hand·connector·controller·workcell·protocol·conveyor calibration이 같은, 서로 중복되지 않은 물리 trial만 합산한다. 정적 trial은 moving-pick을 승인하지 않는다.
  8. Controller commit: 최신 generation, controller limits, measured latency, accepted moving reliability를 다시 확인해야 한다. 이 단계는 아직 구현하지 않았다.

로컬 검증

Planning 환경 discovery는 348개 항목 중 345개가 통과했다. 남은 세 항목은 구현 실패가 아니라 planning 환경에 OpenCV가 없어 module import가 불가능한 항목이었다. 같은 세 module의 실제 14개 test를 beltbench-calibration 환경에서 모두 통과시켜 총 359개 실제 test를 확인했다. 마지막 runtime·Viser·shortlist 집중 test 67개와 git diff --check도 통과했다. 고정 환경에는 ruff와 black이 설치되어 있지 않아 별도 formatter check는 실행하지 못했다.

junjinyong checkout은 기존 BODex build 두 디렉터리와 compiled .so를 그대로 둔 채 0450e96으로 fast-forward했다. 첫 server focused run을 확인하기 전에 같은 suite를 중복 호출해 내부 import subprocess 하나가 SIGTERM으로 종료됐다. 해당 import test를 단독 실행해 17.676초에 통과시킨 뒤 중복 process가 없는 상태에서 grasp·path-family·runtime focused 95개 전체를 다시 실행했고 23.750초에 모두 통과했다. 검증 후에도 기존 세 untracked BODex build 항목만 남았다.

물리 신뢰도 계약의 범위

GraspHardwareReliabilityEvidence는 한 grasp와 한 물리 문맥의 trial ID·success ID, source system, checksummed trial manifest를 보존한다. moving evidence만 측정된 belt-speed 최소·최대 범위를 가지며, requirement는 실제 요청 속도가 그 안에 있는지 확인한다. 서로 다른 connector, controller profile, workcell, protocol revision, conveyor calibration의 trial은 합산하지 않는다.

assess_hardware_grasp_reliability는 중복 evidence ID와 겹치는 trial ID를 거부하고, point estimate뿐 아니라 설정된 confidence level의 one-sided Wilson lower bound를 계산한다. 최소 trial 수, 최소 success 수, lower-bound threshold 중 하나라도 실패하면 거부한다. threshold는 코드 상수가 아니라 배포 requirement가 소유한다.

이 계약은 아직 trial CSV/영상/센서 측정에서 success를 재구성하는 ingestion command가 아니다. 또한 path-family bundle이나 controller commit에 연결되지 않았다. 하드웨어가 없는 현재 단계에서는 이 경계를 먼저 고정하고 synthetic contract test만 수행하며, 실제 protocol과 raw measurement scorer 없이 hardware authority를 생성하지 않는다.

Runtime workload 계약

예제 policy는 candidate-time pair 8개, distinct grasp 4개, dense refinement 2개, robot state age 100 ms로 작업량을 제한한다. 긴 horizon의 rank 1이 짧은 horizon 전체를 밀어내지 않도록 horizon 사이를 round-robin한다. 한 grasp는 atlas가 실제 지원한 horizon에 대해서만 exact planning하며, unsupported yaw·큰 uncertainty·빈 교집합에서 nominal yaw나 stale shortlist를 사용하지 않는다.

이 수치는 안전 인증이나 latency 측정값이 아니다. Atlas lookup p95 약 1.8 ms만 측정됐고 exact CPU planning과 dense reference validation은 수 분 단위다. Production에서는 GPU batched IK/FK/Jacobian, conservative SDF와 bounded continuous checker를 같은 contract 뒤에 구현하고 p50/p95/p99·missed deadline·cancellation을 recorded replay로 측정해야 한다.

검증 결과

ISSUE-100 · 2026-08-28 · NAS Left proposal snapshot replay

512개 Left proposal을 서버 경로에서 분리해 NAS source snapshot으로 재현한다.

기존 raw seed를 다시 생성하지 않고 proposal의 provider/import evidence를 SHA object store로 materialize했다. 이 snapshot은 offline qualification 입력이며 runtime이 NAS를 검색하도록 만드는 기능이 아니다.

현재 판정: BeltBench ff567aa에서 portable proposal snapshot을 구현했다. 실제 NAS closure 7221532e...는 512개 proposal, 2,571개 unique object와 2,571개 binding을 보존한다. NAS batch를 직접 입력한 endpoint와 full-path 평가가 server-local 실행과 candidate별로 일치했지만 qualified grasp는 여전히 0개다.

왜 단순 복사를 하지 않았나

위험원인선택한 해결
서버 checkout을 옮기면 proposal source reference가 깨짐기존 JSON은 raw seed와 config를 상대 경로로 참조한다.모든 direct evidence를 먼저 재해시하고 SHA-256 object store로 복사한 뒤 evidence 위치만 다시 쓴다.
같은 데이터를 여러 경로에 중복 저장Provider/config/seed evidence가 artifact마다 반복된다.Digest당 object 하나를 두고 scope·label별 binding만 분리한다.
Source 보존을 generator replay로 오인Preflight manifest 보존과 과거 GPU 환경 전체 재현은 같은 주장이 아니다.closure_scope=proposal_import_evidence_only, generator_replay_eligible=false를 고정한다.
NAS를 runtime dependency로 만들 위험Portable artifact가 있으면 event에서 직접 조회하기 쉽다.runtime_eligible=false, execution_authorized=false를 고정하고 local staging만 허용한다.

관찰된 병목

첫 materialization은 약 13 MB의 raw seed임에도 2,571개 작은 파일을 NFS에 생성하느라 약 90초가 걸렸다. 반면 생성된 snapshot 전체를 다시 읽어 검증하는 exact replay는 6.40초였다. 총 byte보다 metadata operation이 지배적이었다. 이 결과는 NAS를 event 또는 60 Hz control 경로에서 제외하고, deployment 전에 local NVMe로 최소 subset을 stage해야 한다는 설계를 뒷받침한다.

검증

Local snapshot/proposal/BODex 인접 회귀 28/28, RTX BODex 회귀 19/19를 통과했다. 전체 BeltBench suite는 1,757개 통과, conditional skip 28개, 159.814초였다. NAS 기반 full-path verifier는 46개 record와 2,687개 source를 승인했지만 execution authority는 계속 false다.

남은 작업

  1. upside_down proposal class를 canonical source-002에 symmetry-aware evidence로 binding한다.
  2. Stable-pose 후보를 실제 측정 또는 승인된 simulation perturbation protocol로 qualify한다.
  3. 44개 diagnostic에서 moving retention·release와 xArm/connector yaw×horizon gate를 수행한다.
  4. source-000/001은 AutoDex Right seed를 이용한 Left 재최적화를 수행하고 비어 있을 때만 새로 생성한다.

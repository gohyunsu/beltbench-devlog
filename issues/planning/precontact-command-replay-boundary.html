ISSUE-045 · 2026-08-11 · pre-contact command replay boundary

Resident capture의 실제 범위를 첫 접촉까지로 바로잡고, full-pick 검증과 분리한다.

직전 단계에서는 cuRobo planner request와 controller 이후 capture의 계보를 묶었지만, 다시 코드를 따라가 보니 capture가 담는 time grid는 path start부터 first contact까지만 존재했다. 반면 기존 Viser와 MuJoCo 경로는 close·attach·lift·transfer·drop·return을 포함한 별도 event reference를 소비한다. 두 자료를 하나의 exact command처럼 연결하면 실행하지 않은 suffix를 controller command로 오인하게 되므로, 먼저 계약과 시각화 범위를 명시적으로 축소했다.

현재 효력: source cd879f7은 resident binding·handoff·capture를 path_start_through_first_contact로 고정하고, exact sample과 진단 보간을 구분하는 checksummed Viser scenario를 추가한다. Attach 이후와 bin drop은 아직 controller-consumed command가 아니므로 MuJoCo command rollout에 연결하지 않는다.

발생한 문제

관찰원인위험
Fixed-shape request의 마지막 target sample이 first_contact였다.fixed_shape_precontact_times가 path start부터 contact까지만 time grid를 만든다.Lease를 complete pick command로 해석하면 범위를 과장한다.
ResidentPathCatalogEntry에는 path digest와 waypoint count만 있고 suffix tensor가 없다.현재 catalog 계약은 resident allocation identity이지 full event command materialization이 아니다.Corrected prefix와 certified suffix가 실제로 이어졌는지 재현할 수 없다.
기존 Viser/MuJoCo는 complete EventScheduledTrajectoryRequest를 소비한다.이 경로는 offline reference animation과 physics diagnostic을 위해 먼저 구현됐다.Pre-contact capture와 reference suffix를 섞으면 mixed provenance가 exact command처럼 보인다.
Lease layout은 time/q/qd/qdd만 선언한다.Controller의 sample-between interpolation mode는 아직 계약에 없다.샘플 사이 quintic을 실제 controller 명령이라고 잘못 주장할 수 있다.

원인 분석

문서의 목표 상태와 현재 코드 상태가 한 단계 어긋나 있었다. 설계상 목표는 mutable arm prefix를 exact resident suffix에 splice하는 것이지만, 구현된 결과는 pre-contact prefix request와 그 출력 lease까지만 닫혀 있다. Catalog metadata를 실제 suffix tensor로 간주한 것이 모순의 직접 원인이다. 따라서 시각화 backend를 먼저 연결하는 대신, 현재 증거가 말할 수 있는 범위를 줄이는 것이 타당하다.

충돌 검사와 GPU 방향

사수님의 질문에 대한 결론은 명확하다. 최종 online collision을 순차 HPP-FCL Python 경로로 두지 않고 cuRobo GPU worker에 둔다. 다만 모든 모듈을 무조건 GPU화하는 것도 타당하지 않다. 큰 fixed-shape batch와 resident data reuse가 가능한 hot path만 CUDA에 두고, 작은 ordered state와 I/O를 CPU에 남긴다.

MuJoCo·Isaac·ViserControl deadline 밖 async consumerPhysics와 rendering이 다음 planning decision을 지연시키지 않게 한다.

cuRobo의 병렬 seed와 GPU motion generation 결과는 이 placement의 근거지만 hard deadline 자체를 증명하지는 않는다. Conveyor grasping의 bounded online 경로는 provably constant-time conveyor replanning처럼 offline reusable path set과 bounded update를 결합하는 편이 현실적이다. dynamic grasping의 reachability/motion-aware ranking도 online global search보다 reachability prefilter와 이전 plan reuse를 지지한다. BeltBench는 이를 compiled path-family, bounded cuRobo warm start와 maximin slack 선택으로 반영한다.

구현한 해결

  1. ResidentTrajectoryCommandBinding schema 1.1에 command scope와 captured_sample_points_only interpolation authority를 추가했다.
  2. ResidentWarmStartControllerHandoff schema 1.1은 dispatch mode를 diagnostic_precontact_resident_segment로 제한하고 scheduled end와 first-contact timestamp의 exact 일치를 요구한다.
  3. ResidentTrajectoryCapture schema 1.1은 post-controller pre-contact sample만 기록하며 binding의 scope와 interpolation authority를 교차 검증한다.
  4. 새 Viser scenario는 capture, fixed planner request, robot manifest, object manifest, workcell의 다섯 source path와 SHA-256을 닫힌 집합으로 결속한다.
  5. Input loader는 request digest, named joint order, exact time grid, object ID와 conveyor support obstacle을 fail-closed로 결합한다.
  6. Viewer는 actual arm·hand·connector·object·workcell asset을 사용하고 1.0배 실제 시간으로 자동 반복한다. 모든 label은 하나의 toggle로 제어한다.
  7. Exact timestamp에서는 캡처된 q/qd/qdd만 표시한다. 그 사이의 quintic-Hermite 상태에는 별도 diagnostic reconstruction ID를 붙이고 controller authority를 부여하지 않는다.
  8. MuJoCo 연결은 의도적으로 보류했다. 현재 capture에는 attach, transport, release와 containment command가 없기 때문이다.

검증 결과

  • Resident·controller·arm-prefix·actual-time playback 집중 회귀 33개가 통과했다.
  • cuRobo collision backend, acceleration policy와 path-family 전체를 포함한 확장 회귀 133개가 통과했다.
  • Planning 환경의 전체 tests/ suite는 668개 중 665개 통과, 2개 기존 skip이었다. 나머지 3개는 해당 환경의 선택적 cv2 부재로 수집되지 않았다.
  • 수집 실패한 calibration·pickplace·pose 14개는 OpenCV가 있는 calibration 환경에서 모두 통과했다.
  • Viser 환경에서 새 server CLI import와 --help를 확인했고, 전체 변경 package·script byte-compile과 git diff --check가 통과했다.

현재 제한

  • 현재 capture fixture는 lifecycle contract 검증용이며 실제 cuRobo V2 kernel 출력이 아니다.
  • Junjinyong server의 NVIDIA driver 535는 선택한 cuRobo V2 정책 최소 580.65.06보다 낮아 sphere fit, parity와 deadline benchmark를 실행할 수 없다.
  • Pre-contact viewer는 grasp attach나 drop 성공을 보여주지 않는다. 기존 full animation은 계속 reference-only다.
  • Controller interpolation과 measured encoder feedback이 없으므로 sample 사이 motion과 tracking accuracy를 증명하지 않는다.

다음 작업 순서

  1. Corrected prefix와 exact resident suffix tensor를 실제로 materialize하고 complete event time grid·joint order·event state에 결속한다.
  2. Controller interpolation semantics와 full command digest를 lease/capture에 포함한다.
  3. 그 complete command만 MuJoCo contact·attach·transport·release·containment rollout과 full-task Viser replay에 연결한다.
  4. Compatible driver가 확보되면 actual xArm6·Inspire Left·connector·belt·bin scene으로 cuRobo V2 parity와 p50/p95/p99·deadline miss를 측정한다.
  5. Hardware 복구 뒤 measured feedback, camera/encoder latency, calibration error와 physical grasp/drop 성공률을 같은 clock lineage에 추가한다.

Resident command lineage, cuRobo online authority audit, Runtime path-family harness를 함께 참고한다.

ISSUE-016 · 2026-08-08 · causal runtime evidence

계획 애니메이션과 실제로 발생한 event를 같은 것으로 보이지 않는다.

기존 runtime trace는 한 grasp-selection decision을 설명하지만 observation 도착, supersession, command와 feedback의 실제 순서를 재현하지 못했다. Ideal PickPlayback에서 그 event를 역으로 만들어 내지 않고, monotonic timestamp와 typed evidence를 가진 독립 session 계약과 Viser 시간축을 구현했다.

현재 효력: revision 1ecfa0b은 event/session 계약, source 검증 CLI와 planned-layer replay를 제공한다. 실제 recorder, desired/measured joint·object stream, controller adapter는 아직 없으므로 hardware execution replay나 real-time 완료 상태가 아니다.

문제와 판단

관찰한 문제잘못된 접근채택한 경계
Single-generation trace만으로 여러 observation과 cancellation의 순서를 알 수 없음선택 playback의 phase에서 sensor/planner event를 추정각 module이 monotonic timestamp의 typed event를 직접 기록
파일 path나 ID만으로는 state·trajectory 변조를 검출하지 못함viewer가 존재하는 파일이면 그대로 load모든 외부 artifact의 type·role·content ID·SHA-256 검증
계획 경로가 실제 명령·feedback처럼 보일 수 있음planned frame을 measured state 대신 표시planned_only, command_only, simulation/hardware feedback을 분리
긴 log를 매 render frame 전체 검사하면 viewer가 log 길이에 비례해 느려짐매 frame session.validate()와 linear scanstartup 검증·activation 해석 후 불변 timeline에서 O(log N) event lookup
선택 event 이전부터 frame zero가 보이면 causal timing이 틀림session 시작 즉시 planned mesh 표시선택/commit 전 arm·hand·connector·object·path를 숨기고 workcell만 표시

구현한 계약

  1. RuntimeArtifactEvidence가 observation, belt state, fused track, prediction, trajectory, playback, command, measured state와 outcome evidence를 통제된 type·role로 참조한다.
  2. RuntimeEvent는 contiguous sequence, monotonic timestamp, generation, module, event type, 허용 status, duration, input/output artifact와 reason code를 가진다.
  3. 각 event SHA-256은 이전 event digest를 포함한다. Session은 terminal event digest와 전체 manifest digest를 다시 검사해 순서 변경·중간 삽입·payload 변조를 거부한다.
  4. planned_only는 commit·setpoint·feedback·contact·release event를 금지한다. command_only는 command가 있지만 measured feedback이 없음을 뜻한다. Feedback session은 measured robot state와 simulation/hardware evidence role이 일치해야 한다.
  5. Published observation·belt·track·prediction, accepted query·trajectory, controller setpoint, measured state와 outcome event는 각자 요구되는 output artifact type이 없으면 실패한다.
  6. validate_runtime_event_session.py가 hash chain과 모든 source를 검증하고, serve_pick_playback.py --runtime-session은 trace 모드와 상호 배타적으로 session 시간을 재생한다.

Viser 시간 의미

RuntimeSessionTimeline은 viewer startup에서 playback activation과 최대 1 ms GUI step을 계산한다. 재생 시간은 event.timestamp_s - session.started_timestamp_s이며 기본 1x·자동 반복이다. 현재 event는 binary search로 찾으므로 frame당 log 전체를 순회하지 않는다.

선택 playback은 정확히 한 diagnostic_selected 또는 plan_committed event가 출력한 artifact여야 한다. 그 이전에는 planned mesh를 숨긴다. Feedback session이라도 현재 mesh는 계속 “selected planned playback”으로 표시하며, 측정 geometry를 생성해 내지 않는다.

검증 결과

Round-trip, write-once, event/manifest digest 변조, sequence reorder, unknown artifact, strict boolean, source·playback digest와 ID, planned/command/feedback role, required output type, exact event boundary와 activation 전후 표시를 검사했다. Runtime 집중 test 16개와 전체 compile이 통과했다.

전체 planning 수집 261개 중 OpenCV 전용 import 3개를 제외한 실제 258개가 통과했다. 그 세 module은 calibration 환경에서 14개가 모두 통과해 총 272개를 확인했다. junjinyong 서버의 고정 planning 환경에서도 새 session과 기존 runtime·interception·conveyor 관련 34개가 통과했다.

남은 한계

  • 현재 최종 session JSON은 write-once contract다. Control loop를 막지 않는 bounded queue/async recorder와 crash-safe chunk writer는 아직 없다.
  • Desired setpoint, measured robot/hand state와 measured object pose의 stream schema와 Viser 별도 geometry layer가 없다.
  • Deadline miss, supersession, cutoff, watchdog와 abort의 recorded simulation fixture가 없다.
  • Event replay는 증거 시각화다. Planner·controller deadline이나 hard real-time 성능을 증명하지 않는다.

다음 단계는 path-family/latch/cutoff 계약과 함께 closed-loop simulation의 state stream·async evidence recorder를 구현하는 것이다. 그 기록을 사용해 accelerated backend의 reference agreement, p50/p95/p99, worst case, deadline miss와 cancellation latency를 측정한다.

실시간 conveyor architecture ADR과 single-generation decision trace가 이 session의 상위 방향과 입력 근거다.

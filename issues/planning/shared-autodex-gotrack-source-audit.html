프로젝트이슈
ISSUE-090 · 2026-08-27 · shared AutoDex/GoTrack source audit

공유 RGB episode를 확인해 GoTrack과 grasp 기록의 실제 권한을 다시 분류한다.

프로젝트-site repository만 보면 AutoDex에서 GoTrack이 실제로 어떻게 쓰였는지, 선택 데이터가 RGB-only인지, 실행 grasp가 어떤 hand의 것인지 확정하기 어려웠다. 읽기 전용 공유 archive의 manifest, raw tracking log, pose record와 executed-grasp metadata를 서로 대조해 재사용할 수 있는 요소와 버려야 할 가정을 분리했다.

현재 판정: GoTrack은 실제 24-view RGB tracking 산출물을 만든 AutoDex processing 단계다. 그러나 대표 Pepsi episode는 약 5.15 s/frame, 0.20 inference FPS이므로 BeltBench의 online per-frame tracker로 채택하지 않는다. 공유 데이터는 offline evidence와 replay 입력으로만 읽고 원본에는 쓰지 않는다.

발생한 문제

관찰위험
Public project site와 구현 repository만으로는 실제 episode의 GoTrack 실행 여부가 불명확했다.사용한 적 없는 tracker를 AutoDex 방법으로 오인하거나, 반대로 실제 source lineage를 버릴 수 있다.
상위 result에는 tracking elapsed가 0초로 기록돼 있었다.Cached result를 실시간 측정으로 잘못 읽으면 latency 판단이 완전히 뒤집힌다.
Executed grasp metadata의 success는 null이지만 별도 outcome label이 존재했다.두 source를 결합하지 않으면 결과를 누락하고, 반대로 provider label을 exact-context reliability로 과장할 수 있다.
FoundationPose 이름의 산출물과 FoundPose 방법을 혼동하기 쉬웠다.RGB-only physical pipeline에 RGB-D 전제를 몰래 다시 넣게 된다.

확인한 source와 결과

  • 선택 archive에는 이름과 달리 현재 99개 object directory가 있으며 Pepsi episode는 3개다.
  • 대표 manifest는 24개 camera와 has_depth=false를 명시하고 initial world pose, calibration lineage, FoundationPose-labelled output과 GoTrack output을 가리킨다.
  • GoTrack raw log는 one-GPU model load 1.7초, renderer setup 0.7초 후 24/24 camera initial pose를 읽고 256-anchor bank로 198/198 world pose를 생성했다.
  • 같은 log의 frame loop는 약 1,019초로, 평균 약 5.15초/frame이다. Cached wrapper의 tracking_elapsed_s=0.0은 timing evidence에서 제외했다.
  • 세 executed grasp는 모두 Allegro hand, pose ID 008, executed-FK wrist pose를 기록한다. Companion outcome label은 success 2건, failure 1건이며 reviewer는 robot, source는 candidate result다.
  • 세 producer candidate 경로도 NAS에서 해석되며 각각 wrist, pregrasp, grasp와 result를 포함한다. Candidate result의 episode/success는 companion outcome과 모두 일치한다.
  • Processed manifest는 has_C2R=true지만 선택 C2R.npy symlink는 깨져 있고 source에는 R2C.npy만 있다. 파일명만 보고 역행렬을 추론하지 않는다.
  • 공유 processing source snapshot은 8b50af8로 고정해 조사했다.

원인과 해석

GoTrack은 이전·현재 RGB 대응점, object anchor, multi-view triangulation과 rigid fitting으로 연속 pose를 만든다. 즉 실제 AutoDex processing 아이디어를 확인하는 데 유용하다. 하지만 24-view 구성의 계산량은 BeltBench의 15~30 Hz camera correction이나 60 Hz control loop와 두 자릿수 이상 맞지 않는다. 이름의 online은 API 동작 형태이지 현재 hardware에서 deadline을 만족했다는 증거가 아니다.

또한 공유 episode의 FoundationPose-labelled artifact는 FoundPose가 아니다. Manifest가 RGB-only source를 기술하더라도 해당 artifact가 어떤 중간 입력으로 생성됐는지는 별도 producer audit 없이는 알 수 없다. 따라서 현재 RGB-only runtime provider 권한으로 가져오지 않는다.

실시간 pipeline 반영

  1. Known object와 stable-pose ID를 입력으로 받고, synchronized RGB에서 초기 x/y/yaw와 covariance를 한 번 획득한다.
  2. 물체 yaw는 고정하고 calibrated belt 방향 translation만 encoder로 60 Hz 전파한다.
  3. RGB correction은 5~10 Hz 목표 안에서 별도 qualification을 통과한 provider만 사용한다. GoTrack은 현재 그 provider가 아니다.
  4. Planning core는 provider 이름이 아니라 같은 FusedPlanarObjectTrack만 소비한다.
  5. 공유 grasp는 proposal source일 뿐이다. Exact hand·connector·robot·workcell에 대해 complete path와 moving-contact gate를 다시 통과해야 한다.

보존 규칙과 검증

공유 source tree는 읽기 전용으로 유지하고 사용자 namespace에만 append-only registry와 derived evidence를 쓴다. Registry는 source·resolved URI, object·episode·provider pose·camera·hand·outcome·source defect와 SHA-256을 결속한다. Actual-time runtime은 검증된 최소 bundle을 local storage에 stage해 NFS를 critical path에서 제외한다. Public 기록에는 내부 주소와 raw calibration을 공개하지 않는다.

다음 작업

  1. 세 Pepsi episode의 world pose를 belt-frame planar track으로 import하는 read-only adapter fixture를 만든다.
  2. Raw RGB timestamp와 world pose를 사용해 GoTrack의 drift·dropout·multi-view residual을 offline 기준선으로 평가한다.
  3. 현재 RGB-only planar backend와 같은 episode/split에서 정확도와 end-to-end latency를 비교한다.
  4. Executed wrist pose를 object-relative frame으로 재구성하되 Allegro hand command는 제거하고 Inspire Left grasp generation 입력으로만 사용한다.
  5. 초기 pose producer가 RGB-only 경계를 만족했는지 별도 추적하기 전까지 FoundationPose-labelled 산출물을 runtime evidence로 승격하지 않는다.

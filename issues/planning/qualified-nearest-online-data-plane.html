ISSUE-111 · 2026-08-31 · qualified nearest online data plane

Nearest grasp는 버리지 않고, 후보 검색에만 사용한다.

Nearest 하나를 곧바로 실행하면 현재 robot state, 충돌, 도달 시간과 강건성을 무시한다. 반대로 nearest를 전혀 쓰지 않으면 이미 검증된 정적 grasp library를 효율적으로 좁힐 수 없다. BeltBench는 exact object·stable pose·hand·capability 안의 nearest top-K를 빠른 검색 순서로 사용하고, 최종 실행 후보는 observation 이후 생성·검증한 complete command의 maximin margin으로 다시 고른다.

현재 효력: beltbench@4cda817은 Pepsi Light/source-001/Inspire Left/drop_release의 qualified grasp 82개를 상주 index에 올리고, predicted intercept별 nearest top-K와 source-complete evidence, stage-owned actual timestamp, current-state full-task cuRobo command 및 독립 timing·grasp-bound contact lifecycle/maximin 경계를 제공한다. Planning/validation import는 optional RGB backend와 분리됐지만 connector/workcell/time-indexed moving-object collision과 drop containment, 실제 RGB inference와 Isaac feedback이 아직 완결되지 않았으므로 execution_authorized=false다.

문제와 판단

이 기준은 ISSUE-108의 원칙을 실제 qualified library와 bounded online data path로 갱신한다. ISSUE-110의 upside-down source-002는 proposal 42개가 있어도 unvalidated이므로 여전히 no-pick이며, source-001의 82개를 가져다 쓰지 않는다.

해결 절차

  1. NAS 원본 ancestry와 intrinsic 결과를 다시 검증해 source-001의 offline_intrinsic grasp 82개를 exact registry로 결속했다. Library SHA-256은 0cdb9986...8d32다.
  2. 97caf52와 1d45c05에서 context·capability·quality gate를 startup-only immutable index로 옮기고 numeric nearest와 evidence hashing을 분리했다.
  3. b6c2909에서 current robot state와 resident robot-model FK lineage를 query에 결속했다. 별도 robot model을 다시 적재하지 않는다.
  4. 1c2860a와 18afb30에서 stable-pose composition, covariance propagation, belt prediction과 grasp-time interception을 bounded vectorized data path로 분리했다.
  5. Canonical JSON, digest와 deep replay는 control callback 밖의 evidence worker로 이동했다. 기존 synchronous API는 compatibility/evidence 경로로만 남겼다.

실패한 시도와 원인

RTX workstation의 첫 smoke run은 구현 오류가 아니라 import 단계에서 종료됐다. 실행 environment에 이전 BeltBench package가 설치돼 있어 새 contract module을 찾지 못한 것이 직접 원인이었다. Authoritative checkout을 명시해 다시 실행했고 package mutation이나 algorithm fallback 없이 통과했다. 이 문제는 배포 시 revision뿐 아니라 import root도 고정해야 한다는 재현성 조건으로 남겼다.

2026-08-31 갱신: Timing을 독립 검증하고 actual handoff lead를 재확인

구현 중 발견한 설계 오류

P95 예측과 actual time의 역할 분리

P95 slack이 양수여도 현재 run이 느리면 command start를 이미 놓칠 수 있다. 2026-08-31 갱신: Predicted-intercept nearest를 source-complete evidence로 보존

55a1f44와 436417f는 observation-time nearest batch와 predicted-intercept nearest batch의 역할을 자료구조에서 분리한다. 기존 grasp_batch는 current robot-state FK, exact object·stable pose·hand context와 source library의 root evidence로 유지한다. 새 PredictedInterceptGraspEvidence는 각 selected prediction sample의 object_from_current_hand reference, top-K grasp 전체, distance/rank와 root batch digest를 보존한다.

새 online materialization은 predicted_grasp_evidence_complete=true를 명시한다. 이 marker가 있으면 target, motion result, timing/contact validator는 반드시 candidate의 prediction_sample_index와 연결된 evidence에서 grasp ID·SHA-256·retrieval rank가 모두 일치하는 항목을 찾아야 한다. Observation-time batch에 같은 grasp ID가 있더라도 fallback하지 않는다. Marker가 없는 기존 batch만 historical compatibility 경로를 유지하며 current per-intercept evidence로 주장할 수 없다.

발견한 provenance 문제

Data plane은 5bec63f부터 이미 predicted pose마다 nearest를 다시 계산했지만, source evidence materializer는 observation-time batch 하나만 저장했다. 따라서 실제 RTX command가 predicted reference에서 선택한 grasp를 root batch에서 찾지 못하거나, 우연히 같은 ID가 있으면 잘못된 retrieval rank와 reference를 증거로 사용할 수 있었다. Hot path 계산은 맞아도 비동기 evidence와 독립 validator가 이를 재현하지 못하는 상태였다.

2026-08-31 갱신: Planning과 optional RGB dependency 분리

Online core/validator 회귀 87/87은 RTX cuRobo 환경에서 통과했지만 admission test를 추가하자 test collection 전에 ModuleNotFoundError: cv2가 발생했다. Admission이나 trajectory contract가 OpenCV를 쓰는 것이 아니라, Python이 runtime submodule을 import하면서 package initializer를 실행하고, 여기서 multi-stable-pose simulation adapter와 RGB yaw backend까지 연쇄적으로 적재한 것이 원인이었다. cuRobo 환경에 OpenCV를 추가 설치하는 것은 모듈 결합을 숨기는 해결이므로 채택하지 않았다.

  1. 962cad1에서 beltbench.perception의 기존 RGB-only 공개 API를 source-declared lazy export로 바꿨다. API 이름과 RGB-D 비노출 조건은 유지하며 실제 RGB backend를 요청할 때만 해당 dependency를 import한다.
  2. 첫 재검증에서 runtime initializer의 multi_stable_pose_event가, 두 번째에는 object_only_full_task가 같은 backend를 eager import하는 것을 확인했다. 0aea509와 4cda817에서 이 세 application-level export만 lazy boundary로 이동했다. 전체 runtime initializer를 무리하게 재작성하지 않았다.
  3. cv2가 없는 잠긴 cuRobo 환경에서 admission 10/10이 통과했고, OpenCV 4.6.0이 있는 서버 RGB Python에서 RGB-only wiring과 realtime RGB pipeline 33/33이 0.576초에 통과했다.

서버 RGB Python에는 pytest가 없어 첫 runner 호출은 시작되지 않았다. Dependency를 추가하지 않고 표준 unittest로 동일 모듈을 실행했다. 이 결과는 perception latency나 RGB inference 정확도 측정이 아니라, planning/validation process가 RGB backend package를 불필요하게 적재하지 않으며 실제 RGB process의 API도 유지된다는 import-boundary 검증이다.

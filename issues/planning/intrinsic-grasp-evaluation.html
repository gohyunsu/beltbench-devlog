ISSUE-010 · 2026-08-07 · 실제 BODex smoke 8개 독립 평가, 전부 차단

검증된 grasp가 없으면 새로 생성하되, 재사용 후보와 같은 독립 평가를 통과시킨다.

AutoDex 계열에서 동일한 물체, stable pose, hand, 작업 capability로 이미 검증된 grasp가 있다면 생성 비용을 줄일 수 있다. 그러나 검증 범위가 다르거나 그런 grasp가 없다면 BODex 같은 provider로 후보를 생성해야 한다. 두 경로의 차이는 후보를 얻는 방법뿐이며, BeltBench에서는 접촉, task wrench, support, 접근, hand closure, release를 같은 arm-independent evaluator로 다시 확인한다.

문제와 영향

기존 legacy Pepsi Light/Inspire-left pose는 실제 mesh와 hand joint pose를 포함하지만 검증된 grasp는 아니었다. provider가 남긴 success, contact count, native error를 그대로 신뢰하면 생성기의 내부 목적함수를 BeltBench 작업 성공 기준으로 오해하게 된다. 반대로 xArm IK와 workcell collision을 먼저 검사하면 hand-object grasp 품질이 특정 arm 배치에 묶여 재사용성이 사라진다.

Stale provenance

원본 legacy grasp 파일이 바뀐 뒤 local fixture가 과거 SHA-256을 유지하고 있었다. 이전 loader는 JSON 구조만 읽었기 때문에 이 차이를 즉시 드러내지 못했다.

중복 hand geometry 경로

기존 combined checker가 arm과 hand를 한 class 안에서 모두 배치했다. intrinsic 평가를 별도로 추가하면 mimic joint와 geometry placement가 두 구현으로 갈라질 위험이 있었다.

품질값 의미 혼합

BODex native residual은 후보 생성기의 QP 목적값이다. BeltBench의 지정 작업 wrench를 견디는 margin과 단위, 정규화, acceptance 의미가 같지 않다.

거리 API 경고

hpp-fcl 3.0에서 nearest-point enable flag가 deprecated되었다. 계속 사용하면 관통 상태의 signed distance와 법선 의미가 불명확해질 수 있었다.

해결 구조

  1. 후보 획득: 정확히 호환되는 검증 grasp가 있으면 재사용하고, 없으면 offline provider가 unvalidated_proposal을 생성한다.
  2. Provenance gate: proposal batch뿐 아니라 provider input과 proposal-local source를 모두 다시 hash한다.
  3. Hand-only geometry: end-effector URDF, root link, collision geometry identity, package path, SHA-256을 별도 manifest로 고정한다. arm URDF와 mount transform은 intrinsic 입력에서 제외한다.
  4. 기하 평가: 실제 hand collision geometry와 object mesh로 endpoint 접촉점·법선, non-contact clearance, self-collision, support plane을 계산한다.
  5. 경로 평가: open hand의 object-relative 접근과 fixed grasp pose의 closure를 각각 샘플링한다. intentional fingertip 이외의 충돌과 허용치를 넘는 관통을 실패로 남긴다.
  6. Task quality: 마찰 피라미드와 접촉별 힘 상한을 둔 LP로 각 지정 wrench의 최대 균형 margin을 구하고 최솟값을 품질로 사용한다.
  7. Release: drop capability는 별도 open command에서 잔류 접촉과 clearance를 검사한다.
  8. Promotion과 deployment: approved protocol의 모든 intrinsic gate가 통과해야 offline_intrinsic으로 승격한다. 이후 robot IK, mount, arm-hand-workcell collision과 timing은 별도 평가한다.

토크는 명시한 object-frame 기준점과 characteristic length로 정규화한다. provider score는 이 LP에 입력되지 않는다. combined arm-hand checker도 같은 hand-only model을 합성하도록 리팩터링해 joint expansion과 geometry placement 구현을 하나로 유지했다. 거리 질의는 최신 signed-distance API로 교체했다.

해석 경계: 현재 upside-down stable pose, 접근 방향, 마찰계수, task-wrench set은 provisional이다. 따라서 위 수치는 실제 grasp 성공률이나 하드웨어 안전을 증명하지 않는다. 다만 이 provisional 조건에서도 legacy 후보가 승격 기준에 크게 못 미친다는 진단은 재현됐다.

BODex v2 Pepsi smoke 결과

실제 BODex GPU smoke 8개를 같은 evaluator로 다시 평가했다. 첫 output adapter는 중간 optimization stage wrist와 최종 finger joint를 섞고 있었고, 이 hybrid pose에서는 provider contact 5개가 독립 평가에서 0~1개로 줄었다. 저장 경계를 final wrist로 수정하고 중간 wrist를 별도 evidence로 보존한 v2에서는 두 stage root가 2.8~8.6 mm, 1.9~4.2° 달랐으며, 독립 접촉 수가 2~4개로 회복됐다.

검증과 다음 행동

합성 opposing-contact 사례에서 양·음 force margin이 양수이고 생성할 수 없는 축 torque margin은 0이 되는지 확인했다. no-contact, explicit evaluator failure, source checksum drift가 모두 fail-closed로 동작하며, 기존 combined collision 결과도 hand-only model 합성 후 유지되는 회귀 테스트를 추가했다. Planning/core test 162개와 OpenCV가 분리된 test 14개, 총 176개가 통과했다. 실제 평가 artifact에는 NumPy 1.26.4, SciPy 1.13.1, Pinocchio 3.4.0, hpp-fcl 3.0.1, trimesh 4.8.3과 evaluator source SHA를 기록했다.

첫 전체 test discovery는 tests/를 importable package로 요구하는 unittest 옵션 때문에 시작 전에 실패했다. 모든 module을 명시하는 기존 방식으로 바꿔 실제 162개 test를 실행했다. OpenCV test를 처음에는 존재하지 않는 환경 이름으로 호출해 실패했고, dependency가 설치된 calibration 환경으로 바로잡아 14개를 통과시켰다. 이 두 실패는 algorithm failure와 분리했다.

실제 Pepsi mesh와 Inspire URDF 실행은 상세 evaluation bundle과 promotion summary를 생성했지만 항상 execution-blocked로 남는다. 마지막 negative smoke에서는 assessment, evaluation, proposal, protocol, asset, evaluator source checksum을 모두 재검증한 다음 promotion이 위 failure code를 이유로 거부되는 것을 확인했다. Public devlog의 새 page, issue index, homepage, CSS도 local static server에서 모두 HTTP 200을 반환했다.

다음 단계는 smoke보다 충분한 production seed budget으로 후보를 생성하고, 독립 endpoint screening 후 생존 후보의 approach·closure·release 경로만 정밀 평가하는 것이다. 동시에 stable pose를 측정해 provisional 상태를 해소하고 approved task protocol을 확정해야 한다. 통과 후보만 xArm deployment와 moving interception planning으로 넘기며, 선형 closure가 계속 관통한다면 threshold를 완화하는 대신 hand closing trajectory 또는 후보 생성 제약을 수정한다.

Offline planning과 Viser 기록에서 이후 robot deployment와 moving interception 연결을 계속 관리한다.

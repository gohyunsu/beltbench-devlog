ISSUE-010 · 2026-08-07 · 12-direction draft .2 재검증 완료

검증된 grasp가 없으면 새로 생성하되, 재사용 후보와 같은 독립 평가를 통과시킨다.

AutoDex 계열에서 동일한 물체, stable pose, hand, 작업 capability로 이미 검증된 grasp가 있다면 생성 비용을 줄일 수 있다. 그러나 검증 범위가 다르거나 그런 grasp가 없다면 BODex 같은 provider로 후보를 생성해야 한다. 두 경로의 차이는 후보를 얻는 방법뿐이며, BeltBench에서는 접촉, task wrench, support, 접근, hand closure, release를 같은 arm-independent evaluator로 다시 확인한다.

현재 효력: 아래 2,000→153→129 수치는 ±force 3축과 ±yaw만 사용한 draft-2026-08-07.1의 역사적 진단이다. Roll·pitch moment를 포함한 draft-2026-08-07.2의 12방향 기준으로 전체 ancestry를 다시 계산했고 현재 결과는 2,000→140→117이다. 두 결과를 섞지 않으며, 새 결과도 stable pose와 protocol이 provisional이므로 diagnostic일 뿐 실행 권한은 아니다.

문제와 영향

기존 legacy Pepsi Light/Inspire-left pose는 실제 mesh와 hand joint pose를 포함하지만 검증된 grasp는 아니었다. provider가 남긴 success, contact count, native error를 그대로 신뢰하면 생성기의 내부 목적함수를 BeltBench 작업 성공 기준으로 오해하게 된다. 반대로 xArm IK와 workcell collision을 먼저 검사하면 hand-object grasp 품질이 특정 arm 배치에 묶여 재사용성이 사라진다.

Stale provenance

원본 legacy grasp 파일이 바뀐 뒤 local fixture가 과거 SHA-256을 유지하고 있었다. 이전 loader는 JSON 구조만 읽었기 때문에 이 차이를 즉시 드러내지 못했다.

중복 hand geometry 경로

기존 combined checker가 arm과 hand를 한 class 안에서 모두 배치했다. intrinsic 평가를 별도로 추가하면 mimic joint와 geometry placement가 두 구현으로 갈라질 위험이 있었다.

품질값 의미 혼합

BODex native residual은 후보 생성기의 QP 목적값이다. BeltBench의 지정 작업 wrench를 견디는 margin과 단위, 정규화, acceptance 의미가 같지 않다.

거리 API 경고

hpp-fcl 3.0에서 nearest-point enable flag가 deprecated되었다. 계속 사용하면 관통 상태의 signed distance와 법선 의미가 불명확해질 수 있었다.

해결 구조

  1. 후보 획득: 정확히 호환되는 검증 grasp가 있으면 재사용하고, 없으면 offline provider가 unvalidated_proposal을 생성한다.
  2. Provenance gate: proposal batch뿐 아니라 provider input과 proposal-local source를 모두 다시 hash한다.
  3. Hand-only geometry: end-effector URDF, root link, collision geometry identity, package path, SHA-256을 별도 manifest로 고정한다. arm URDF와 mount transform은 intrinsic 입력에서 제외한다.
  4. 기하 평가: 실제 hand collision geometry와 object mesh로 endpoint 접촉점·법선, non-contact clearance, self-collision, support plane을 계산한다.
  5. 경로 평가: open hand의 object-relative 접근과 fixed grasp pose의 closure를 각각 샘플링한다. intentional fingertip 이외의 충돌과 허용치를 넘는 관통을 실패로 남긴다.
  6. Task quality: 마찰 피라미드와 접촉별 힘 상한을 둔 LP로 각 지정 wrench의 최대 균형 margin을 구하고 최솟값을 품질로 사용한다.
  7. Release: drop capability는 별도 open command에서 잔류 접촉과 clearance를 검사한다.
  8. Promotion과 deployment: approved protocol의 모든 intrinsic gate가 통과해야 offline_intrinsic으로 승격한다. 이후 robot IK, mount, arm-hand-workcell collision과 timing은 별도 평가한다.

BODex v2 Pepsi smoke 결과

실제 BODex GPU smoke 8개를 같은 evaluator로 다시 평가했다. 첫 output adapter는 중간 optimization stage wrist와 최종 finger joint를 섞고 있었고, 이 hybrid pose에서는 provider contact 5개가 독립 평가에서 0~1개로 줄었다. 저장 경계를 final wrist로 수정하고 중간 wrist를 별도 evidence로 보존한 v2에서는 두 stage root가 2.8~8.6 mm, 1.9~4.2° 달랐으며, 독립 접촉 수가 2~4개로 회복됐다.

Production endpoint screening

Production 생성은 smoke보다 훨씬 많은 seed를 사용하므로 모든 후보에서 approach 20, closure 12, release 12개 상태를 즉시 계산하면 비용이 커진다. 이를 줄이기 위해 전체 batch에는 endpoint contact, penetration, hand self-clearance, support clearance, task-wrench만 먼저 계산하고, 모든 endpoint hard gate를 통과한 ID만 full-path worklist에 넣는 별도 immutable artifact를 추가했다. Screening은 항상 execution-blocked이며 provider success와 native metric 필드가 decision schema에 존재하지 않는다.

역사적 draft .1 screening과 full-path 결과

2,000개 normalized proposal을 4개 process로 screening했다. 각 process가 독립 Pinocchio/FCL hand·object model을 소유하고 numeric library 내부 thread는 1개로 제한했다. 8-seed fixture에서는 worker 1개와 2개의 endpoint 결과와 순서가 8/8 완전히 같았다. Production run은 약 2분 14초에 끝났고 1,847개를 endpoint에서 차단해 153개만 approach·closure·release 평가 대상으로 남겼다.

반복 full evaluator의 복잡도 결함

처음에는 기존 single-proposal CLI를 153번 호출하는 방안을 검토했다. 그러나 이 방식은 매 후보마다 10,009개 provider source를 다시 hash하고 mutable hand/object model을 다시 load한다. Batch 구현 초안도 common context 확인 함수를 survivor마다 호출해 내부적으로 2,000개 proposal validation을 반복하는 O(S×N) 결함이 있었다. 실행 전에 이를 발견해 source와 common context는 parent에서 한 번만 검증하고, worker마다 model을 한 번 load한 뒤 contiguous partition을 순차 평가하도록 바꿨다.

각 후보는 여전히 독립 evaluation/assessment JSON을 갖는다. 파일명에는 untrusted proposal ID를 쓰지 않고 screening index를 사용한다. 모든 worker가 끝난 뒤에만 ordered summary.json을 만들며, PBS 후처리 verifier가 proposal 원본, screening, source code, 153개 artifact pair를 총 10,339개 verified file로 다시 대조해야 run이 완료된다.

Production evidence Viser 검증

처음 local mirror에서 index 73 evaluation을 열었을 때 synthesis request가 exact relative path에 없어 viewer가 source 확인 단계에서 중단됐다. 누락 파일을 원격 evidence에서 가져와 expected SHA-256 013cc1a30dd…81b7와 일치시킨 뒤 다시 실행했다. 실제 Pepsi mesh와 Inspire hand URDF를 load한 Viser HTTP/WebSocket server가 기동됐고 자동 loop state를 구성한 뒤 timeout으로 종료했다.

이 과정에서 viewer가 선택 후보 1개만 사용하면서 proposal 2,000개의 native source 10,009개를 모두 다시 hash하는 startup 병목도 확인했다. Evaluation이 proposal-batch JSON 자체를 이미 checksum으로 고정하므로, 공통 provider input과 선택 proposal의 5개 native file만 재검증하는 scoped evidence 모듈로 바꿨다. 사용하지 않는 후보 source가 없어도 선택 후보 검토는 통과하고, 선택 후보나 공통 source가 바뀌면 여전히 fail-closed가 되는 회귀 test를 추가했다.

진단과 승인 분리: diagnostic_geometry_clear는 provisional context failure와 그에 따른 capability failure를 제외한 root geometry/path 결과다. 이를 failure_free, offline_intrinsic, hardware execution 권한으로 해석하면 안 된다. Stable pose 측정과 protocol 승인 후 같은 evidence를 다시 생성해야 하며, 이후에도 xArm deployment와 moving interception gate가 남는다.

검증과 다음 행동

BeltBench revision 3c3e2ef에서 합성 opposing-contact, no-contact, explicit failure, source checksum drift, deterministic partition, worker별 model 1회 load, summary tamper, selected-proposal source scope를 회귀 test로 확인했다. Planning/core test 181개와 OpenCV 분리 test 14개, 총 195개가 통과했다. Production full evaluation은 revision c8c4492에서 수행됐고, viewer startup 최적화는 결과 schema나 evaluator source를 변경하지 않는 후속 revision이다.

첫 전체 test discovery는 tests/를 importable package로 요구하는 unittest 옵션 때문에 시작 전에 실패했다. 모든 module을 명시하는 기존 방식으로 바로잡았다. 정적 검사기 Ruff는 planning 환경에 설치되어 있지 않아 실험 환경에 새 dependency를 임의로 추가하지 않았고, 전체 module import·회귀 test와 실제 CLI 실행으로 검증했다. OpenCV test는 calibration 환경에서 분리 실행했다.

실제 Pepsi mesh와 Inspire URDF 실행은 상세 evaluation bundle과 promotion summary를 생성했지만 항상 execution-blocked로 남는다. 마지막 negative smoke에서는 assessment, evaluation, proposal, protocol, asset, evaluator source checksum을 모두 재검증한 다음 promotion이 위 failure code를 이유로 거부되는 것을 확인했다. Public devlog의 새 page, issue index, homepage, CSS도 local static server에서 모두 HTTP 200을 반환했다.

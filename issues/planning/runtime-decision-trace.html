ISSUE-014 · 2026-08-08 · recorded runtime evidence

선택된 trajectory만 보지 않고, 어떤 grasp가 어느 gate를 통과했는지 함께 재현한다.

Rolling planner는 atlas, exact planning, dense validation 근거를 메모리에 갖고 있었지만 종료 후 재현 가능한 artifact는 없었다. Backend 객체를 pickle하거나 모든 후보 playback을 복제하지 않고, 한 observation generation의 필터 근거와 선택 playback의 무결성을 연결하는 trace 계약을 추가했다.

현재 효력: revision 7dc7953은 단일 runtime decision을 기록하고 Viser overlay로 반복 재생한다. 이는 recorded diagnostic이며 sensor stream, causal online scheduling, controller feedback, command dispatch를 재현하지 않는다.

문제 정의

  1. 저장된 PickPlayback만 보면 왜 다른 grasp와 intercept time이 탈락했는지 알 수 없었다.
  2. RuntimeInterceptDecision은 exact-search backend 객체와 여러 playback을 포함해 장기 저장 계약으로 쓰기 부적합했다.
  3. Viser가 임의의 playback과 decision 설명을 함께 열 수 있으면 stale 또는 다른 후보를 선택 결과처럼 보일 수 있었다.
  4. 계산 단계 표시가 execution authority처럼 해석되면 offline diagnostic의 안전 경계가 무너진다.

구현 절차

  1. RuntimeInterceptTrace와 단계별 typed summary를 별도 contract로 정의했다. Boolean을 integer로 허용하지 않고, timestamp·rank·digest·identity·accepted/rejected 불변식을 load 시 다시 검사한다.
  2. build_runtime_intercept_trace가 in-memory decision을 compact trace로 변환한다. Accepted decision은 선택 playback 상대 경로가 반드시 필요하고, rejected decision은 어떤 fallback playback도 참조할 수 없다.
  3. write_runtime_intercept_trace는 기존 파일을 덮어쓰지 않는다. Playback은 canonical JSON payload의 SHA-256으로 연결해 경로나 ID만 맞는 다른 파일을 거부한다.
  4. serve_pick_playback.py --runtime-trace가 trace의 상대 경로, playback ID, digest를 모두 확인한 후 atlas query, exact planning, full-frame validation, 최종 diagnostic 상태와 필터 수를 표시한다.
  5. 계산 구간은 기록된 duration을 candidate playback 시간축 위에 overlay한다. 실제 sensor 도착과 robot dispatch를 재현한 것처럼 표현하지 않도록 화면에 command authority가 없음을 계속 표시한다.

검증 결과

Accepted/rejected round-trip, overwrite 거부, playback path·ID·digest 검증, non-boolean 거부, recorded stage 구간을 포함한 집중 test 17개가 통과했다. 전체 planning 환경에서는 OpenCV 전용 세 module을 제외한 실제 test 241개가 통과했고, 그 세 module을 calibration 환경에서 실행한 14개도 통과해 총 255개를 확인했다. 전체 compileall, staged diff whitespace 검사, viewer CLI import도 통과했다.

관리형 planning 환경을 사용하는 서버 checkout에서도 source revision과 NumPy·SciPy·Trimesh·Pinocchio·HPP-FCL 버전을 확인하고 같은 집중 test 17개를 재실행해 모두 통과했다. 이 결과는 contract 재현성 검사이며 GPU latency 또는 real-time 성능 측정이 아니다.

남은 한계와 다음 단계

  • 현재 trace는 한 observation generation의 decision이다. 여러 generation의 arrival, supersession, cancellation을 하나의 append-only session으로 기록하지 않는다.
  • Viser stage는 recorded compute duration을 candidate timeline 위에 표시한다. 실제 wall-clock sensor·planner·controller causal replay가 아니다.
  • CPU exact planner와 full-frame validator는 여전히 offline oracle이다. Accelerated backend와 reference agreement benchmark가 필요하다.
  • Controller commit, feedback, abort, hand closing state와 hardware outcome은 별도 실행 trace 계약이 필요하다.

다음 구현은 여러 request·prediction·decision trace를 순서대로 묶는 append-only session과 deterministic observation replay다. 그 위에서 latest-generation cancellation과 deadline miss를 실제 기록 시간으로 반복 재생하고, 이후에만 accelerated backend의 p50/p95/p99와 reference 불일치를 측정한다.

AutoDex 필터 감사와 rolling 선택 구현이 이 trace가 기록하는 판정 규칙이다.
